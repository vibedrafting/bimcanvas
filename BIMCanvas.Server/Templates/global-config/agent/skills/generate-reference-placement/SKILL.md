# Generate 参考布置

> 你在本 Skill 中是施工方。第一职责是按图施工，不是重新设计。
> 设计权属于用户（通过参考图表达），你的专业体现在精准落地和品质识别。

## 核心禁令

**【硬约束】**以下四条在任何环节、任何执行模式下都不可违反：

1. **不得添加** `v0.2` 中没有的家具或附属件
2. **不得删除** `v0.2` 中已有家具；若确实无法落地，只能走授权流程
3. **不得侵占** `v0.2` 中记录的保留空段
4. **不得改变** `v0.2` 指定的角部或邻接关系——不能在同一面墙上自由换端点

WHY：用户通过参考图表达了设计意图，图纸是用户意图的契约。违反这四条 = 擅自改写用户意图。

---

## 1. 执行模式

进入本 Skill 后，先确认执行模式：

- **交互模式**：当前可用工具包含 `AskUserQuestion`（主控 Agent 直接执行）
- **自主模式**：当前可用工具不包含 `AskUserQuestion`（layout-agent 执行）

后续所有需要用户确认的节点，统一按当前模式处理：

- 交互模式 → 提问确认
- 自主模式 → 选择"最可施工"替代方案，标记"自动改图纸"

---

## 2. 入场动作

**【必须】**进入本 Skill 后第一步调用：

```text
load_semantic_plan({ zoneId })
```

只接受：

- `status = ok` 且 `planType = reference` → 继续
- `status = missing` → 停止，说明未找到图纸
- `status = ambiguous_legacy` → 停止，说明旧图纸不可自动判定
- `planType ≠ reference` → 停止，说明图纸类型不匹配

读取后必须显式复述：

- `planType` 与 `effectiveVersion`
- 完整家具清单（每项的墙面/角部/朝向）
- 保留空段清单
- 若有"自动适配"或"自动改图纸"标记，也必须复述

若任何一项仍不足以唯一定位到具体墙段或角部，按执行模式处理。

如果当前设计区含 `subZones`：

- 图纸仍从父设计区 `zoneId` 读取
- 实际写入目标是子分区的 `modules.json`
- `validate_layout` 使用子分区 `zoneIds`

---

## 3. 施工前读取

- `references/design_principles.md`
- `references/design_evaluation.md`
- `modules/module_library.json`
- `schemes/zones.json`
- 当前 `modules.json`（若已存在）
- 对应房间策略文件：`references/bedroom.md` / `references/bathroom.md` / `references/livingroom.md`

**房间策略文件的角色**：在 reference 模式下只负责"怎么合法落地"（模块选型、坐标计算、间距规范），不负责"决定要不要换位置、补家具、吞留白"。

---

## 4. 按图施工

规则优先级（固定）：

1. `semantic_plan` 中的家具清单与保留空段
2. `validate_layout` 等几何硬约束
3. 房间施工规则（仅用于合法性）

**【必须】**保留空段按一级对象处理：先从目标墙段中扣除保留空段，再做模块选型。

快路径：

1. 复述图纸中的家具清单与保留空段
2. 先从目标墙段中扣除保留空段
3. 逐项施工家具
4. 一次性写入完整 `modules.json`
5. `validate_layout`
6. 若无偏离，进入 Layer 1 验证

反例：

- 图纸没有床头柜，却自动补双床头柜（违反禁令 1）
- 图纸有门侧留白，却把衣柜排满整墙（违反禁令 3）
- 图纸有梳妆台在暗角，却因"采光更好"改到窗边（擅自改写用户意图）

---

## 5. 修正循环

验证失败时按优先级修正：

`平移 → 旋转 → 缩小 → 拆除附属件 → 替换 → 移除`

以下操作等于修改图纸，需要授权：

- 跨墙面迁移
- 删除图纸家具
- 侵占图纸保留空段
- 把家具从指定角部/邻接位置改到同墙另一端

按执行模式处理：交互模式先询问用户；自主模式选择最可施工的替代方案，标记"自动改图纸"。

---

## 6. Layer 1 验证

`validate_layout` 通过后，继续做：

- 可达性验证
- 功能完整性验证

任何一项失败，继续修正并重新验证。

---

## 7. 优化尾段

**【必须】**调用截图工具审查结果，参照 `design_evaluation.md` 做品质复核。

**【必须】**审查截图时以当前视觉证据为准。若截图显示的布局与 modules.json 中的数据不一致，以截图为准重新审查，不得用已写入数据解释截图。

识别流程与 derived 模式一致——逐维度审查，记录可优化项。

执行权限：

- **交互模式**：向用户汇报识别到的优化项及建议 → 用户明确许可后才能执行优化 → 优化后重新 `validate_layout`
- **自主模式**：记录识别到的优化项 → 不执行优化（无法获得用户许可）→ 在汇报中列出优化建议

WHY：设计权属于用户。AI 的品质识别能力始终有价值（用户需要知道哪里可以更好），但执行优化 = 偏离用户意图，必须经过授权。

**【必须】**即使获得优化授权，优化动作也不得违反核心禁令。

---

## 8. 汇报

最终汇报必须包含：

- 施工依据：`planType=reference` + `effectiveVersion`
- 放置结果：家具、墙面、朝向、保留空段执行结果
- 验证结果：布局验证 + 可达性 + 功能完整性
- 识别摘要（来自参考图翻译阶段）
- 适配说明
- 与原参考图存在的偏离点
- 若发生自动兜底：`自动适配`（translation 阶段）/ `自动改图纸`（placement 阶段）
- 优化建议（若有识别到的优化项）

---

## 约束总览

**【硬约束】**

- 核心禁令四条（见文件头部）
- 入场必须 `load_semantic_plan`，仅接受 `planType=reference`
- 一次性写入后必须 `validate_layout`
- 优化执行必须经过用户授权

**【软指导】**

- 修正优先级：平移 → 旋转 → 缩小 → 拆除附属件 → 替换 → 移除
- 房间策略文件用于合法性计算，不用于设计决策

**【自由区域】**

- 家具间精确间距（在满足通道要求前提下）
- 附属件精确位置（椅子、镜柜等）
- 模块参数化尺寸的精确值（在 limits 范围内）
- 坐标计算方式
