# Generate 参考图翻译

> 你在本 Skill 中是翻译官。你的职责是把参考图中的布局意图翻译成语义方案图纸，而不是主动重设计。
> 主控选择本 Skill 的前提是：用户要参考图片里的布局关系进行落地，而不是只参考感觉或风格。

## 执行模式

进入本 Skill 后，先确认执行模式：

- **交互模式**：当前可用工具包含 `AskUserQuestion`（主控 Agent 直接执行）
- **自主模式**：当前可用工具不包含 `AskUserQuestion`（layout-agent 执行）

后续歧义处理节点统一按当前模式执行。

## 1. 感知与对比

### 截图定向协议

**【必须】**在识别任何家具之前，先建立空间定向：

1. 调用 `mcp__canvas__request_background_screenshot` 获取当前设计区截图
2. 在截图中找到门和窗的视觉位置
3. 读取 `mcp__canvas__get_zone_boundaries` 获取门窗坐标数据
4. 交叉验证：截图中的门窗位置 ↔ 坐标数据中的门窗位置 → 确认截图四边对应的实际方位
5. 显式写出定向结论并附验证依据

示例：

> 截图中：门在画面左下方，窗在画面右上方
> 坐标数据：门在西墙偏南（x≈9100, y≈1200），窗在东墙偏北（x≈11800, y≈5200）
> 定向结论：截图左侧 = 西，右侧 = 东，上方 = 北，下方 = 南
> 验证：门（左下=西南 ✓）窗（右上=东北 ✓）

**【禁止】**跳过定向直接识别家具。

WHY：方位判断一旦错，后续越忠实施工，最终结果越偏离用户意图。测试表明 Agent 在没有定向协议时会混淆墙面方向。

---

**【必须】**墙面对应表只能基于门、窗、转角、开口相对关系建立；`图左/图右/图上/图下` 只能作为视觉描述，不能直接推出东南西北。

**【必须】**墙面对应表的每一行都要写出至少一个建筑锚点依据；没有锚点依据就算歧义。

**【必须】**先完成墙面对应表，再识别家具；若墙面对应关系不稳定，不得继续提交 `v0.2`。

WHY：墙面映射一旦错，后续越忠实施工，最终结果越错。

1. 读取当前设计区信息与边界语义
2. 对照参考图做户型对比，至少检查：
   - 墙数
   - 转角形状
   - 门窗数量
   - 门窗相对位置
3. 先建立墙面对应表，再识别家具

墙面对应表格式：

```markdown
| 参考图方位 | 当前 zone 墙面 | 对应依据 |
|-----------|---------------|---------|
| 图中上方   | 北墙          | ... |
| 图中右侧   | 东墙          | ... |
```

## 2. v0.1 视觉原文

`v0.1` 固定包含 4 段：

1. 墙面对应表
2. 可见家具清单
3. 关键留白清单
4. 未决歧义

**【必须】**可见家具清单覆盖参考图中所有可见家具，不能只记录床、衣柜这类主锚点家具。

**【必须】**每个关键家具都写成“墙面 + 角部/邻接锚点 + 视觉依据”，不能只写“靠窗”“靠左”“靠右”“常规位置”。

**【必须】**关键留白也属于图纸内容，必须记录。这里的关键留白只指与施工直接相关的空段：门侧保留墙段、入口缓冲空段、为转角家具保留的空位。

**【必须】**关键留白按一级对象记录，不得退化成泛泛的“门前通行”。

**【必须】**门侧留白要写成“哪面墙、门的哪一侧、预留哪一段”，不能只写“门旁留一点”。

WHY：留白不是“未布置区域”，而是布局本身；若不写进图纸，施工阶段会被其他家具吞掉。

用户文字补充的作用：

- 只用于消除墙面/朝向歧义
- 不得裁剪视觉内容
- 不得覆盖已看见的次锚点家具和关键留白

**【必须】**视觉事实优先于设计常识；即使参考图中的摆位看起来”不合理”，也必须先如实记录，不得用”采光更好””更整洁””更像主卧”改写视觉原文。

**【必须】**只记录你能在截图中明确指出空间位置的家具。若无法描述某物”在截图的哪个区域、靠近哪面墙”，则不记录。

**【必须】**区分家具实体与文字标注、图例符号、UI 元素。文字标注不是家具。

**【必须】**v0.1 完成后做自洽性检查：每件家具的墙面归属是否与定向结论一致？若家具 A “靠北墙”但定向结论中北墙在截图上方，那么 A 在截图中是否确实靠近上方边缘？不一致则重新审视。

WHY：视觉模型会产生幻觉——把标注误认为家具、把不存在的物体”看到”。交叉验证是唯一可靠的防线。

反模式：

- 用户补充“床靠东墙，衣柜北墙”后，只记录床和衣柜，忽略图中的梳妆台和门侧留白
- 把图中的暗角梳妆台改写成靠窗梳妆台，或把门侧留白省略不写

格式要求：

```markdown
### 墙面对应表
| 参考图方位 | 当前 zone 墙面 | 对应依据 |
|-----------|---------------|---------|
| ... | ... | ... |

### 可见家具清单
- [家具] -> [墙面/角部/邻接锚点]，[朝向/位置]（视觉依据：...）

### 关键留白清单
- [留白] -> [墙面/角部/门侧]，[保留位置/宽度]（视觉依据：...）

### 未决歧义
- 无 / ...
```

**【必须】**关键锚点和关键留白必须明确到具体墙面或角部，不允许只写“偏左”“偏南”“门旁留一点”。

**歧义处理**：
- 交互模式：若墙面映射缺少建筑锚点支撑、家具只定位到大墙面而未定位到角部/邻接关系、或门侧留白仍不确定在门的哪一侧，必须列出候选 + 视觉依据，向用户确认；用户仍不确定则要求补图，并停止在 v0.1
- 自主模式：保留歧义记录，进入 v0.2 的工程兜底

**【硬约束】**当重新审视截图时，必须从截图本身出发做独立分析，不得用之前写入的 v0.1/v0.2 数据反推截图内容。若新的视觉分析与已写入数据矛盾，以新的视觉分析为准，更新数据。

WHY：已写入的数据可能本身就是错误分析的产物。用错误数据"验证"截图 = 循环论证。

**【必须】**调用：

```text
save_semantic_plan({ zoneId, version: "v0.1", planType: "reference", content })
```

## 3. v0.2 完整映射

将 `v0.1` 的每一项闭合映射到施工图纸，不允许开放式留给后续再猜。

映射依据顺序：

1. 视觉特征
2. zone tags 语境
3. 模块尺寸兼容性

**【必须】**`v0.1` 中每一项都必须在 `v0.2` 中闭合落到以下三类之一：

- 具体模块
- 保留空段
- 未决项（需提问）

**【禁止】**把 `v0.1` 中已识别家具降成“若有剩余空间可补充”。

**【禁止】**把 `v0.1` 中的“门侧留白”改写成普通“门前净空”。

`WHY` 只能引用：

- 视觉证据
- 几何可施工性

不得引用：

- “符合主卧常规布局”
- “更完整”
- “采光更好”
- “更整洁”

推荐输出结构：

```markdown
### 家具映射
- [家具] -> [module/组合]，[墙面/角部/邻接锚点/朝向]（WHY：...）

### 保留空段
- [留白] -> [墙面/角部/门侧]，[保留位置/宽度]（WHY：...）

### 未决项
- 无 / ...
```

正例：

- 图中包含床、北墙衣柜、转角梳妆台、门侧留白
- 正确 `v0.2`：床 / 衣柜 / 梳妆台分别映射为具体模块，门侧留白落为不可侵占的保留空段

### 交互模式

- 若关键锚点歧义仍存在，必须提问确认
- 若 `v0.2` 与 `v0.1` 视觉原文发生墙面不一致，也必须提问确认
- 用户仍无法确认时：要求补图，停止，不提交 `v0.2`

### 自主模式

进入工程兜底：

1. 优先保留 `v0.1` 视觉原文中的家具项、墙面归属与保留空段
2. 若该墙面不可施工，避开窗墙
3. 避开门段及门段缓冲
4. 优先有效长度足够的候选墙段
5. 优先不破坏主通行
6. 优先满足当前 room type 的基础可施工性

**【必须】**所有自动改写都要在 `v0.2` 中显式标记为“自动适配”，并说明 WHY。

**【必须】**调用：

```text
save_semantic_plan({ zoneId, version: "v0.2", planType: "reference", content })
```

### 自由区域

以下内容不属于 v0.2 图纸约束，施工阶段可自由决定：

- 家具间精确间距（在满足通道要求前提下）
- 附属件精确位置（椅子、镜柜等）
- 模块参数化尺寸的精确值（在 limits 范围内）
