  为什么有两个后端项目？

  根据 Architecture.md §4.1，当前设计其实是同进程运行的：

  ┌─────────────────────────────────────────────────────────┐
  │                    BIMCanvas.Web.Server                  │
  ├─────────────────────────────────────────────────────────┤
  │   ┌─────────────────┐      ┌─────────────────────────┐  │
  │   │  Canvas-MCP     │ ←──→ │  CanvasStateManager     │  │
  │   │  Tools 实现     │      │  (内存中的画布状态)      │  │
  │   └─────────────────┘      └─────────────────────────┘  │
  │            ↑                           ↑                │
  │   ┌────────┴────────┐      ┌───────────┴───────────┐    │
  │   │  MCP Protocol   │      │  SignalR Hub          │    │
  │   │  (stdio)        │      │  (WebSocket)          │    │
  │   └─────────────────┘      └───────────────────────┘    │
  └─────────────────────────────────────────────────────────┘
           ↑                               ↑
      Claude Code                     Web Browser

  关键点：Canvas-MCP 的功能是内嵌在 Web.Server 中的，它们共享状态。

  问题分析

  当前架构中 BIMCanvas.MCP.Canvas
  作为独立项目存在的原因可能是为了代码组织清晰。但实际上：
  - 两者在同一进程运行
  - 共享画布状态
  - 不需要 IPC 通信

  这确实造成了理解上的困惑。

  建议：简化为单一后端

  你的需求很清晰：
  1. 接收 JSON 数据并渲染显示
  2. 网页交互式编辑
  3. 渲染+截图功能

  建议合并为一个项目：

  BIMCanvas.Server/                        【单一后端项目】(.NET 6+)
  ├── Program.cs                           入口（支持 MCP stdio + Web Host）
  ├── Hubs/
  │   └── CanvasHub.cs                     SignalR 实时通信
  ├── Controllers/
  │   └── CanvasController.cs              REST API
  ├── McpTools/                            MCP 工具定义
  │   ├── CanvasTools.cs
  │   └── ModuleTools.cs
  ├── Services/
  │   ├── CanvasStateManager.cs            画布状态管理
  │   ├── ZoneCalculator.cs                Zone 计算（rawBoundary →
  innerBoundary）
  │   ├── ModulePlacementService.cs        Module 放置转换
  │   └── ScreenshotService.cs             截图服务
  └── ...

  关于渲染格式

  你提到"或许也不是 SVG"——这是个好问题：

  | 方案                       | 优点            | 缺点              |
  |--------------------------|---------------|-----------------|
  | 前端直接渲染 JSON → Canvas/SVG | 交互性好、前端掌控渲染逻辑 |
  需要前端实现渲染逻辑      |
  | 后端生成 SVG 传给前端            | 前端简单、渲染逻辑集中   | SVG
  作为中间格式增加复杂度 |

  建议采用前端直接渲染：
  - 后端只传递 JSON 数据
  - 前端根据 JSON 渲染（可以是 SVG、Canvas 2D、甚至 WebGL）
  - 截图功能后端调用无头浏览器渲染 JSON → 图片

  这样就不需要 SVG 作为中间格式。

  2. BIMCanvas.Revit 项目职责

  讨论问题：
  - BIMCanvas.Revit 项目在整个流程中负责的具体功能有哪些？
  - 负责的具体功能，分别需要接受什么信息、交付什么数据？

  结论：

  BIMCanvas.Revit 项目只负责原始数据提取：

  | 功能    | 输入         | 输出                        |
  |-------|------------|---------------------------|
  | 墙体提取  | Revit View | List<Wall>（轮廓多边形）         |
  | 门窗提取  | Revit View | List<Opening>（线段 + 类型）    |
  | 房间提取  | Revit View | List<Room>（边界 + 类型）       |
  | 视图元数据 | Revit View | Metadata（viewId, levelId） |

  不负责：
  - ❌ Zone 计算（innerBoundary、exclusionAreas）
  - ❌ WallFinish 计算
  - ❌ ZoneTag 推断

  理由：Canvas 后端是使用 Zone 和 Module

  PlacementAgent（布置 Agent）设计

  核心概念

  你提出的是一个布置 Agent 的概念，它负责：
  - 接收布置任务（整体生成/局部调整）
  - 分析当前画布状态
  - 生成/调整模块布置
  - 验证布置结果

  三种触发方式

  ┌─────────────────────────────────────────────────────────────────┐
  │                      PlacementAgent                              │
  │                    （布置决策核心）                               │
  ├─────────────────────────────────────────────────────────────────┤
  │  输入：Zone 信息、已有模块、用户意图、模块库                       │
  │  输出：模块布置方案（位置、朝向）                                  │
  └─────────────────────────────────────────────────────────────────┘
                                ▲
                ┌───────────────┼───────────────┐
                │               │               │
       ┌────────┴────────┐ ┌────┴────┐ ┌────────┴────────┐
       │  触发方式 1     │ │ 触发方式 2 │ │  触发方式 3     │
       │  AI 对话触发    │ │ Web 按钮   │ │  自动修正触发   │
       │                 │ │           │ │                 │
       │ "帮我布置客厅"   │ │ "一键布置" │ │ 检测到重叠/越界 │
       │  ↓              │ │  ↓        │ │  ↓              │
       │ Claude Code     │ │ Server    │ │ Server          │
       │ 调用 Agent      │ │ 调用 Agent │ │ 调用 Agent      │
       └─────────────────┘ └───────────┘ └─────────────────┘

  Agent 的架构位置

  关键问题：PlacementAgent 在哪里运行？

  | 方案  | 位置          | 优点                        | 缺点       |
  |-----|-------------|---------------------------|----------|
  | A   | MCP 工具      | Claude Code 和 Server 都能调用 | MCP 协议限制 |
  | B   | 独立 AI 服务    | 灵活、可独立部署                  | 架构复杂
   |
  | C   | Server 内部服务 | 简单、状态共享                   | 耦合度高
  |

  推荐方案：混合架构

  BIMCanvas.Server/
  ├── Services/
  │   ├── PlacementService.cs          ← 布置逻辑核心
  │   │   ├── GenerateLayout()         ← 整体生成
  │   │   ├── AdjustModule()           ← 局部调整
  │   │   ├── ValidateLayout()         ← 验证布置
  │   │   └── AutoFix()                ← 自动修正
  │   │
  │   └── PlacementAgentBridge.cs      ← AI Agent 桥接
  │       └── InvokeAI()               ← 调用 Claude API（复杂决策时）
  │
  ├── McpTools/
  │   └── PlacementTools.cs            ← MCP 工具封装
  │       ├── generate_layout          ← 暴露给 Claude Code
  │       └── adjust_module
  │
  ├── Controllers/
  │   └── PlacementController.cs       ← REST API
  │       └── POST /api/canvas/{id}/generate  ← Web 按钮调用
  │
  └── Hubs/
      └── CanvasHub.cs
          └── OnLayoutError()          ← 检测到错误时触发修正

     三、关键实现细节

     3.1 CoordinateAdapter 设计

     核心职责：Revit XYZ (feet, 项目坐标系) → BIMCanvas Point2D (mm, 
     视图坐标系)

     public class CoordinateAdapter
     {
         private readonly XYZ _viewOrigin;      // 
     视图裁剪框左下角（世界坐标）
         private readonly double _viewRotation; // 视图旋转角度（弧度）

         public CoordinateAdapter(View view)
         {
             // 从视图裁剪框计算原点
             _viewOrigin = CalculateViewOrigin(view);
             _viewRotation = CalculateViewRotation(view);
         }

         /// <summary>
         /// Revit XYZ → BIMCanvas Point2D
         /// </summary>
         public Point2D ToPoint2D(XYZ revitPoint)
         {
             // 1. 相对于视图原点
             var relative = revitPoint - _viewOrigin;

             // 2. 应用视图旋转（如果有）
             var rotated = RotatePoint(relative, -_viewRotation);

             // 3. 单位转换 feet → mm (使用 Core 层 UnitConverter)
             return new Point2D(
                 UnitConverter.ToMillimeters(rotated.X),
                 UnitConverter.ToMillimeters(rotated.Y)
             );
         }

         /// <summary>
         /// BIMCanvas Point2D → Revit XYZ
         /// </summary>
         public XYZ ToXYZ(Point2D point, double elevation = 0)
         {
             // 1. 单位转换 mm → feet
             var x = UnitConverter.ToFeet(point.X);
             var y = UnitConverter.ToFeet(point.Y);

             // 2. 应用视图旋转
             var rotated = RotatePoint(new XYZ(x, y, 0), _viewRotation);

             // 3. 加上视图原点偏移
             return rotated + _viewOrigin + new XYZ(0, 0, elevation);
         }
     }

       182 +  ### 4. 决策分层策略
       183 +  
       184 +  - **优先级**：Suggestion
       185 +  
       186 +  - **双轨决策**：
       187 +  
       188 +  ```csharp
       189 +  public class PlacementService
       190 +  {
       191 +      private readonly RuleEngine _rules;           // 
           + 规则引擎（快速、确定性）
       192 +      private readonly PlacementAgentBridge _aiBridge;  // AI
           +  桥接（复杂决策）
       193 +  
       194 +      public async Task<LayoutResult> GenerateLayoutAsync(
       195 +          string canvasId,
       196 +          GenerateOptions options)
       197 +      {
       198 +          // 1. 获取画布状态
       199 +          var canvas = await 
           + _stateManager.GetAsync(canvasId);
       200 +  
       201 +          // 2. 简单场景：使用规则引擎
       202 +          if (IsSimpleCase(canvas, options))
       203 +          {
       204 +              return _rules.Generate(canvas, options);
       205 +          }
       206 +  
       207 +          // 3. 复杂场景：调用 AI
       208 +          return await _aiBridge.InvokeAI(canvas, options);
       209 +      }
       210 +  
       211 +      private bool IsSimpleCase(CanvasDocument canvas, 
           + GenerateOptions options)
       212 +      {
       213 +          // 判断条件：Zone 
           + 数量少、无复杂约束、用户未指定特殊需求等
       214 +          return canvas.Zones.Count <= 2 && 
           + !options.HasCustomConstraints;
       215 +      }
       216 +  }
       217 +  ```

       219 +  ### 5. 潜在风险
       220 +  
       221 +  - **PlacementAgentBridge 的实现复杂度**：调用 Claude API 
           + 需要处理 Token 限制、超时、重试等问题
       222 +    - **缓解**：MVP 阶段可先只实现规则引擎，AI 
           + 桥接作为后续增强
       223 +  
       224 +  - 
           + **自动修正的触发条件**：过于敏感可能导致用户操作被频繁覆盖
       225 +    - **缓解**：设置阈值（如重叠面积 > 10%）或用户确认机制
       226 +  
       227 +  - **多入口一致性**：MCP、REST、SignalR 
           + 调用同一服务，需确保状态同步
       228 +    - **缓解**：PlacementService 内部加锁或使用乐观并发控制
