## 一、设计哲学

### 1.1 整体架构定位

```
┌─────────────────────────────────────────────────────────────────┐
│                    BIMCanvas Agent 架构                          │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│   ┌─────────────────────────────────────────────────────────┐   │
│   │  主控 Agent（协调者）                                    │   │
│   │  • 分析用户意图，判断任务类型                            │   │
│   │  • 派发任务给 SubAgent                                  │   │
│   │  • 整合结果，向用户汇报                                  │   │
│   └─────────────────────────────────────────────────────────┘   │
│                              ↓ 派发                             │
│   ┌─────────────────────────────────────────────────────────┐   │
│   │  SubAgent（领域专家）                                    │   │
│   │  • layout-agent：家具布置专家                            │   │
│   │  • zone-agent：空间分区专家                              │   │
│   │  • ...                                                  │   │
│   └─────────────────────────────────────────────────────────┘   │
│                              ↓ 调用                             │
│   ┌─────────────────────────────────────────────────────────┐   │
│   │  MCP 工具（能力扩展）                                    │   │
│   │  • 领域特定功能封装                                      │   │
│   │  • 数据访问接口                                          │   │
│   └─────────────────────────────────────────────────────────┘   │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 1.2 主控 Agent 定位

**角色**：任务协调者、意图解析器、结果整合者

**核心职责**：
- 理解用户自然语言，判断任务类型和复杂度
- 决定是否需要调用 SubAgent，选择合适的 SubAgent
- 整合 SubAgent 返回的结果，向用户汇报

**不应该做的事**：
- 直接执行领域专业任务（如家具布置计算）
- 绕过 SubAgent 直接操作专业数据

### 1.3 SubAgent 定位

**角色**：领域专家、任务执行者

**核心职责**：
- 专注于单一领域的专业任务
- 严格按照任务描述执行，不越权
- 完成后返回结构化结果

**不应该做的事**：
- 自作主张扩展任务范围
- 在查询任务中修改数据
- 再派发 SubAgent（禁止嵌套）

### 1.4 MCP 工具定位

**角色**：能力扩展、数据接口

**核心职责**：
- 封装领域特定功能（如截图、验证）
- 提供标准化数据访问接口
- 隔离复杂实现细节

**与 SubAgent 的区别**：

| 维度 | SubAgent | MCP 工具 |
|------|----------|----------|
| **本质** | AI Agent，有决策能力 | 函数调用，无决策能力 |
| **复杂度** | 复杂任务，需要推理 | 简单任务，确定性输出 |
| **自主性** | 有限自主性 | 无自主性，被动调用 |
| **示例** | 布置家具、规划方案 | 读取数据、验证碰撞 |

## 二、核心设计原则

### 2.1 任务类型分类（关键！）

> **教训来源**：layout-agent 在执行"统计模块数量"查询任务时，错误地写入了数据。

**必须区分两种任务类型**：

| 任务类型 | 操作类型 | 允许的工具 | 示例 |
|----------|----------|------------|------|
| **query** | 只读 | Read, Glob, Grep | 统计、查看、列出、检查 |
| **execute** | 可写 | Read, Write, Edit, Glob, Grep | 布置、添加、移动、删除 |

**主控 Agent 判断规则**：

```markdown
## 任务类型判断

**query（只读）任务关键词**：
- "有多少..."、"统计一下..."、"查看..."、"列出..."
- "当前状态是..."、"已经布置了什么..."、"检查..."
- 特征：用户只想获取信息，不期望系统做任何修改

**execute（可写）任务关键词**：
- "帮我布置..."、"添加一个..."、"移动..."、"删除..."
- "设计..."、"创建..."、"修改..."、"更新..."
- 特征：用户明确期望系统修改数据
```

**任务描述规范**（主控 Agent 调用 SubAgent 时）：

```markdown
调用 SubAgent 时，必须在任务描述开头指定：

【操作类型】: query 或 execute
【用户需求】: ...
【目标对象】: ...
【约束条件】: ...
```

### 2.2 最小权限原则

**按任务类型配置工具权限**：

```python
# query 任务：只读工具
query_tools = ["Read", "Glob", "Grep"]

# execute 任务：完整工具
execute_tools = ["Read", "Write", "Edit", "Glob", "Grep"]
```

**SubAgent 提示词中明确声明**：

```markdown
## 工具权限

**query 模式工具**：Read, Glob, Grep
**execute 模式工具**：Read, Write, Edit, Glob, Grep

⚠️ query 模式下禁止使用 Write 和 Edit 工具
```

### 2.3 行为边界约束

**SubAgent 提示词必须包含的约束**：

```markdown
## 行为边界

### 禁止行为
- ❌ 在 query 任务中使用 Write/Edit 修改任何数据
- ❌ 在发现空数据时自动创建示例数据
- ❌ 执行用户未明确要求的操作
- ❌ 自作主张扩展任务范围
- ❌ 猜测用户意图并主动执行

### 允许的主动行为
- ✅ 发现问题时提出建议（但不自动执行）
- ✅ 在 execute 任务中优化布置方案
- ✅ 报告执行过程中遇到的问题
```

### 2.4 主动性边界

> **核心原则**：宁可少做，不可多做

**主动性等级**：

| 等级 | 描述 | 示例 |
|------|------|------|
| **被动执行** | 严格按任务描述执行 | query 任务 |
| **有限主动** | 在任务范围内做合理优化 | execute 任务中的布置优化 |
| **建议但不执行** | 发现问题时报告，等待指令 | 发现空数据时报告而非创建 |

**反例（禁止）**：

```
用户问"有多少模块"
→ Agent 发现是空数组
→ Agent 认为"用户可能想要布置"
→ Agent 自动创建数据  ← 错误！
```

**正例（正确）**：

```
用户问"有多少模块"
→ Agent 发现是空数组
→ Agent 报告"当前项目没有布置任何模块，数量为 0"
→ 结束  ← 正确！
```

## 三、提示词设计规范

### 3.1 结构模板

```markdown
---
name: {agent-name}
description: {一句话描述，用于主控 Agent 判断何时调用}
tools: {工具列表，逗号分隔}
model: {模型：sonnet/opus/haiku}
---

你是 BIMCanvas 的 {agent-name}，{角色定位}。

## 职责
{核心职责列表，3-5 条}

## 操作模式

### query 模式（只读）
{query 模式的行为规范}

### execute 模式（可写）
{execute 模式的行为规范}

## 文件结构
{输入/输出文件说明}

## 核心规则
{领域规则，精简版}

## 工作流程
{步骤化的工作流程}

## 行为边界
{禁止行为 + 允许行为}

## 输出格式
{输出数据格式说明}

## 交互规范
{语言、风格要求}
```

### 3.2 长度限制（重要！）

> **已知问题**：SubAgent 提示词过长会导致加载失败。

**长度建议**：

| 指标 | 建议值 | 说明 |
|------|--------|------|
| **总字符数** | < 3000 字符 | 超过可能导致加载失败 |
| **总行数** | < 150 行 | 便于维护和阅读 |
| **单条规则** | < 50 字符 | 便于 AI 理解 |

**精简策略**：

1. **分离详细规则到知识库**
   ```markdown
   ## 知识库

   知识库路径：`knowledge/placement_guide.md`

   ### 查阅规则
   - 生成任务：必须查阅
   - 编辑任务：简单任务无需查阅
   ```

2. **使用索引而非完整内容**
   ```markdown
   ## 章节索引

   | 需求 | 关注章节 |
   |------|----------|
   | 通道宽度 | 四、尺寸标准 |
   | 家具朝向 | 六、朝向决策 |
   ```

3. **精简规则表达**
   ```markdown
   # 冗长版（避免）
   当用户请求布置家具时，需要确保大型家具如床、衣柜、沙发等尽量靠墙放置

   # 精简版（推荐）
   - 大型家具靠墙（床、衣柜、沙发）
   ```

### 3.3 关键要素清单

**必须包含的要素**：

| 要素 | 重要性 | 说明 |
|------|--------|------|
| 操作模式定义 | ⭐⭐⭐ | 必须区分 query/execute |
| 行为边界 | ⭐⭐⭐ | 明确禁止和允许的行为 |
| 工作流程 | ⭐⭐ | 步骤化的执行流程 |
| 输出格式 | ⭐⭐ | 数据格式规范 |
| 知识库引用 | ⭐ | 详细规则外置 |

### 3.4 常见陷阱

| 陷阱 | 问题 | 解决方案 |
|------|------|----------|
| **缺少操作模式** | Agent 不知道是否可以写入 | 明确定义 query/execute 模式 |
| **工作流以写入结尾** | 默认所有任务都要写入 | 区分 query 和 execute 工作流 |
| **缺少禁止行为** | Agent 过度主动 | 明确列出禁止行为 |
| **提示词过长** | 加载失败 | 精简 + 知识库分离 |
| **规则过于笼统** | Agent 自由发挥过度 | 具体化规则，给出示例 |

## 四、SubAgent 清单与职责

### 4.1 layout-agent（家具布置专家）

**职责**：
- 读取房间分区数据，理解空间特点
- 分析门窗位置，规划动线
- 根据布置规则为房间布置家具
- 输出符合规范的布置结果

**操作模式**：

| 模式 | 触发条件 | 允许工具 |
|------|----------|----------|
| query | 统计、查看、检查 | Read, Glob, Grep |
| execute | 布置、添加、移动、删除 | Read, Write, Edit, Glob, Grep |

**关键约束**：
- query 模式：只能读取和报告，禁止修改
- execute 模式：可以修改 `schemes/modules.json`

### 4.2 zone-agent（空间分区专家）

**职责**：
- 分析户型结构
- 划分功能区域
- 生成 Designable Zone

**操作模式**：与 layout-agent 类似

### 4.3 规划中的 SubAgent

| SubAgent | 职责 | 状态 |
|----------|------|------|
| **strategy-agent** | 策略生成、方案对比 | 规划中 |
| **validation-agent** | 布置验证、冲突检测 | 规划中 |
| ~~git-agent~~ | ~~版本管理、分支操作~~ | **已取消** |

> **注**：Git 操作改由 MainAgent 统一处理，取消独立 git-agent。原因见 §4.4。

### 4.4 MainAgent Git 职责（新增）

**设计决策**：Git 操作由 MainAgent 统一管理，SubAgent 不参与。

**原因**：
- 避免多个 SubAgent 并行时的 Git 冲突
- 便于在任务完成后统一提交
- SubAgent 提示词字数限制（< 3000 字符），无法容纳 Git 知识

**MainAgent Git 工具**：
- `git_status` - 获取工作区状态
- `git_commit` - 提交更改
- `git_branches` - 列出分支
- `git_checkout` - 切换/创建分支
- `git_merge` - 合并分支
- `git_discard` - 放弃更改
- `worktree_create` - 创建隔离 Worktree
- `worktree_remove` - 删除 Worktree
- `worktree_list` - 列出所有 Worktree

**SubAgent 约束**：
- tools 列表不包含 git_* 工具
- 提示词不包含 Git 操作知识
- 只负责写入分区文件，不执行 Git 命令

**操作流程**：
1. 任务开始前：MainAgent 检查 `git_status()` 确认工作区状态
2. SubAgent 工作期间：在独立 Worktree 中操作文件
3. 任务完成后：MainAgent 合并分支、执行 `git_commit()`、清理 Worktree

## 五、协作工作流

### 5.1 主控 Agent 调用流程

```
┌─────────────────────────────────────────────────────────────────┐
│                     主控 Agent 调用流程                          │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  1. 接收用户输入                                                 │
│     ↓                                                           │
│  2. 判断任务类型                                                 │
│     • 是否需要调用 SubAgent？                                    │
│     • 如果需要，是 query 还是 execute？                          │
│     ↓                                                           │
│  3. 构建任务描述                                                 │
│     • 【操作类型】: query/execute                                │
│     • 【用户需求】: ...                                          │
│     • 【目标对象】: ...                                          │
│     ↓                                                           │
│  4. 调用 SubAgent                                                │
│     Task(subagent_type="layout-agent", prompt=任务描述)          │
│     ↓                                                           │
│  5. 接收结果                                                     │
│     ↓                                                           │
│  6. 整合并汇报给用户                                             │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 5.2 任务描述规范

**标准格式**：

```markdown
【操作类型】: {query | execute}
【用户需求】: {用户原始需求的准确描述}
【目标对象】: {目标房间/区域/文件，如果有}
【约束条件】: {特殊要求或限制，如果有}
【期望输出】: {期望 SubAgent 返回什么}
```

**query 任务示例**：

```markdown
【操作类型】: query
【用户需求】: 统计当前项目已布置的模块数量
【目标对象】: schemes/modules.json
【约束条件】: 仅统计，不做任何修改
【期望输出】: 模块数量 + 按类型分布（如果有）
```

**execute 任务示例**：

```markdown
【操作类型】: execute
【用户需求】: 在主卧布置一张双人床
【目标对象】: 房间 rz_3（主卧）
【约束条件】: 床头靠北墙，不阻挡门
【期望输出】: 更新后的 modules.json + 布置说明
```

### 5.3 结果整合规范

**SubAgent 返回格式**：

```markdown
【执行结果】: {成功 | 失败 | 部分成功}
【操作摘要】: {执行了什么操作}
【数据变更】: {修改了哪些文件，如果有}
【详细信息】: {具体数据或说明}
【问题报告】: {遇到的问题，如果有}
```

**主控 Agent 整合规则**：
- 成功：向用户汇报结果
- 失败：向用户解释原因，提供建议
- 部分成功：汇报完成部分，说明未完成原因

## 六、经验教训

### 6.1 已知问题与解决方案

#### 问题 1：SubAgent 在查询任务中修改数据

**问题描述**：
用户问"有多少模块"，layout-agent 发现 modules.json 是空数组后，自作主张写入了家具数据。

**根因分析**：
1. 主控 Agent 没有明确指定操作类型
2. SubAgent 提示词缺少 query 模式定义
3. SubAgent 工作流默认以 Write 结尾

**解决方案**：
- 主控 Agent 调用时必须指定操作类型
- SubAgent 提示词定义 query/execute 两种模式
- query 模式禁止使用 Write/Edit 工具

#### 问题 2：SubAgent 提示词过长导致加载失败

**问题描述**：
SubAgent 提示词文本过长时，会导致 SubAgent 加载失败。

**解决方案**：
- 提示词控制在 3000 字符以内
- 详细规则外置到知识库
- 使用索引引用而非完整内容

#### 问题 3：SubAgent 过度主动

**问题描述**：
SubAgent 在发现"问题"时，自作主张地"帮助"用户解决，违背用户原始意图。

**解决方案**：
- 明确列出禁止行为
- 强调"宁可少做，不可多做"原则
- 发现问题时报告而非自动解决

#### 问题 4：SubAgent 在空数据中产生幻觉

**问题描述**：
用户查询"有多少模块"，modules.json 实际为空数组 `[]`，但 Agent 返回了虚假的"18 个模块"结果。

**根因分析**：
1. Agent 读取了 modules.json 发现为空
2. Agent 读取了 room_zones.json 看到有 6 个房间
3. Agent 根据房间类型"推断"应该有什么家具
4. 编造了一个看似合理但完全虚假的结果

**解决方案**：
- 添加"数据真实性约束"：输出必须严格基于实际读取的文件内容
- 明确"空数据处理规则"：空数据时必须报告"数量为 0"，禁止推断
- 添加"输出验证"步骤：报告前验证内容与文件实际一致
- 在禁止行为中明确：禁止根据其他文件推断不存在的数据

#### 问题 5：Git 操作分散导致冲突

**问题描述**：
最初设计中，每个 SubAgent 可以独立执行 Git 操作（提交、分支切换等）。当多个 SubAgent 并行处理不同分区时，各自执行 Git 提交导致冲突和状态混乱。

**根因分析**：
1. Git 操作需要全局协调，不适合分散到各个 SubAgent
2. SubAgent 提示词字数限制（< 3000 字符），难以容纳完整的 Git 操作流程知识
3. 并行 SubAgent 同时操作 Git 会产生竞态条件

**解决方案**：
- **Git 操作集中到 MainAgent**：所有 Git 操作（commit/checkout/merge/worktree）由 MainAgent 统一执行
- **SubAgent 只操作文件**：SubAgent 只负责读写分区文件（schemes/{zoneId}/modules.json），不执行 Git 命令
- **MainAgent 任务后统一提交**：SubAgent 完成后，MainAgent 合并分支并统一提交
- **取消 git-agent**：原计划的独立 git-agent 改为 MainAgent 内置能力

详细设计见 §4.4 MainAgent Git 职责。

### 6.2 最佳实践

#### 实践 1：提示词模块化

```
提示词核心（< 3000 字符）
├── 角色定义
├── 操作模式
├── 行为边界
└── 知识库引用

知识库（详细规则）
├── 布置规则
├── 尺寸标准
└── 常见错误
```

#### 实践 2：防御性设计

在 SubAgent 提示词中添加防御性检查：

```markdown
## 执行前检查

在执行任何操作前，确认：
1. 操作类型是否为 execute？（query 禁止修改）
2. 操作是否在任务描述范围内？
3. 是否有明确的用户授权？

如果任何一项不满足，停止执行并报告。
```

#### 实践 3：渐进式开发

1. **先实现 query 模式**：确保只读功能正确
2. **再实现 execute 模式**：在 query 基础上添加写入
3. **最后添加优化**：在基本功能稳定后添加智能优化
