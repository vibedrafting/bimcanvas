# Design_Insights — 让 AI 胜任室内设计的有效经验

> **本文用途**：记录 BIMCanvas 在"把通用大模型调教成会做室内设计的设计师"过程中提炼的设计灵感。每则力求讲透三件事——**洞见（是什么）、为什么（从什么失败/观察来、背后的机制、为什么有效）、怎么落地（在 BIMCanvas 里靠什么代码/机制实现）**。
>
> **关于诚实**：每则的"怎么落地"都经代码核实并附线索；尚未实现、仅为设计构想的，明确标注"未落地"，不假装做了。已退役的旧接口名不写。判断现状以代码为准。
>
> **读者**：BIMCanvas 贡献者；以及任何想让 LLM 胜任某种专业判断的工程师——多数手段不限于室内设计。

---

## 1. AI 是"OBB 规划师"：决策与计算分离

> 让 AI 决策"放哪里"，让代码计算"精确几何"——这条边界决定了整个系统谁该干什么。

### 洞见

人和 AI 看的是同一个空间的两层。人看到的是"皮"，AI 应当只看"骨"：

| 维度 | 人类（皮 / SVG） | AI（骨 / OBB） |
|------|------------------|----------------|
| 视觉几何 | 看到家具的真实形状、材质、光影、墙体厚度 | 世界由有向包围盒（OBB）构成；无论家具是 L 形还是圆形，只操作其外接矩形 |
| 坐标直觉 | 屏幕坐标（原点左上，Y 向下） | CAD 坐标（原点左下，Y 向上，`above` = Y 更大） |
| 关注点 | 美感与体验、氛围 | 拓扑关系（在 Zone 内、不重叠）、数值约束（距离、尺寸）、语义方向（North/South） |
| 处理方式 | 直观感知 | 数据计算（多边形交集 / 包含判断） |

核心一句话：**AI 不计算几何，只决策位置。** 它的职责被限定为定向包围盒的规划——不需要理解复杂墙体构造或精细家具模型，只需知道"哪里是边界、哪里不能放、该靠哪面墙、朝哪个方向"。

### 为什么

早期让 AI 直接产出家具的精确多边形坐标，结果既慢又频繁出错——它在 thinking 里逐个顶点心算坐标、反复验算是否越界，既消耗大量思考预算，又因为概率性计算而不可靠。

根因是混淆了两类性质完全不同的工作：

- **决策**是语义判断（"床该靠最长的那面完整墙"），有多个合理解、依赖对空间和功能的理解——这是 LLM 擅长的。
- **计算**是确定性运算（四个角的精确坐标、两个多边形是否相交），有唯一正确答案、有成熟算法——这是代码擅长、LLM 不擅长的。

让 LLM 去做计算，等于用一个概率性工具去做一件确定性工具能做得又快又准的事。把这条线划清楚，AI 的注意力就能集中在它真正能创造价值的决策上。

### 怎么落地

- AI 的输出落盘为 `Module.bounds`（`Polygon2D`，矩形 4 顶点）+ `Module.facing`（值对象：`value` 单位向量是几何真理，`semantic` 是 AI 的临时输入槽）。数据模型**不存** center/size——它们只是转换前的中间态（`BIMCanvas.Core/Models/Layout/Module.cs`）。
- 语义意图 → 精确几何由 `GeometryNormalizer` 完成：`CreateRectangle(center, size, facing)` 先建朝北矩形 → 按 `facing` 算旋转角 → 绕中心旋转出 `Polygon2D`（`Core/Algorithms/Spatial/GeometryNormalizer.cs`）。AI 给方向意图，代码给精确几何。
- 校验器 `PlacementValidator` **只验证、不修正**：只收集 `Violation` 返回结果，没有任何写回 bounds 的副作用（`Core/Algorithms/Spatial/PlacementValidator.cs`，类注释明示"只验证，不修正"）。"床头靠墙"是 AI 的规划职责，不是 Core 的修正职责；要吸附功能，应单独做 SnapHelper，而不是让校验器偷偷改 AI 的决策。

**工程价值**：这条"决策 / 计算"分界线向上决定了整个系统的职责划分（Agent 不做几何、不持状态；Server / Core 做几何、做校验）。对任何"LLM + 精确计算"的系统都通用：识别出任务里的确定性部分，交给代码，别让 LLM 去做有确定性算法可替代的事。

## 2. 为 AI 而画的视图：把隐性约束变成显性视觉

> 给 AI 看的图要为它的逻辑服务，而非复用给人看的渲染图。

### 洞见

当引入视觉能力（多模态）做辅助验证或规划时，直觉做法是把渲染精美的效果图丢给 AI。这往往低效甚至误导。AI 需要的是一张**"语义增强的工程视图"**——专为它的判断逻辑而画，把人眼能脑补、AI 看不见的约束显性化，把对判断无用的视觉细节抽象掉。

### 为什么

精美渲染图对 AI 是双重的坏：

- **它充满噪音**：阴影、纹理、圆角、抱枕——这些对"是否碰撞""朝向哪里"的判断毫无意义，却占据 AI 的视觉注意力。
- **它缺失关键约束**：很多约束在人类视图里是隐形的——门扇开启扫过的那片区域、墙面完成面的厚度。人能凭常识脑补，AI 只看图就会把家具摆进门的开启范围。

所以正确的做法是反过来：**为 AI 重画一张图**，遵循三条原则——把隐形约束画出来、把无用细节抹掉、给每个对象一个可引用的身份。

### 怎么落地（严格区分已实现与构想，避免夸大）

| 手段 | 状态 | 落地 |
|------|------|------|
| **AI 视觉层（双 mesh）** | ✅ 已落地 | 每个构件成对生成"给人看的普通材质 mesh"+"给 AI 看的纯色无光照 mesh"（`MeshBasicMaterial`，高对比、平涂），后者归 `LAYER_AI_VISION` 层；截图工具 `canvas_vision` 走 Agent 预设启用该层（`BIMCanvas.Web/src/services/builders/SceneBuilder.ts`、`LayerManager.ts`）。**精确表述**：Agent 预设是 overlay 叠加（普通层仍在），不是纯净的高对比分割图。 |
| **约束层显性化** | ✅ 已落地 | 禁区半透明红（`ExclusionBuilder`）、可设计区淡绿背景（`ZoneBuilder`，"这是你的安全工作区"）、家具 OBB 描边 + 朝向箭头（`SceneBuilder` 的 `createModuleBoundsLine` / `createFacingArrow`）、构件 ID 标签（`LabelBuilder`，CSS2D；AI 报告"3 号挡住 5 号"时可精确定位）。 |
| **语义网格（A/B/C × 1/2/3 符号坐标）** | ✅ 已落地（路径有别） | `GridBuilder.buildSemanticLabels` 真生成 Excel 风格列行标签（列 A/B/C…做 26 进制进位 × 行 1/2/3）。但它是渲进截图的 DOM 标签，AI 经**截图视觉**读取这套符号——**没有**独立的符号坐标数据通道喂入。 |
| **设计场线** | ❌ **仅构想，未落地** | `LAYER_SEMANTIC` 层已定义但永远是空层——没有任何 builder 往里放对象。详见下方构想说明。 |

> **语义网格为什么有用**：把连续度量空间离散成符号空间，是对 AI 的降维打击。`C3` 是语义符号，AI 天然知道"A3 在 B3 左边""A1 到 C3 是对角线"——这种空间推理直接靠语义完成，不必做坐标减法；而 `x:1200,y:3400` 这样的数字，AI 要消耗算力去"算"位置关系。配合"由粗到精"（先在网格级粗规划"沙发放 C2–E2 区"，再在格内细调坐标），既快又降幻觉。

> **设计场线（构想，未实现）**：把设计师的隐性习惯画成 AI 能视觉遵循的显性约束——**对齐轴线**（解决"正对"：主家具中心吸附墙面中轴）、**锚点十字**（"居中"：对准重点墙面几何中心）、**动线通道带**（"挡路"：连接出入口的半透明带，"虚拟河流"，家具只能在岸边）、**视线锥**（"遮挡"：沙发到电视墙的扇形内禁高家具）、**对称参考线**（"平衡"：镜像位也放对应家具）。思路仍有价值，留待实现（对应当前空着的 `LAYER_SEMANTIC` 层）。

**工程价值**：多模态 LLM 的输入应按"它要判断什么"来构造，而非复用给人看的产物。把领域专家的隐性直觉显性化为视觉 / 符号约束，是让 LLM 应用专业判断的通用手段——但要诚实区分哪些真画了、哪些还只是想法。

## 3. 设计即熵减：把决策外化为可见文本

> 逼 AI 把每个决定写成可见、逐步精化的文本，而非闷在 thinking 里反复权衡。

### 洞见

一个空房间有无穷多种布置可能。设计的本质是**熵减**——每做一个决定，可能性空间就收窄一些，直到坍缩为唯一方案：

```
高熵（无穷可能）                                   低熵（唯一方案）
"空房间"  →  "床靠东墙"  →  "衣柜北墙"  →  "梳妆台延伸区"  →  精确坐标
              ↓ 可能性骤降    ↓ 进一步收窄    ↓ 接近确定         ↓ 完全确定
```

人类设计师的熵减是**快速、渐进、外化**的——扫视五秒说出"床放东墙"，这一句话当场消灭大量可能性；然后在这个约束下继续决策，每步立即外化（说出来、画下来），决策链清晰可见、不可逆转。**关键不在"想得对"，而在"把想的立即落到外部、形成锚点"。**

### 为什么

一次真实失败：为主卧布置家具，AI 耗时 27 分钟、其中八成在思考。结果完美（8 件家具、0 错误），但过程暴露三个结构性问题：同一空间从零分析了三遍；方案间反复横跳、没有"评估完成"的信号；所有推理塞进一次超长输出，超过上限被截断、全部丢失、重来。

它能力没问题——最终做对了。问题是它**用错误的方式在思考**：熵减发生在 thinking 块内部，不可见、不可恢复、不可锚定。AI 在脑中同时维护多种可能性、反复横向比较而不肯落子，直到 thinking 溢出。

解法是把熵减过程搬到可见文本里——决定一件、写一件，从粗到细逐步精化。它精确对应四类浪费：

| 问题 | 外化如何解决 | 为什么可靠 |
|------|-------------|-----------|
| 中间决策在 thinking 中，截断即丢失 | 写入可见输出 | 可见即存活，截断不影响已落盘的决策 |
| 反复重新分析相同信息 | 已写决策可直接引用 | 不必重推——引用的是结论，不是原材料 |
| 决策不承诺、反复 second-guessing | 写入即承诺 | 白纸黑字的决定形成锚点，不再摇摆 |
| 一次性巨大输出撑爆上限 | 每次只增量几行 | 物理上不可能触发上限 |

两条配套的领悟同样重要：

- **精度边界——规划期只做粗估**。规划全程只做空间预演级的粗估（"北墙 4070mm 放衣柜深 600、通道约 950，够用"），精确坐标推迟到落地阶段。WHY：粗估是空间预演的必要工具（"放得下吗？通道够吗？"），但精确坐标心算正是 thinking 膨胀的主因——把它推迟、配合确定性校验，既更快又更可靠。
- **方案即"设计图纸"，享有权威**。曾发生：AI 在规划阶段按用户参考图把床定在东墙，落地阶段却被一条"最长实墙放床"的设计偏好诱导改到西墙，背叛了用户意图。根因是它把"已定方案"和"通用偏好"当成平级信息。规矩由此而来：方案是设计图纸、其他规则是施工规范——规范决定"在这面墙上怎么放"，但不能改"放在哪面墙"；要改图纸须用户许可。这条权威性靠在多个阶段重复强化（LLM 注意力会衰减，重复出现的约束获得更高权重）。

### 怎么落地

- **逐段结构化外化**：workflow 五段流每段都让 agent 把产出写进设计区的 `DESIGN.md`（感知节 → 方案草稿 → 多方案战略概述 → 方案对比），由单写者 `design-scribe` 统一落盘（`workflows/interior-layout.workflow.js` + `agents/design-scribe.md`）。
- **schema 强制结构化**：每段有 JSON Schema 钉死必返字段（`PERCEPTION_SCHEMA` / `OVERVIEW_SCHEMA` / `PLACEMENT_SCHEMA` …），agent 产出首字符强制 markdown 标题——确保是"逐步精化的可见文本"而非 thinking 自由发挥。
- **精度边界**：规划阶段的 agent（感知 / 双思维）提示词只要求空间预演级判断，精确坐标计算在落地阶段（`placement-agent`）才进行。
- **图纸权威**：`placement-agent` 三级红线规定语义级改图不能静默执行、自主模式只能记 `[自动改图建议]` 上报；`BIMCANVAS.md` 失败处置红线规定"终选属于用户、绝不替用户翻 adopted 指针"。（旧的 semantic_plan JSON 合同已退役，意图统一收口到 DESIGN.md。）

**工程价值**：让 LLM 的中间状态可见且可锚定，是对抗"长链思考发散 / 上下文溢出"的结构性手段——不依赖模型"更自律"，而是改变它思考的物理形态。

## 4. 结构性解法优于文字规则

> 当某信息已在上下文中产生干扰，加一条"请忽略"无效；有效的解法是让它在关键时刻物理上不在场。

### 洞见

这是本文最具普适性的一条，也是反直觉的：**文字规则对抗不了上下文里已有信息的隐性引导。** 当你想让 AI 不受某段信息影响，加一句"请忽略它"几乎总是失败——因为模型读得到上下文里的一切，"请别理它"这句话本身反而再次强化了那段信息的存在。有效的解法永远是结构性的：让该消失的信息，在关键决策的那一刻，物理上不在上下文里。

### 为什么

两个同源的失败，揭示了同一条规律：

- **污染源一：设计偏好**。为防房间设计偏好污染对用户参考图的解读，先加文字规则"请忽略墙面偏好、以图为准"。无效——AI 仍被偏好悄悄带偏，把图片里明明在东墙的床"润色"成偏好推荐的西墙。
- **污染源二：示例过拟合**。提示词里放了个示例，空间参数恰好与测试房间相同，AI 直接抄了示例的结论（"床→西墙"），跳过独立推理——哪怕示例明明白白标注了"不提供可复用的结论"。

两个问题本质相同：信息一旦进入上下文，就会隐性引导判断，文字层面的"请别用它"无法对冲。当年的解法都是结构性的——**延迟加载**（解读参考图的全过程不加载偏好文件，让它物理上不在场）+ **示例去参数化**（示例改用与任何真实场景都不同的虚构参数，保留方法示范、消除结论照抄）。辅以一条：基准记录必须精确——若空间骨架用模糊描述（"居中偏南"而非"东墙"），后续一致性检查会失效，因为任何结论都能"一致"于模糊基准。

### 怎么落地（注意：载体已变）

上述两条具体做法属于已退役的"参考分析链路"，随该链路一起退役，当前不再适用。但**结构性隔离污染的思想仍在用，换了载体**——`perception-agent`（感知分身）的"地基防污染护栏"：提示词硬性规定它"永不读取参考图、参考分析或他人设计意图"、"墙面命名中性化、禁写房型专属功能命名、禁引用未加载的 references"（`agents/perception-agent.md`）。即在"感知"这道地基工序，用结构把会带偏判断的信息挡在上下文之外，而非靠文字叮嘱 AI"别被带偏"。

**工程价值**：控制 LLM 行为时，"移除 / 重构上下文"远比"增加约束文字"可靠。这条对任何需要精确控制 LLM 行为的系统都适用——遇到"AI 总是被某信息带偏"，第一反应不该是加一条禁止规则，而是问"能不能让这段信息在该决策时根本不进上下文"。

## 5. 分区是结论，而非前提

> 分区线从家具预布置与动线中浮现，不是先验地切割空间。

### 洞见

一个常见的思维陷阱，是把分区当成预处理步骤——"空间太复杂，先切小再处理"。这只是分区最浅的一层理解。真相是：**分区线是设计结论，不是设计前提。** 它从家具预布置与动线推演中"浮现"，而不是先画线、再往格子里填家具。

### 为什么

**先看分区是怎么真正做出来的。** 设计师脑中的过程不是"先画分区线、再规划过道、再放家具"三个顺序步骤，而是三件事同时发生、互相验证：

> "门在这边，窗在那边……床大概放那面墙……那从门到床要走这条线……衣柜靠这面墙的话，过道够不够……不够的话床往窗边挪一点……那这块区域自然就是更衣区了。"

| 面向 | 回答的问题 | 性质 |
|------|-----------|------|
| 家具预布置 | 这里需要多大空间？ | 空间需求 |
| 过道设计 | 人怎么在家具间移动？ | 空间连接 |
| 分区 | 前两者叠加后浮现的结构 | 空间组织 |

家具是岛屿，过道是河流，分区是看着岛屿和河流之后画出的地图——你不能先画地图再造岛屿。一条没有物理依据（没在脑中验证过"主要家具放得下、人走得通"）的分区线，只是一刀随意的几何切割，不是设计决策。

**再看分区为什么值得做——它有三层递进的价值：**

| 层 | 价值 | 说明 |
|----|------|------|
| 工程价值 | 约束解耦 | 一个 25㎡ 卧室要同时处理床朝向、衣柜墙面、书桌采光、各家具通道——高维耦合的优化问题。分区后每个子空间聚焦单一功能，约束大幅解耦。这是最浅、最易看见的一层。 |
| 质量价值 | 创造设计语言 | **分区赋予空间以意图**。当一块地方被定义为"更衣区"，你不必再用规则解释衣柜和梳妆台为何该靠近——"更衣区"三个字激活了关于这类空间的全部设计常识。分区越清晰，需要的显式规则越少。"有设计感"与"只是塞满了"的本质区别，就在空间有没有意图，而分区正是创造意图的容器。 |
| 过程价值 | 可交付的成果 | 在真实设计工作流中，分区图本身是一种交付物——设计师前期展示的不是家具布置图，而是分区图。客户几秒就能判断方向对错，调整分区的成本远小于推翻整套家具布置。分区是设计过程中最早的对齐点。 |

**最后是分区的"双向锁定"作用**：分区从预布置浮现，但一旦确立又反过来成为后续精确布置的约束框架——`预布置（发散探索）→ 浮现分区 → 分区锁定 → 收敛执行`。它是设计过程的锁定点：之前是开放的搜索空间（"床放这里行不行？那里呢？"），之后是有界的执行问题（"睡眠区已定，在这范围内把床放好"）。没有这个锁定点，设计就是无限发散的搜索。

### 怎么落地

- `zoning-design-agent` 整段落地此灵感：提示词明写"分区线不是凭空画的，从主要家具粗占位、通行路径和有意留白中浮现"；步骤为"主要家具粗占位 → 通道 / 留白识别 → 功能边界浮现"，且"不分区是合法结论"（`agents/zoning-design-agent.md`）。
- **家具先于分区**（单向约束）：明写"基于已确定的主要家具墙面结论，只验证能不能形成空间组织，不重新选择家具墙面"——约束方向是 物理空间 → 家具位置 → 过滤分区，单向无循环。
- **分区是一条推演轴、不是前置硬步骤**：workflow Step2 把 `zoning-design`（分区思维）与 `sequential-design`（顺序思维：从最重要家具按重要度依次锁墙）**并行**为两条多样性轴；分区结论的数据物化推迟到落地阶段（zoning agent 明确"不碰 zones.json"，避免把尚未验证的分区焊死成数据）。

**工程价值**：理顺约束方向——先确定受物理约束的部分，让高层结构从中浮现，而不是先定一个抽象结构再去填。这避免了在抽象层（"该怎么分区"）反复试探的发散，是"让结论浮现而非前置假设"的一般化。

## 6. 工程合规 ≠ 设计品质：评价维度即设计目标

> "不出错"和"做得好"是两件事；评价标准应前置为设计目标，而非事后检查清单。

### 洞见

`validate_layout` 通过只代表工程合规（没违反约束），不代表设计品质（这是个好设计）。更深一层：**评价维度本身就该是设计目标，且应前置到设计之初**——好的设计不是先随便做、再检查有没有碰巧做对，而是从第一笔就被目标牵引。

### 为什么

一次主卫，台盆和马桶放在了门偏向的一侧，进门要折返才能用。几何完全合法——不越界、不重叠、通道宽度 950mm ≥ 900mm 标准。审查没拦住。沿着"为什么"层层追问，挖到了系统性盲区：

1. **为什么 SubAgent 选错了墙？** 规则写的是"选距门中心较远的长墙"，结论其实指向正确的墙，但 AI 仍选错——因为规则只给了一个几何公式，没解释 WHY。AI 在执行公式，不是在追求目标；公式在复杂空间里变模糊时，它没有更高层的目标可以回退。
2. **为什么审查没发现？** 审查检查了三件事：validate 通过、通道达标、截图就位——全满足。审查没有能力发现"虽然能走过去，但走的路线不自然"。
3. **为什么审查体系发现不了？** 因为整个框架是**工程合规检查**（有没有违反约束），而不是**设计品质评估**（这个设计好不好）。这不是某条规则缺失，是评估维度的系统性缺失——我们定义了"什么不能做"，从没定义"什么是做得好"。

由此得到核心领悟：**好设计不是碰巧的。** 人类设计师画卫生间时，不会先随便选面墙放台盆、画完再检查动线自不自然——他拿起笔之前就想好了"门在这边，人进来往那边走，所以台盆在那边"。动线自然性不是事后检验项，是从第一笔就在引导他的设计目标。如果 AI 在策略阶段就声明了"进门直达台盆"这个目标，它选墙时会自然选对，根本不需要公式。

这导向从"规则驱动"到"目标驱动"的转变：规则告诉 AI 不要做什么（不挡门、不越界、不留死角，是护栏），目标告诉 AI 要追求什么（自然的动线、清晰的意图、连贯的叙事，是驱动力）。两者缺一不可，但目标是方向。

### 分层评价体系（递进、不可跳跃）

```
Layer 1  工程合规    "有没有错？"          以不出错为底线
Layer 2  设计品质    "好不好？"            以好设计为目标
Layer 3  设计倾向    "合不合业主喜好？"     （未来：偏好作 Layer 2 权重调节器）
Layer 4  经济指标    "花多少钱？"           （未来：成本 / 性价比）
```

每层是上一层的前提——有错的布局谈不上品质，品质差谈不上偏好。当前聚焦 L1 + L2。Layer 1 含三块：几何合法（不越界 / 穿墙 / 占柱 / 侵禁区 / 重合，由确定性校验自动查）、通行可达（主通道 ≥900mm、次通道 ≥600mm、全功能点可达无死端）、功能完整（zone 每个功能标签至少一个对应模块、必选家具不遗漏）。

### Layer 2 设计品质：当前是 6 维设计品质 + 4 项通用品质

每个维度既是审查标准、也是设计目标，每维都有正反例：

| 维度 | 核心问题 | 好 / 差 |
|------|---------|---------|
| 动线设计 | 从入口到功能点的路径是否直觉、无折返？ | 进门右转直达台盆 / 需绕门扇、洗手后折返才到马桶 |
| 空间意图 | 每个区域有明确存在理由吗？ | L 形延伸做化妆间、凹角做书桌 / 延伸区空置、<600mm 缝隙无用途 |
| 功能叙事 | 同区家具讲连贯故事吗？墙面主题统一吗？ | 一整面墙做衣柜、台盆+镜柜+毛巾架成洗漱区 / 衣柜-空隙-床头柜-书桌混杂一墙 |
| 空间节奏 | 入口到深处有意识递进吗？留白是选择还是遗漏？ | 私密度递进 台盆→马桶→淋浴 / 一进门正对家具、马桶紧贴门口 |
| 采光通风 | 窗户资源是否被合理利用？ | 高柜沿非窗墙、梳妆台靠窗 / 高衣柜正对窗使深处变暗 |
| 家具最优布局 | 家具尺度 / 组合是否最优？ | （第六维，与上五维并列检查） |

> 关键区分：动线设计 vs Layer 1 通行可达——后者问"能不能走到"（900mm 底线），前者问"走到的过程是否自然"。一条需折返的 900mm 通道，工程合规但动线不合格。
>
> "意图"不等于"填满"——空旷区域也可以有意图（"这是主通道的呼吸空间"是意图，"家具放不下所以空着"不是）。区别在于：有意图的空白从功能需求推导而来，无意图的空白是家具排列的副产品。

### 品质标准贯穿四阶段（同一套维度，不同角色）

- **理解阶段**——作为读空间的透镜：不只"这空间长什么样"，而是"它支撑什么动线？能讲什么功能叙事？光从哪来？"
- **策略阶段**——作为显式声明的设计目标：用品质语言表达意图，不是"台盆放东墙"（what），而是"进门右转直达台盆（动线目标）/ 东墙统一洗漱区（叙事目标）"（why）。这一步是关键——目标被显式声明后，后续每个执行决策都有了判据。
- **执行阶段**——作为每个决策的判据：选墙时想动线、分组时想叙事、留白时想节奏、靠窗时想采光。
- **审查阶段**——作为目标达成的验证：不再是"拿一份不知从哪来的清单挨个对照"，而是"检查策略阶段声明的目标是否实现"。审查有了锚点，因为标准就是自己设的目标。

### 怎么落地

- 维度定义在 `projectMount/references/design_evaluation.md`，开篇即声明"这些维度既是策略阶段的设计目标、也是审查阶段的验证标准"，每维提供双向 schema（声明用 / 审查用的视觉检查问法）。
- **声明端**：感知与双思维阶段加载 design_evaluation 作"空间阅读判据"，用品质语言显式声明目标。
- **验证端**：`placement-agent` 落地后做**识图自评**——按 design_evaluation 各维的"视觉检查"问法，结构化列 6 个设计品质小问 + 4 项通用品质小问，定点提问、禁大杂烩、禁引导性提问（`agents/placement-agent.md` Step F）；另有零领域 `verify-agent` 独立跑 validate 闸门。

**工程价值**：对任何"质量难以用约束穷举"的 LLM 任务都适用——与其堆砌"不许做什么"的检查清单，不如先定义"什么是做得好"的维度、让 AI 带着这些目标从一开始就被牵引，审查阶段只是验证目标达成。

## 7. 强外壳 + 弱内核：知识的双层切分

> 同一份领域知识，切成"机器校验的契约层"和"AI 理解的意图层"。

### 洞见

构建"AI 设计师"时面临一个核心矛盾：**Server 需要严谨性，AI 需要理解力。** Server / Web 不关心"私密性"或"对齐电视"，只关心"几何尺寸"和"是否重叠"以保证渲染合法；AI 则需要理解"为什么这张床放这里"（意图），而不只是坐标。把两者塞进同一种数据结构，要么把 Server 搞得没法校验，要么把 AI 框得不会思考。解法是混合架构：明确划分**契约层**与**意图层**。

### 为什么

两类消费者对同一份家具知识的需求是正交的：机器要的是**强结构、强校验、零模糊**（尺寸必须是数字、标签必须在枚举内，差一点就该被拦）；LLM 要的是**可理解的语义**（"靠墙放""避开门""与坐便器相邻"这类自然语言，比一堆几何参数更能激活它的设计常识）。强行统一只会两败俱伤。按消费者切层，两边都松快：Server 不必懂"对称"是什么意思也能校验几何；AI 不必懂几何算法也能表达"这两件该并排"。维护也变得可定位——AI 老把柜子拉太长，去修外壳的尺寸约束；AI 老把马桶摆路中间，去修内核的拓扑规则。

### 怎么落地

`projectMount/modules/module_library.json` 每条家具分两层：

- **契约层（强外壳）**：`tags`（对齐 ZoneTag 枚举）、`size`、资源路径。**确被机器消费**——`ModuleLibraryService` 读取下发，Web `ModuleCard.vue` 渲染 tag 标签与尺寸提示、支持按 tag 过滤选品。
- **意图层（弱内核）`agent_config`**：三支柱——`morphology` 形态学 + `topology_rules`（物体↔空间，如"靠墙""避让动线""深处角落"）+ `relation_rules`（物体↔物体，如"面向电视""与坐便器相邻""优先成对对称"）。Server 不解析这些自然语言，交 AI 理解。

**形态学**让家具声明自己的可变性，这让 AI 做的是"设计"（寻优）而非"摆图块"（已核实库中实际只有这三种策略）：

| 策略 | 含义 | 典型 |
|------|------|------|
| `fixed` | 刚体，尺寸不可变 | 成品床、马桶、成品柜 |
| `horizontal_fill` | 横向填满两墙之间（1D） | 定制衣柜、窗帘、一字淋浴屏 |
| `parametric` | 二维范围内自寻最佳长宽比（2D） | L 形沙发、转角淋浴房 |

> **一处诚实标注**：这套设计的意图之一是"用强类型 `limits` 物理拦截 AI 幻觉尺寸（如生成一个 5 米的马桶）"。但该拦截**当前未实现**——`limits` 只被解析成 UI 软提示文本，Server / Core 全链路没有 size-vs-limits 的硬校验挂点，`Module` 数据模型甚至不含 morphology 字段。这是个**已知缺口、设计构想**，不是已生效的防线。

**工程价值**：当一份数据同时服务"确定性系统"和"LLM"时，按消费者切层——强类型部分给机器、自然语言部分给 LLM。切分本身已落地且有效（解耦、可维护、表达力）；其中"用 limits 兜底拦幻觉"的鲁棒性是待补的下一步。

## 8. 提示词是激活，而非注入

> 提示词唤醒 AI 已有的知识，无法注入它没有的。它构建的是"认知环境"，不是"命令清单"。

### 洞见

提示词不是"命令"，而是**认知环境的构建**。它决定的不是"AI 做什么"，而是"AI 站在什么认知环境中做决策"。当你写"作为资深室内设计师"，AI 不是在"扮演"——它是在激活训练数据中与室内设计相关的知识区。提示词能唤醒 AI 已有的知识，无法注入它没有的（一个它从没见过的模式，再详细的规则也只能让它机械模仿）。

### 为什么 / 五个底层机制

| 机制 | 要点与推论 |
|------|-----------|
| **注意力零和** | 每个 token 都在竞争注意力，规则越多，模型定位并聚焦正确规则越难。推论：一条精准规则 > 十条模糊规则；加规则前问"去掉它，AI 会变差吗？不会就删"。 |
| **激活而非注入** | 提示词唤醒已有知识区，无法灌输没有的模式。"考虑 L 形转角方案"能激活相关设计模式；从未见过的模式则只能机械模仿。 |
| **WHY = 泛化** | "衣柜填满有效段"只能在完全匹配场景执行；"衣柜填满有效段，因为连续柜面更整洁、最大化收纳"——AI 得到一个推理框架，边界场景能从原理推导。没理由的规则只能机械执行，有理由的能灵活应用。 |
| **示例 = 锚定** | LLM 从示例提取模式比从文字解析规则更自然（transformer 的训练本身就是大规模模式提取）。十条文字描述输出格式，不如一个示例。推论：能用示例就用示例锚定基准，场景无法穷举时用 WHY 覆盖边界。 |
| **位置效应** | AI 对开头和结尾的关注高于中间（"lost in the middle"）。最关键的规则放头部或尾部，中间放说明性内容。 |

### 三层论 + 三级约束

提示词设计分三层：

- **第一层 信息架构**（决定 AI"怎么处理"信息）：结构化分层（角色目标 → 约束规范 → 具体指令，用标题和层级帮 AI 建索引）+ 保持信噪比（每条规则都问"去掉会变差吗"）。做对了不加分，做错了严重扣分。
- **第二层 认知校准**（决定 AI"以什么标准"工作）：示例锚定（一个示例校准的不止输出风格，还有推理深度、决策逻辑）+ 禁止项（"不要做什么"比"要做什么"更精准）+ WHY + 渐进信任（分阶段放权：执行 → 验证 → 扩展自主）。
- **第三层 留白**（决定 AI"在哪里发挥"判断）：好提示词不追求全覆盖。过度规则化让 AI 把注意力用于合规检查，而非思考怎么做好。

留白靠三级约束实现：

| 层级 | 性质 | AI 行为 | 语气 |
|------|------|---------|------|
| 硬约束 | 功能 / 安全 | 必须满足、无例外 | "必须" / "禁止" |
| 软指导 | 质量规范 | 默认遵守，说明理由后可偏离 | "应" / "建议" + WHY |
| 自由区域 | 风格 / 偏好 | AI 自主决策 | **有意识地不写规则** |

> 自由区域不是"还没来得及写规则的地方"，而是"经过深思熟虑后决定不写规则的地方"。没有校准的留白是失控，没有留白的校准是僵化。

常见反模式：规则叠加（修 A 加 X、X 致 B 又加 Y → 应找根因用一条精准规则）、职责越界（流程文件写领域标准 → 拆到知识库）、面面俱到（覆盖每种场景 → 给原理让 AI 推导）、留白恐惧（每个决策点都写规则 → 自由区有意识不写）、示例缺失（大量文字描述输出 → 1–2 个精选示例替代）。

### 怎么落地

这是方法论，落地在"提示词怎么写"，当前 agent 提示词里处处可见：
- **WHY 注脚**：如 `placement-agent` 北极星"你是载具、知识是能力——载具变了能力不应该变"。
- **示例锚定**：design_evaluation 每维 ✓/✗ 对照、multi-plan / placement 的 ❌反例 / ✅正确。
- **三级约束语气**：module_library 规则带 `【必须】/【建议】/【提示】`，agent 带 `【必须】/【禁止】/【边界】`。
- **约束力分级（留白）**：`placement-agent` 显式把 anchorSeed（硬约束）/ direction（方向参考，"不是合同条款，描述性语句不得当禁令"）/ avoidance（反模式）分级——不过度预设，留全局重判空间。
- 这套方法论也提炼进了插件 README 的"关键设计决策"（差异化在方向层、粗粒度 agent、硬约束越少越精准）。（注：`prompt-review` / `rule-review` 等审查 skill 属平台 / 工具层，不在本插件内。）

**工程价值**：提示词设计的本质是"构建认知环境"而非"下达命令"。信噪比、WHY、示例、留白、约束分级，是任何 LLM 系统提示词都通用的杠杆。

## 9. 两道独立防线：能解析 ≠ 能安全使用

> 面向"无容错能力的下游"，要有一道不依赖上游的独立闸门。

### 洞见

**"能反序列化"不等于"可以安全渲染 / 使用"。** 一份数据能被 JSON 解析，不代表它对下游是安全的。面向"无容错能力的下游"（渲染引擎、外部接口、跨进程边界），需要一道**完全不依赖上游是否尽责**的独立闸门。

### 为什么

一次事故：AI 写出一份字段格式错误的数据，缺了关键几何字段。JSON 反序列化**没有抛异常**——未知字段被忽略，缺失字段被静默赋为 null。Server 以"数据已加载"的状态把它推给前端，前端渲染时撞上 null、画布崩溃。

事后揭示两个结构性盲点：① "能反序列化"不等于"可以安全渲染"；② 崩溃发生在 AI 主动调用校验**之前**——渲染这条路径根本不经过校验工具（文件变更通知比 AI 的校验调用早了约 9 秒）。

这说明：只靠一道"AI 主动调用的校验"不够，因为它依赖 AI 真的去调、且渲染路径不经过它。必须有第二道、且两道职责不可互替。先把"坏数据"分层，才能讲清两道各管什么：

| 层级 | 定义 | 例子 |
|------|------|------|
| 数据损坏 | JSON 无法解析 / 转换器无法处理 | 语法错误、`bounds: "hello"` |
| 数据缺失 | JSON 合法但渲染 / 布置必需字段缺失或为 null | `bounds: null`、`facing: null` |
| 数据不正确 | 结构完整但语义 / 空间决策错 | 模块越界、零向量朝向、moduleId 不在库 |

### 两道防线（职责正交，代码无互调）

| | 第一道：validate_layout（语义 / 几何级） | 第二道：Load 质检闸门（结构级） |
|---|------------------------------------------|--------------------------------|
| 触发 | AI 主动调用 | 每次加载数据自动运行 |
| 服务对象 | AI（有推理能力） | 渲染引擎（无容错） |
| 目标 | 从源头预防坏数据 | 阻止坏数据到达下游 |
| 覆盖 | 全部三层 | 仅影响渲染安全的两层（损坏 + 渲染必需字段缺失） |
| 修正 | 自动修 + 诊断（混合） | 不修，只隔离并报告 |
| 独立性 | 依赖 AI 主动调 | **完全独立，不假设第一道已运行** |

**第一道的混合修正策略**，划分标准是"程序能否在不猜测 AI 意图的情况下确定正确结果"：意图明确的自动修（`semantic:"south"` → 转 `value:[0,-1]`；非单位向量 `[3,0]` → 归一化 `[1,0]`；semantic 与 value 冲突 → semantic 优先），意图不明的返回诊断让 AI 重做（`"NE"` 非标准词——缩写还是笔误？；`[0,0]` 零向量无方向；越界 / 重叠 / moduleId 不在库）。

### 怎么落地

- **第一道 · validate_layout**：canvas MCP 工具 → Server 薄壳端点 `POST /api/validation/layout` → `PluginValidatorOrchestrator`。C# 只编排（跑拓扑、注入 stdin、原子落盘），**实际校验与修正委派给插件的 Python validator 脚本**（`validators/{pluginId}.py`，仅 trusted + active 插件）。"自动修"（如 facing `semantic→value` 写回）在插件脚本里做——这正是架构红线"Server 不做领域逻辑"的体现：校验器即插件脚本（design-first）。Server 侧只保留与领域无关的 bounds 结构预检。（`BIMCanvas.Server/Services/PluginSecurity/PluginValidatorOrchestrator.cs`、`ValidationController.cs`）
- **第二道 · Load 质检闸门**：每次 `GET /api/project` 加载自动跑，读 modules 走 `ModulesReaderService`（严格只认 wrapper 格式 `{schemeMetadata, modules}`，裸数组直接拒绝）。两级隔离：L1 整 zone 反序列化失败 → 隔离（`ParseError`）；L2 单模块结构质检（bounds null / 顶点<3 / NaN / moduleId 缺失）→ 剔除（`StructureError`）。**源文件不改**，生成 `ZoneLoadError` 随响应返回前端提示。（`ProjectController.cs` 的 `LoadAllZoneModules`、`Dtos/ProjectData.cs`）

两道真独立：渲染路径（`LoadAllZoneModules`）不调 validate_layout，validate_layout 也不调加载质检，覆盖项互补（结构 vs 语义 / 几何）。第二道的全部意义，是即使第一道完全失守（压根没被调用）也守住底线——因为渲染不经过第一道。

**工程价值**：系统里凡"下游无容错能力"之处，都值得为其单设一道不依赖上游的闸门。别假设上游会尽责——尤其上游是 AI、且关键路径绕过了它主动调用的那道校验时。

## 贯穿性原则

上述灵感反复指向三条更底层的倾向，可作为设计 LLM 系统时的默认偏好：

1. **结构 > 文字**：用结构让 AI 自然走对（移除污染上下文、外化决策、按消费者切分知识、为 AI 单建视图、给下游加独立闸门），优先于用文字规则去命令它。模型读得到上下文里的一切，靠"请别这样"的文字几乎拦不住，改结构才拦得住。
2. **目标 > 规则**：让 AI 带着显式目标工作（评价维度即设计目标），优先于堆砌"不许做什么"。规则是护栏，目标是驱动力——护栏防止出界，但只有目标能指明方向。
3. **激活 > 注入**：唤醒模型已有的能力（提示词激活知识、分区激活意图、角色激活专业常识），优先于试图灌输它没有的。提示词构建的是认知环境，不是命令清单。

这些经验提炼自室内设计这一个领域，但"让通用大模型胜任某种专业判断"的工程问题多数可迁移。本文不求体系完整，按需增补——也包括把上面标注"未落地"的构想（设计场线、limits 物理拦截）补成现实。
