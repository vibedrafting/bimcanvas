# Design_Insights — 让 AI 胜任室内设计的有效经验

> **本文用途**：记录 BIMCanvas 在"把通用大模型调教成会做室内设计的设计师"过程中，提炼出的、对工程实践有效的设计灵感。每则给出三件事：**洞见（是什么）→ 背景（从什么失败/观察来）→ 怎么落地（在 BIMCanvas 里靠什么代码/机制实现）**。
>
> **关于"落地"的诚实**：每则的落地都经代码核实并附线索。承载灵感的具体机制一直在演进——已退役的旧接口名不写；**尚未实现、仅为设计构想的，明确标注"未落地"**，不假装做了。判断现状以代码为准。
>
> **读者**：BIMCanvas 贡献者；以及任何想让 LLM 胜任某种专业判断的工程师——多数手段不限于室内设计。

---

## 1. AI 是"OBB 规划师"：决策与计算分离

> **洞见**：让 AI 决策"放哪里"，让代码计算"精确几何"。

**背景**：早期让 AI 直接产出家具精确多边形坐标，既慢又频繁出错（thinking 中逐角心算、易越界）。

人看空间看的是"皮"（形状、材质、光影），AI 应只看"骨"——有向包围盒（OBB），只关心外接矩形落在哪、朝哪。由此划出系统的根本边界：**AI 决策**（靠哪面墙、朝向、与谁相邻，语义判断）/ **代码计算**（多边形、碰撞、坐标，确定性运算）。

**怎么落地**：
- AI 的输出落盘为 `Module.bounds`（`Polygon2D`，矩形 4 顶点）+ `Module.facing`（值对象：`value` 单位向量是真理、`semantic` 是 AI 临时输入槽）——数据模型**不存** center/size，它们只是转换前的中间态（`BIMCanvas.Core/Models/Layout/Module.cs`）。
- 语义意图 → 精确几何由 `GeometryNormalizer` 完成：`CreateRectangle(center,size,facing)` 建朝北矩形 → 按 `facing` 算角度 → 绕中心旋转出 `Polygon2D`（`Core/Algorithms/Spatial/GeometryNormalizer.cs`）。
- 校验器 `PlacementValidator` **只验证、不修正**：只收集 `Violation` 返回结果，无任何写回 bounds 的副作用（`Core/Algorithms/Spatial/PlacementValidator.cs`，类注释明示"只验证，不修正"）——"床头靠墙"是 AI 的规划职责，不是 Core 的修正职责。

**工程价值**：这条"决策 / 计算"分界线决定整个系统的职责划分（Agent 不做几何、Server 做几何）。对任何"LLM + 精确计算"系统通用：别让 LLM 做有确定性算法可替代的事。

## 2. 为 AI 而画的视图：把隐性约束变成显性视觉

> **洞见**：给 AI 看的图要为它的逻辑服务，而非复用给人看的渲染图。

**背景**：把渲染精美的效果图给 AI 做视觉判断反而帮倒忙——美图全是噪音（阴影、纹理、圆角），关键约束却隐形（门扇扫过区、完成面厚度），AI 会把家具摆进门的开启范围。解法是为 AI 单独渲一套语义增强视图。

**怎么落地**（区分已实现与构想，避免夸大）：

| 手段 | 状态 | 落地 |
|------|------|------|
| **AI 视觉层（双 mesh）** | ✅ 已落地 | 每个构件成对生成"给人看的普通材质"+"给 AI 看的纯色无光照 mesh"（`MeshBasicMaterial`），后者落 `LAYER_AI_VISION`；截图工具 `canvas_vision` 走 Agent 预设启用该层（`BIMCanvas.Web/src/services/builders/SceneBuilder.ts`、`LayerManager.ts`）。**注意**：Agent 预设是 overlay 叠加（普通层仍在），不是纯净的高对比分割图。 |
| **约束层显性化** | ✅ 已落地 | 禁区半透明红（`ExclusionBuilder`）、可设计区淡绿背景（`ZoneBuilder`）、家具 OBB 描边 + 朝向箭头（`SceneBuilder` 的 `createModuleBoundsLine`/`createFacingArrow`）、构件 ID 标签（`LabelBuilder`，CSS2D）。 |
| **语义网格（A/B/C×1/2/3 符号坐标）** | ✅ 已落地（路径有别） | `GridBuilder.buildSemanticLabels` 真生成 Excel 风格列行标签。但它是渲进截图的 DOM 标签，AI 经**截图视觉**读取这套符号，**没有**独立的符号坐标数据通道。 |
| **设计场线（见下）** | ❌ **仅设计构想，未落地** | `LAYER_SEMANTIC` 层已定义但永远是空层——没有任何 builder 往里放对象，五种场线代码中无生成逻辑。这是 2026-01 的 aspirational 构想，至今未实现。 |

> **设计场线（构想，未实现）**：把设计师的隐性习惯画成 AI 能视觉遵循的显性约束——对齐轴线（解决"正对"，主家具中心吸附墙面中轴）、锚点十字（"居中"，对准重点墙面几何中心）、动线通道带（"挡路"，连接出入口的半透明带，家具只能在岸边）、视线锥（"遮挡"，沙发到电视墙的扇形内禁高家具）、对称参考线（"平衡"，镜像位也放对应家具）。思路仍有价值，留待实现（对应空的 `LAYER_SEMANTIC` 层）。

**工程价值**：多模态 LLM 的输入应按"它要判断什么"来构造，而非复用给人看的产物。把约束显性化为视觉/符号，是让 LLM 应用专业判断的通用手段——**但要诚实区分哪些真画了、哪些还只是想法**。

## 3. 设计即熵减：把决策外化为可见文本

> **洞见**：逼 AI 把每个决定写成可见、逐步精化的文本，而非闷在 thinking 里反复权衡。

**背景**：一次布置任务 AI 耗时 27 分钟、八成在思考——同一空间分析三遍、方案间反复横跳、推理塞进单次超长输出被截断丢失。它能力没问题（结果正确），是思考方式错了。设计的本质是熵减（不断做决定、收窄可能性到唯一解）；人类设计师的熵减是**外化**的（说出"床放东墙"，可能性当场坍缩），AI 的熵减却闷在 thinking 块内——不可见、不可锚定、溢出即全失。

**怎么落地**：
- **逐段结构化外化**：workflow 五段流每段都让 agent 把产出写进设计区的 `DESIGN.md`（感知节 → 方案草稿 → 多方案战略概述 → 方案对比），由单写者 `design-scribe` 落盘（`workflows/interior-layout.workflow.js` + `agents/design-scribe.md`）。
- **schema 强制结构化**：每段有 JSON Schema 钉死必返字段（`PERCEPTION_SCHEMA`/`OVERVIEW_SCHEMA`/`PLACEMENT_SCHEMA`…），agent 产出首字符强制 markdown 标题——是"逐步精化的可见文本"而非 thinking 自由发挥。
- **精度边界**：规划期只做空间预演级粗估（"北墙 4070mm 放衣柜深 600，通道约 950，够用"），精确坐标推迟到落地阶段才算——把精确坐标心算（thinking 膨胀主因）挡在规划期外。
- **方案即"设计图纸"、改图需许可**：`placement-agent` 三级红线规定语义级改图不能静默执行、自主模式只能记 `[自动改图建议]` 上报；`BIMCANVAS.md` 失败处置红线"终选属于用户、绝不替用户翻 adopted 指针"。（旧的 semantic_plan JSON 合同已退役，统一收口到 DESIGN.md。）

**工程价值**：让 LLM 中间状态可见且可锚定，是对抗"长链思考发散 / 上下文溢出"的结构性手段——不依赖模型"更自律"。

## 4. 结构性解法优于文字规则

> **洞见**：当某信息已在上下文中产生干扰，加一条"请忽略"无效；有效的解法是让它在关键时刻物理上不在场。

**背景**：曾为防设计偏好污染对参考图的解读，加文字规则"请忽略偏好、以图为准"——无效，AI 仍被悄悄带偏。当年的解法是结构性的：解读参考图全程**不加载**偏好文件（延迟加载），示例改用**虚构参数**防结论照抄。

**怎么落地（注意：载体已变）**：上述两条具体做法属于已退役的"参考分析链路"，随该链路一起退役，当前不再适用。但**结构性隔离污染的思想仍在用**，换了载体——`perception-agent`（感知分身）的"地基防污染护栏"：提示词硬性规定它"永不读取参考图、参考分析或他人设计意图"、"墙面命名中性化、禁写房型专属功能命名、禁引用未加载的 references"（`agents/perception-agent.md`）。即在感知这道地基工序，用结构把会带偏判断的信息挡在上下文之外，而非靠文字叮嘱。

**工程价值**：本则最具普适性。**控制 LLM 行为时，"移除/重构上下文"远比"增加约束文字"可靠**——模型读得到上下文里的一切，"请别理它"反而强化它的存在。有效解法始终是：让该消失的信息在关键决策时刻真的不在场。

## 5. 分区是结论，而非前提

> **洞见**：分区线从家具预布置与动线中浮现，不是先验地切割空间。

**背景**：曾把"分区"当预处理步骤——先切块、再在块内摆家具。但真实设计师是反过来的："门在这边，床放那墙，从门到床走这条线，衣柜靠这面过道够不够……那这块自然就是更衣区了。"家具是岛屿、过道是河流、分区是看着岛屿河流后画出的地图——不能先画地图再造岛屿。

分区的三层价值（递进）：**工程**（约束解耦，把高维耦合拆成单功能子问题）→ **质量**（赋予空间以意图：命名"更衣区"即激活该类空间全部常识，无需逐条规则）→ **过程**（分区图是设计最早的对齐点，几秒就能判断方向对错）。

**怎么落地**：
- `zoning-design-agent` 整段落地此灵感："分区线不是凭空画的，从主要家具粗占位、通行路径和有意留白中浮现"；步骤为"主要家具粗占位 → 通道/留白识别 → 功能边界浮现"，且"不分区是合法结论"（`agents/zoning-design-agent.md`）。
- **家具先于分区**：明写"基于已确定的主要家具墙面结论，只验证能不能形成空间组织，不重新选择家具墙面"——约束方向单向（物理空间 → 家具位置 → 过滤分区）。
- **分区是一条推演轴、非前置硬步骤**：workflow Step2 把 `zoning-design`（分区思维）与 `sequential-design`（顺序思维：从最重要家具按重要度依次锁墙）**并行**为两条多样性轴；分区结论的数据物化推迟到落地阶段（zoning agent 明确"不碰 zones.json"）。

**工程价值**：理顺约束方向，先确定受物理约束的部分、让高层结构从中浮现，避免在抽象层反复试探。

## 6. 工程合规 ≠ 设计品质：评价维度即设计目标

> **洞见**："不出错"和"做得好"是两件事；评价标准应前置为设计目标，而非事后检查清单。

**背景**：一次卫生间布置几何完全合法（不越界、不重叠、通道达标），却很别扭——进门需折返才能用洁具。审查没拦住，因为整套审查只问"有没有违反约束"。系统性盲区：定义了"什么不能做"（工程约束），从没定义"什么是做得好"（设计品质）。

**分层评价**（递进、不可跳跃）：Layer 1 工程合规（有没有错）→ Layer 2 设计品质（好不好）→ Layer 3 设计倾向（合不合喜好，未来）→ Layer 4 经济（成本，未来）。当前聚焦 L1+L2。

**怎么落地**：评价维度定义在 `projectMount/references/design_evaluation.md`，**当前是 6 维设计品质 + 4 项通用品质**（不是纯五维）：

| 维度 | 核心问题 | 好 / 差 |
|------|---------|---------|
| 动线设计 | 路径是否直觉、无折返？ | 进门右转直达台盆 / 需绕门扇、洗手后折返才到马桶 |
| 空间意图 | 每区有明确存在理由？ | L 形延伸做化妆间 / 延伸区空置、<600mm 缝隙无用途 |
| 功能叙事 | 同区家具讲连贯故事？ | 一整面墙做衣柜 / 衣柜-空隙-床头柜-书桌混杂一墙 |
| 空间节奏 | 入口到深处有意识递进？ | 私密度递进 台盆→马桶→淋浴 / 马桶紧贴门口 |
| 采光通风 | 窗户资源合理利用？ | 高柜沿非窗墙、梳妆台靠窗 / 高衣柜正对窗使深处变暗 |
| 家具最优布局 | 家具尺度/组合是否最优 | （第六维，与上五维并列检查） |

- **评价维度即设计目标**：design_evaluation.md 开篇即声明"这些维度既是策略阶段的设计目标、也是审查阶段的验证标准"，每维提供双向 schema（声明用 / 审查用）。
- **声明端**：感知与双思维阶段加载 design_evaluation 作"空间阅读判据"，用品质语言显式声明目标（不是"台盆放东墙" what，而是"进门直达、东墙统一洗漱区" why）。
- **验证端**：`placement-agent` 落地后做**识图自评**——按 design_evaluation 各维的"视觉检查"问法，结构化列 6 个设计品质小问 + 4 项通用品质小问，定点提问、禁大杂烩、禁引导性提问（`agents/placement-agent.md` Step F）；另有零领域 `verify-agent` 独立跑 validate 闸门。

**工程价值**：从"规则驱动"转向"目标驱动"。规则是护栏（不要做什么），目标是驱动力（要追求什么）——对任何"质量难以用约束穷举"的 LLM 任务都适用。

## 7. 强外壳 + 弱内核：知识的双层切分

> **洞见**：同一份领域知识，切成"机器校验的契约层"和"AI 理解的意图层"。

**背景**：给 AI 喂家具知识时撞上矛盾——Server 要严谨（尺寸、碰撞），AI 要理解力（为什么这样放）。塞进同一结构，要么 Server 没法校验，要么 AI 被框得不会思考。

**怎么落地**：`projectMount/modules/module_library.json` 每条家具分两层——

- **契约层（强外壳）**：`tags`（对齐 ZoneTag 枚举）、`size`、资源路径。**确被机器消费**：`ModuleLibraryService` 读取下发，Web `ModuleCard.vue` 渲染 tag 标签与尺寸提示、支持按 tag 过滤。
- **意图层（弱内核）`agent_config`**：三支柱——`morphology` 形态学 + `topology_rules`（物体↔空间，如"靠墙""避让动线"）+ `relation_rules`（物体↔物体，如"面向电视""与坐便器相邻""优先成对对称"）。Server 不解析这些自然语言，交 AI 理解。

**形态学**让家具声明可变性（实际 3 种策略，已核实库中只有这三值）：

| 策略 | 含义 | 典型 |
|------|------|------|
| `fixed` | 刚体，尺寸不可变 | 成品床、马桶 |
| `horizontal_fill` | 横向填满两墙之间 | 定制衣柜、窗帘、一字淋浴屏 |
| `parametric` | 二维范围内自寻最佳长宽比 | L 形沙发、转角淋浴房 |

**一处诚实标注**："强类型 `limits` 物理拦截幻觉尺寸（如 5 米的马桶）"是这套设计的**意图，但当前未实现**——`limits` 只被解析成 UI 软提示文本，Server/Core 全链路没有 size-vs-limits 的硬校验挂点（`Module` 数据模型甚至不含 morphology 字段）。这是个**已知缺口、设计构想**，不是已生效的防线。

**工程价值**：当一份数据同时服务"确定性系统"和"LLM"时，按消费者切层——强类型部分给机器、自然语言部分给 LLM。切分本身已落地且有效；其中"用 limits 兜底拦幻觉"是待补的下一步。

## 8. 提示词是激活，而非注入

> **洞见**：提示词唤醒 AI 已有的知识，无法注入它没有的。它构建的是"认知环境"，不是"命令清单"。

**背景**：写"作为资深室内设计师"，AI 不是在演，是在激活训练数据中相关的知识区。能唤醒已有的，无法注入没有的（没见过的模式，再详细的规则也只能机械模仿）。

**五个底层机制**：

| 机制 | 要点 |
|------|------|
| 注意力零和 | 规则越多每条权重越低；一条精准规则 > 十条模糊规则 |
| 激活而非注入 | 唤醒已有知识区，无法灌输没有的模式 |
| WHY = 泛化 | 附理由的规则给出推理框架，边界场景能从原理推导 |
| 示例 = 锚定 | LLM 从示例提取模式比解析文字更自然；示例锚基准、WHY 覆边界 |
| 位置效应 | 头尾关注度高于中间，关键规则放头/尾 |

配套"三层论"（信息架构 → 认知校准 → 留白）与"三级约束"（硬约束"必须/禁止" / 软指导"应/建议"+WHY / 自由区域"有意识地不写规则"）。

**怎么落地**：这是方法论，落地在"提示词怎么写"。当前 agent 提示词里处处可见：
- **WHY 注脚**：如 `placement-agent` 北极星"你是载具、知识是能力——载具变了能力不应该变"。
- **示例锚定**：design_evaluation 每维 ✓/✗ 对照、multi-plan/placement 的 ❌反例/✅正确。
- **三级约束语气**：module_library 规则带 `【必须】/【建议】/【提示】`，agent 带 `【必须】/【禁止】/【边界】`。
- **约束力分级（留白）**：`placement-agent` 显式把 anchorSeed（硬约束）/ direction（方向参考，"不是合同条款，描述性语句不得当禁令"）/ avoidance（反模式）分级——不过度预设、留全局重判空间。
- 这套方法论也提炼进了插件 README 的"关键设计决策"（差异化在方向层、粗粒度 agent、硬约束越少越精准）。（注：`prompt-review` / `rule-review` 等审查 skill 属平台/工具层，不在本插件内。）

**工程价值**：提示词设计的本质是"构建认知环境"而非"下达命令"。信噪比、WHY、示例、留白、约束分级，是任何 LLM 系统提示词都通用的杠杆。

## 9. 两道独立防线：能解析 ≠ 能安全使用

> **洞见**：面向"无容错能力的下游"，要有一道不依赖上游的独立闸门。

**背景**：一次 AI 写出字段格式错误、缺关键几何字段的数据，JSON 解析未报错（未知字段被忽略、缺失字段静默填空），系统以为就绪、推给前端，渲染撞上空值崩溃。且崩溃发生在 AI 主动校验**之前**——渲染路径根本不经过校验工具。结论：**"能反序列化"不等于"可以安全使用"**，需两道职责不可互替的防线。

**怎么落地**（两道，代码无互调）：

- **第一道 · validate_layout（语义/几何级，自动修 + 诊断）**：canvas MCP 工具 → Server 薄壳端点 `POST /api/validation/layout` → `PluginValidatorOrchestrator`：C# 只编排（跑拓扑、注入 stdin、原子落盘），**实际校验与修正委派给插件的 Python validator 脚本**（`validators/{pluginId}.py`，仅 trusted+active 插件）。"自动修"（如 facing `semantic→value` 写回）在插件脚本里做——这正是架构红线"Server 不做领域逻辑"的体现：校验器即插件脚本（design-first）。Server 侧只保留与领域无关的 bounds 结构预检。（`BIMCanvas.Server/Services/PluginSecurity/PluginValidatorOrchestrator.cs`、`ValidationController.cs`）
- **第二道 · Load 质检闸门（结构级，隔离不修）**：每次 `GET /api/project` 加载数据自动跑，读 modules 走 `ModulesReaderService`（严格只认 wrapper 格式）。两级隔离：L1 整 zone 反序列化失败 → 隔离（`ParseError`）；L2 单模块结构质检（bounds null / 顶点<3 / NaN / moduleId 缺失）→ 剔除（`StructureError`）。**源文件不改**，生成 `ZoneLoadError` 随响应返回前端提示（`ProjectController.cs` 的 `LoadAllZoneModules`、`Dtos/ProjectData.cs`）。

两道真独立：渲染路径（`LoadAllZoneModules`）不调 validate_layout，validate_layout 也不调加载质检，覆盖项互补（结构 vs 语义/几何）。第二道的全部意义是即使第一道完全失守（压根没被调用）也守住底线——因为渲染不经过第一道。

**工程价值**：系统里凡"下游无容错能力"之处（渲染、外部接口、跨进程边界），都值得为其单设一道不依赖上游的闸门。

## 贯穿性原则

上述灵感反复指向三条更底层的倾向，可作为设计 LLM 系统时的默认偏好：

1. **结构 > 文字**：用结构让 AI 自然走对（移除污染上下文、外化决策、按消费者切分知识、为 AI 单建视图），优先于用文字规则去命令它。
2. **目标 > 规则**：让 AI 带着显式目标工作（评价维度即设计目标），优先于堆砌"不许做什么"。规则是护栏，目标是驱动力。
3. **激活 > 注入**：唤醒模型已有的能力（提示词激活知识、分区激活意图、角色激活专业常识），优先于试图灌输它没有的。

这些经验提炼自室内设计这一个领域，但"让通用大模型胜任某种专业判断"的工程问题多数可迁移。本文不求体系完整，按需增补——也包括把上面标注"未落地"的构想（设计场线、limits 物理拦截）补成现实。
