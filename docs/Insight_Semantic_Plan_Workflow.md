# 语义方案驱动的渐进式布置工作流

> 本文档记录 generate-workflow 的重设计思路。核心命题：如何让 AI 既有人类设计师的快速决策能力，又保持精确执行的工程质量。

---

## 一、从一次失败说起

一次"为主卧布置家具"的测试中，Agent 花了 27 分钟才完成首次写入，其中 81% 的时间在思考。最终结果质量完美（8 件家具，0 错误，全部设计目标达成），但过程暴露了三个结构性问题：

1. **重复分析**：同一个空间被从零分析了 3 次（理解阶段 1 次，加载分区 Skill 后重做 1 次，会话重启后再做 1 次）
2. **决策不收敛**：分区评估在三个方案之间反复摇摆，没有明确的"评估完成"信号
3. **输出块溢出**：策略阶段的全部推理（床头墙选择 + 衣柜评估 + L 形分析 + 梳妆台扫描 + 决策收敛 + 策略声明）塞在一次输出中，超过 32K token 上限后被截断，全部丢失

根因不是 Agent 能力不足——它最终做出了正确决策。问题在于**工作流让 Agent 用错误的方式使用正确的知识**：bedroom.md 的优先级规则表本身就是高效的决策工具，但工作流引导 Agent 把它当作穷举评估的清单，而不是快速匹配的经验模式。

---

## 二、从熵减理解布置设计

一个空房间有无穷多种布置可能。设计过程的本质是**熵减**——每做一个决定，设计的可能性空间就缩小一些，直到收敛为唯一确定的方案。

```
高熵（无穷可能）                                    低熵（唯一方案）
"空房间"        →  "床靠西墙"   →  "衣柜北墙"  →  "梳妆台延伸区"  →  精确坐标
                    ↓ 可能性骤降     ↓ 进一步收窄     ↓ 接近确定          ↓ 完全确定
```

人类设计师的熵减是**快速、渐进、外化**的——扫视 5 秒后说出"床放西墙"，这一句话就消灭了大量可能性。然后在这个约束下继续决策，每步都立即外化（说出来、画下来），决策链条清晰可见。

当前 Agent 的问题：熵减发生在 thinking block 内部——不可见、不可恢复、不可锚定。Agent 在脑中同时维护多种可能性，反复横向比较而不收敛，直到 thinking block 溢出。

**新工作流的核心策略**：用一个叫"语义方案"的可见文本来承载熵减过程。每做一个决定就写入语义方案，决策可见即不可逆转（除非物理约束不允许）。语义方案从粗到细演进，其演进过程本身就是方案的熵减。

## 三、语义方案：设计过程的外化

### 什么是语义方案

语义方案是一段**持续演进的文本**，用自然语言描述当前的布局决策状态。它不是精确的坐标数据（那是 modules.json 的职责），而是家具与墙面的语义映射——"床在西墙"、"衣柜沿北墙线性排列"。

它存在于 Agent 的对话输出中（不是单独的文件），随工作流推进而更新。每个阶段在前一版本基础上增量更新，不重写。

### 为什么它能解决问题

| 当前工作流的问题 | 语义方案如何解决 |
|----------------|----------------|
| 中间决策在 thinking 中，截断即丢失 | 决策写入对话输出，可见即存活 |
| Agent 反复重新分析相同信息 | 已写入的决策可直接引用，不需重新推导 |
| 决策不承诺，反复 second-guessing | 写入即承诺——白纸黑字的决策不再摇摆 |
| 策略声明是一次性巨大输出 | 语义方案渐进构建，每次更新仅几行 |

### 演进规则

```
v0.1  空间骨架     动线方向 + 纵深层次 + 采光轴 + 初步设计意图
v0.2  主体框架     分区结论 + 主要家具墙面归属 + 设计目标
v0.3  完整方案     可选家具 + 设计目标细化 + 全部确认
```

确定性标记：
- `✓` 已确认——不再变动
- `~` 暂定——后续可能因联动调整
- `→ 待用户确认` 战略选择，需要 AskUserQuestion

## 四、五阶段工作流

### 总览

```
1.感知 → 2.规划(2.1→2.2→2.3) → 3.尝试↔修改 → 4.优化 → 5.汇报
 加载      语义方案 v0.1→v0.3     坐标+验证       设计品质      交付
 上下文    熵减：粗→细            Layer 1 闭环     Layer 2 改善
```

与当前 6 阶段工作流的映射：

| 当前 | 新设计 | 核心变化 |
|------|--------|---------|
| Perceive | 1. 感知 | 基本一致 |
| Understand | 2.1 基础规划 | 产出语义方案 v0.1（替代纯空间画像） |
| Understand + Zoning | 2.2 分区设计 | 家具位置→过滤分区方案（顺序反转） |
| Strategy | 2.3 丰富细节 | 可选家具纳入语义方案 v0.3 |
| Execute + Review(L1) | 3. 尝试↔修改 | 执行和 Layer 1 验证合并为闭环 |
| Review(L2) | 4. 优化 | 从被动检查变为主动改善 |
| Report | 5. 汇报 | 基本一致 |

### 1. 感知

**目标**：建立上下文——把 Agent 需要的所有信息加载到对话中。

**操作**：
1. 截图（聚焦目标分区）
2. 并行读取：design_principles.md + module_library.json + zones.json + exclusions.json + design_evaluation.md
3. 调用 `get_zone_boundaries` 获取墙面语义
4. 读取房间策略文件（bedroom.md / bathroom.md / livingroom.md）

**关键数据源选择**：`get_zone_boundaries` 返回的**预处理墙面数据**是后续所有阶段的主要空间数据来源，而非 zones.json 中的 rawBoundary 原始坐标。

```
rawBoundary（原始坐标）：
  [[14100, 5750], [11200, 5750], [9100, 5750], ...]
  → Agent 必须手动追踪顶点、推导墙面、计算长度
  → 每次引用都可能重新走一遍推导过程

get_zone_boundaries（预处理结论）：
  北墙 | 总长 5000mm | 实墙 4250mm
    wall 4070mm ... + door(d_3) 750mm ... + wall 180mm ...
  → 墙面已命名、已分类、已测量
  → 直接用"北墙门右段 4070mm"引用，无需重新推导
```

这是一个**结构性防重分析**措施：当数据本身已经是结论形态时，Agent 在物理上无法"重新分析"——因为它引用的不是原材料，而是成品。后续的语义方案、分区评估、家具决策全部基于 `get_zone_boundaries` 的墙面语义来描述空间，不回溯到原始坐标点。

> 当前工作流中，房间策略文件在 Understand 阶段才加载。新设计提前到感知阶段，确保 Stage 2 的规划从一开始就有完整的决策依据。

---

### 2. 规划

**目标**：通过三个递进的子阶段，将语义方案从"空间骨架"演进到"完整方案"。

**精度边界**：规划阶段全程只做**空间预演级别的粗估**——"这面墙 4070mm，放 600mm 深衣柜，通道约 950mm，够用"。不计算精确的 bounds 坐标点。精确坐标只在 Stage 3 写入 modules.json 时才产生。

| 规划阶段允许 | 规划阶段不允许 |
|------------|-------------|
| "北墙 4070mm 放衣柜，深 600mm，通道约 950mm" | 计算 bounds 四角坐标 |
| "西墙放床+两柜约 2700mm，剩余 2150mm" | 逐件家具确定精确 X/Y 坐标 |
| "延伸区 1700×1550，扣除衣柜后约 950mm 可用" | 验证家具边界是否在 innerBoundary 内 |

WHY：粗估是空间预演的必要工具（"放得下吗？通道够吗？"），但精确坐标计算是 thinking block 膨胀的主要原因之一——日志中 Agent 在策略阶段花了 5 分钟在 thinking 中逐件验算坐标。将精确计算推迟到 Stage 3，配合 validate_layout 的自动检查，既更快又更可靠。

#### 2.1 基础规划 → 语义方案 v0.1

以 design_evaluation.md 的品质维度为指引，完成空间的初步阅读：

- **动线方向**：人从入口进来自然往哪走？
- **纵深层次**：哪里是前场（过渡），哪里是深处（私密）？
- **采光轴**：窗户在哪，光怎么进来？
- **初步设计意图**：这个空间应该有怎样的体验序列？

产出语义方案 v0.1——只有空间骨架，不涉及任何家具决策。

#### 2.2 分区设计 → 语义方案 v0.2

必须加载 generate-zoning Skill（分区是空间功能定义的必经流程，即使结论是"不分割"）。

但执行顺序与当前工作流不同——**先家具，再分区**：

**Step 1：确定主要家具的最优位置**

在不考虑分区的前提下，用房间策略的优先级规则确定主要家具应该在哪面墙。

为什么可以先于分区决定？因为家具位置由**物理约束**（墙面长度、门位置、窗位置）决定，这些约束来自空间本身，不来自概念上的分区划分。无论怎么分区，西墙还是最长的实墙，北墙右段还是最长的非窗非门段——物理事实不因概念组织而改变。

**Step 2：用家具位置过滤分区方案**

确定了主要家具需要哪些墙面资源后，反过来检查哪些分区方案与这些需求兼容：

- 分区切割打断了家具需要的连续墙面？→ 该分区方案被淘汰
- 分区后家具仍能正常布置？→ 该方案可行，保留

这是**单向约束**：物理空间 → 家具最优位置 → 过滤分区方案。不存在循环依赖。

**Step 3：确定分区结论 + 功能定义**

- 如果多个可行方案对用户日常体验有质的差异 → 战略选择 → AskUserQuestion
- 确定分区（或"不分割"）后，进行功能定义
- 更新语义方案为 v0.2：加入分区结论 + 主要家具决策 + 设计目标

#### 2.3 丰富细节 → 语义方案 v0.3

将主要家具之外的家具纳入语义方案：

- 可选家具（梳妆台、展示柜等）：扫描候选墙段，标注位置
- 附属家具（窗帘、床头柜等）：跟随锚点家具
- 判断是否存在战略选择（可选家具位置影响日常体验）→ AskUserQuestion

更新语义方案为 v0.3。此时所有家具的墙面归属均已确定，设计目标完整。

**关于"位置暂定"**：v0.2 中主要家具标记为 `~`（暂定），因为可选家具的加入可能发现更优的全局布局——例如缩短衣柜为梳妆台腾出组合位置。v0.3 完成后，所有位置升级为 `✓`（确认）。

### 3. 尝试 ↔ 修改

**目标**：将语义方案转化为精确坐标，写入 modules.json，通过 Layer 1 工程合规验证。

**核心姿态：允许试错**

像人类设计师一样工作——先放下去看效果，出错了调整就好。validate_layout 是安全网，它比心算更快、更准。不需要在脑中完成所有验证后才敢动手。

"一次完美"的心理预期是 thinking block 膨胀的隐性推手：Agent 试图在写入前预演所有可能的冲突，导致坐标验算在 thinking 中无限展开。正确的姿态是**快速迭代**——写入 → 验证 → 发现问题 → 针对性修正 → 再验证。每轮迭代成本很低（一次 Write + 一次 validate_layout），远低于在 thinking 中预防所有问题的成本。

**操作**：
1. 根据语义方案 v0.3 + module_library 的 agent_config，计算每件家具的精确坐标
2. Write modules.json
3. 调用 validate_layout → 通过则进入 Stage 4
4. 失败 → 修正（平移 → 旋转 → 缩小 → 替换 → 移除）→ 重新 Write + validate
5. 最多 2 轮修正

**手动检查的有限清单**：Agent 在写入前只需检查以下 validate_layout 无法检测的语义问题，不做其他预验证：

| 检查项 | WHY validate_layout 检测不到 |
|--------|---------------------------|
| 门开启方向与家具是否冲突 | validate_layout 检查门扇禁区重叠，但不理解"门能不能顺畅打开" |
| 通行间隙 vs 使用间隙的类型区分 | validate_layout 不区分"人要从这里走过"和"人在这里伸手操作" |
| 前瞻协调：主家具是否阻断可选家具的策略位置 | 这是语义层面的设计意图，不是几何计算 |

**其余全部交给 validate_layout**：越界(E001)、墙体重叠(E002)、柱子重叠(E003)、禁区重叠(E004)、模块间重叠(E005)。

---

### 4. 优化

**目标**：以 design_evaluation.md 的五个品质维度为标准，结合截图的多模态理解，寻找可改善之处。

**与当前 Layer 2 审查的区别**：当前工作流把 Layer 2 当作"检查是否达标"——一种被动验证。新设计把它变为"主动寻找优化机会"——一种设计改善。

**操作**：
1. 截图审查布局效果
2. 逐项检查 design_evaluation 的 5 个维度，对比策略阶段声明的设计目标
3. 识别改善机会（动线挤压、功能区断裂、采光遮挡等）
4. 每个维度最多一次调整尝试
5. 调整后重新 validate_layout 确认工程合规

**典型优化场景**：
> 梳妆台布置在床尾对面墙的远离窗户端，导致从卧室门到窗户的主动线在中间被挤压。将梳妆台移到靠窗端后，挤压只发生在动线末端，影响大幅降低。

这类优化不是"错误修正"——原布局完全合规。它是"从合格到优秀"的品质提升。

---

### 5. 汇报

仅在 Stage 3 合规 + Stage 4 优化完成后汇报。

内容：空间画像摘要 + 策略要点 + 家具清单 + 品质评估（Layer 1 合规 + Layer 2 设计目标达成）+ 决策痕迹。

### 示例 2：窄长卫生间

**空间**：矩形 1540×2540mm，南墙入口(d_2)偏东，北墙高窗。

#### v0.1

```
## 语义方案 · 公卫 rz_2 · v0.1

空间：矩形 1540×2540，短边 ≤ 1800mm（窄长型）
动线：南墙门 d_2（偏东）→ 北向
```

#### v0.2（卫生间是模板匹配型空间，分区 + 家具一步到位）

```

（空间/动线/纵深/采光：同 v0.1）

分区：不分割（矩形 + 单功能）

  门在南墙偏东 → 入门开阔侧在西 → 洁具沿西墙

  · 洗手 → 如厕 → 淋浴由浅入深 (空间节奏)
```

> 卫生间的 v0.2 已接近完整方案——卫生间是"模板匹配型"空间，决策空间小，不需要 v0.3 的丰富细节阶段（或 v0.3 仅补充花洒、毛巾架等配件）。

## 六、关键设计决策及其理由

### 决策 1：家具先于分区

**选择**：Stage 2.2 先确定主要家具位置，再用这些位置过滤分区方案。
**否决**：先评估分区方案，再在分区内布置家具（当前做法）。

**理由**：家具位置由物理约束（墙面长度、门窗位置）决定，这些约束来自空间本身，不受概念分区影响。实测中，L 形主卧的床→西墙、衣柜→北墙在所有分区方案下都是相同答案。反过来，家具的墙面需求能主动淘汰不兼容的分区（衣柜需要北墙 4070mm 连续 → 竖切打断此段 → 竖切被淘汰）。

**约束方向**：`物理空间 → 家具位置 → 过滤分区`（单向，无循环）。

### 决策 2：Layer 1 和 Layer 2 分属不同阶段

**选择**：Stage 3 只管工程合规（能用吗？），Stage 4 管设计品质（好用吗？）。
**否决**：在同一个 Review 阶段同时检查 Layer 1 和 Layer 2（当前做法）。

**理由**：Layer 1 是二元判断（合规/不合规），Layer 2 是连续光谱（合格→优秀）。混在一起时，Agent 倾向于在"还没放好"的状态下就开始优化品质，造成认知负担叠加。分开后，Stage 3 可以专注于"先让它能用"——快速修正几何冲突；Stage 4 在确认合规的基础上从容思考"怎么更好"。

### 决策 3："写入→验证→修正" 优于 "心算→写入"

**选择**：Agent 在执行阶段直接计算坐标并写入，用 validate_layout 捕获错误，然后修正。
**否决**：Agent 在策略阶段或写入前在 thinking 中逐一验算坐标、间距、重叠。

**理由**：日志中 Agent 花了 5 分钟在 thinking 中做坐标心算——其中大部分是 validate_layout 能自动检查的内容（越界、重叠、禁区）。validate_layout 是确定性计算，比概率性的 LLM 心算更可靠、更快速。Agent 放置前只需关注 validate_layout 检测不到的语义问题（门开启方向、通道 vs 使用间隙的类型区分、前瞻协调）。

### 决策 4：语义方案替代策略声明

**选择**：用渐进演进的语义方案（v0.1 → v0.3）替代一次性的策略声明。
**否决**：在策略阶段末尾输出单一完整的策略声明（当前做法）。

**理由**：策略声明试图在一次输出中包含所有决策及其推理，这直接导致了 32K 截断。语义方案将同样的信息分散到多次输出中——每次更新仅 5-10 行增量，总量相同但每次输出体量极小。更重要的是，v0.1 的输出锚定了 v0.2 的思考方向，v0.2 锚定了 v0.3——渐进外化自然防止思考漩涡。

### 决策 5：分区 Skill 必须执行，但复用已有分析

**选择**：始终加载 generate-zoning Skill 完成空间功能定义。但 Skill 基于已输出的空间画像做判断，不重新推导空间信息。
**否决**：跳过分区（即使是小面积延伸区也需要经过功能审视）。
**否决**：完整重新分析（Skill 加载触发的"上下文切换"导致重复分析）。

**理由**："不分割"是分区 Skill 的合法结论，不是跳过分区的理由。功能定义是布置的前提——"这里是更衣区、那里是睡眠区"需要经过显式审视才能确立。但审视应基于 Stage 2.1 已经产出的空间骨架，不需要重新推导空间的形状、尺寸和墙面信息。

## 七、提速机制分析

新工作流的提速不靠"告诉 Agent 快一点"——而是通过结构性改变，让慢的路径在物理上不可达。

### 结构性保证（不依赖 Agent 是否"听话"）

| 机制 | 消除的浪费 | 为什么可靠 |
|------|-----------|-----------|
| 语义方案 v0.1→v0.3 拆分输出 | 32K 截断 → 丢失 → 重来（~5 min） | 每次输出 5-15 行，物理上不可能触发上限 |
| 家具→分区顺序反转 | 在 3 个抽象分区方案间循环（~5 min） | 搜索空间从"评估所有分区"降为"过滤不兼容的分区" |
| get_zone_boundaries 替代 rawBoundary | 重复空间分析（3 次 → 1 次）（~8 min） | 数据本身是结论形态，没有可"重新分析"的原材料 |
| Layer 1 / Layer 2 分属不同阶段 | 执行+审查认知负担叠加 | 每阶段只关注一件事 |

### 行为引导（靠指令+示例影响 Agent 行为）

| 机制 | 目标效果 | 强化手段 |
|------|---------|---------|
| "允许先试后改" | 减少 thinking 中的坐标预验证 | 在 SKILL.md 中表达为设计哲学，配合有限检查清单 |
| 正确节奏示例 | Agent 输出简短决策而非长篇分析 | 示例锚定（机制 4）+ 反例对比 |
| 决策承诺 | 防止 second-guessing 循环 | 语义方案的可见文字作为锚点 |
| 粗估边界 | 阻止策略阶段的精确坐标计算 | 明确的"允许/不允许"表格 |

### 预期效果

```
原始：27 min（首次写入在第 25 分钟）
目标：10-14 min（首次写入在第 7-9 分钟）

结构性保证节省：~13 min（截断重来 + 搜索空间 + 重复分析）
行为引导预期节省：~3-5 min（坐标心算 + 决策循环残余）
不可压缩下限：~8 min（LLM 推理 + 工具调用 + 用户交互）
```

## 八、与 design_evaluation.md 的关系

design_evaluation.md 定义的五个品质维度（动线设计、空间意图、功能叙事、空间节奏、采光通风）在新工作流中承担双重角色：

**Stage 2（规划）→ 设计目标**：品质维度引导语义方案中设计目标的产生。Agent 看到"入口在北、衣柜在北、床在南"时，直接写出"入口→更衣→睡眠的隐私递进(空间节奏)"——设计目标从空间骨架和家具决策中自然涌现，不需要额外的分析步骤。

**Stage 4（优化）→ 改善标准**：品质维度是优化阶段的检查清单。逐项对比实际布局与声明的设计目标，识别改善机会。已达成的目标确认通过，未充分达成的目标触发定向调整。

这个"目标声明→执行→目标验证"的闭环保持不变——变的是声明时机（从策略阶段末尾移到语义方案的渐进构建中）和验证方式（从被动审查变为主动优化）。
