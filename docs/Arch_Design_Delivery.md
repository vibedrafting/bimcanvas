# Arch_Design_Delivery — 设计交付物数据模型

> **本文用途**：介绍 BIMCanvas 的设计交付物模型——AI（或人）产出的设计方案如何存储、如何并存多个候选、如何"采纳"生效、分区如何递归嵌套。
>
> **读者**：想了解"多方案 AI 设计的成果该怎么建模"的工程师，不要求 BIMCanvas 背景。
>
> **与执行层的关系**：本文是**数据契约层**，姊妹文档 [Arch_Workflow.md](./Arch_Workflow.md) 是**执行层**。两层刻意解耦——换掉 workflow 引擎、回到单 Agent 甚至人工设计，本文的模型依然成立。字段级 .bcp 格式见 [Schema.md](./Schema.md)。
>
> **状态**：2026-06 当前态。

---

## 1. 要解决的问题

AI 设计天然是**多候选**的：一个房间出 3 个方案让用户挑；挑完之后用户可能反悔换另一个；落选方案要可回溯。传统做法的坑：

- **复制式采纳**（胜者拷贝到"正式目录"）：双份数据漂移、回退困难、目录里"哪份是真的"靠口口相传。
- **固定 canonical + variants/ 子层**：胜者与候选地位不对等，"换一个采纳"变成跨层搬家，目录结构随采纳动作变形。
- **删除式收口**（落选即删）：不可回溯，用户反悔无路。

我们的答案是两个互相正交的模型：**纯指针式平级**（横向：多方案如何并存与生效）+ **Zone 递归嵌套**（纵向：分区如何层层展开）。

## 2. 模型一：纯指针式平级（横向）

### 2.1 核心规则

所有方案**平级**存放，没有固定 canonical、没有 `variants/` 子层；父目录的 `DESIGN.md` 用一行 frontmatter 指针标记当前生效方案：

```
schemes/{zoneId}/DESIGN.md          ← frontmatter: adopted: {slug}
schemes/{zoneId}/{slug-A}/...       ← 方案 A（平级）
schemes/{zoneId}/{slug-B}/...       ← 方案 B（平级）
```

**采纳 = 翻指针**。零复制、零删除、零降级、完全可逆。换方案就是改一行 frontmatter；所有消费方（Web 渲染 / Revit 导出 / 验证 / 查询）统一走 `resolve-adopted(zoneId) → path` 解析器取生效方案。

### 2.2 文件划界口诀

| 内容 | 载体 | 粒度 |
|------|------|------|
| 设计意图（方向、战略、施工简报、自检记录、决策日志） | `DESIGN.md`（Markdown） | 设计区粒度：父一份 + 每方案一份 |
| 几何（家具坐标、bounds） | `modules.json`（JSON） | 叶子分区粒度 |

一句话：**意图给人和 LLM 读，写散文；几何给代码读，写 JSON。**

### 2.3 父与子的职责分界

- **父 `{zoneId}/DESIGN.md`**：只持共享内容——客观空间骨架（几何、动线、采光，所有方案共用）+ `adopted` 指针 + append-only 决策日志。**永不存任何一个方案的战略或简报**。
- **方案 `{slug}/DESIGN.md`**：自包含的完整施工合同——方向、战略、施工简报、自检与优化记录。无 frontmatter。

这样"AI 终选"和"用户终选"两种产品形态在文件级完全统一，唯一差别是指针由谁翻。

### 2.4 可见性与生效正交

目录名 `_` 前缀 = 对用户隐藏（可回溯但 Web 不显示）；`adopted` 指针 = 生效。两者正交：可以有可见但未采纳的候选（用户对比中），也可以有隐藏的历史方案。当前产品形态（用户终选）下候选全部可见、无前缀。

### 2.5 读时叠加

设计或施工前，从根到叶顺序读每层 `DESIGN.md`（`schemes/ → {zoneId}/ → {slug}/`），约束从宽到窄逐层收紧。没有"合并视图"这种派生产物——**文件本身就是唯一真理源**，叠加发生在读取时而非落盘时。

## 3. 模型二：Zone 递归嵌套（纵向）

### 3.1 被推翻的前提

最初假设"子分区是所有方案共享的前提"。错——**分区线是设计结论，不是前提**：它从家具预布置与动线中"浮现"，不同设计思维产出不同分区结构（线性思维可能不分区，分区思维可能切 2-3 个子区）。所以子分区不可能一律共享。

### 3.2 subZones 的两种来源，落点必须不同

| 来源 | 性质 | 落点 | 共享？ |
|------|------|------|--------|
| AI 设计产生（分区思维方案） | 设计决策 | `{zone}/{slug}/zones.json`（slug **之内**） | 每方案各异 |
| 用户/上游指定 | 冻结边界 | `{zone}/zones.json`（slug **之上**） | 所有方案共享 |

判据极简：**slug 在路径里的位置**说明一切——`rz_3/{slug}/dz_1/`（slug 在分区之上）= AI 的分区方案，采纳方案就连分区一起采纳；`rz_6/dz_客厅/{slug}/`（分区在 slug 之上）= 用户给定的共享分区，每个叶子各自跑设计。

### 3.3 统一抽象：「设计区」是递归概念

**设计区 = 任何"跑一次完整设计流程"的节点**，路径可以是 `rz_3`，也可以是 `rz_6/dz_客厅`：

- 节点带用户给定的 subZones → 它是**容器**：本级不设计，每个叶子各成更深一层设计区；
- 节点没有 → 它**就是设计区**：本级跑流程，某个方案可以用分区思维在自己内部产生 subZones（落在 slug 内）。

深一层的设计区和浅一层的在流程眼里是**同一种东西**，只是路径长一截。不为任何层级写特例——这正是与执行层解耦的体现：workflow 拿到一个路径就能跑，不关心它在树的第几层。

## 4. 两模型如何咬合

```
schemes/
├── DESIGN.md                          # 全屋父：项目配置（冻结）+ 全屋设计核
├── {zoneId}/
│   ├── DESIGN.md                      # 分区父：共享骨架 + adopted 指针 ←── 模型一
│   ├── {slug-A}/
│   │   ├── DESIGN.md                  # 方案 A 完整合同
│   │   ├── zones.json                 # （可选）A 自己的分区思维结论 ←── 模型二
│   │   ├── dz_1/modules.json          # 叶子几何
│   │   └── dz_2/modules.json
│   └── {slug-B}/
│       ├── DESIGN.md                  # 方案 B（线性思维，不分区）
│       └── modules.json               # 设计区自身即叶子
```

横向（模型一）回答"A 和 B 谁生效"；纵向（模型二）回答"A 内部还要不要再切"。两者唯一的交点是路径形态约定（§3.2 的判据），除此之外互不知晓。

## 5. 设计原则沉淀

| # | 原则 | 一句话 |
|---|------|--------|
| 1 | 采纳=翻指针 | 状态变更永远是改一行指针，不搬文件 |
| 2 | 平级无特权 | 没有 canonical 目录；胜者与落选者结构同构 |
| 3 | 意图/几何分离 | md 给人与 LLM，json 给代码 |
| 4 | 父持共享、子自包含 | 父永不存方案私有内容；每个方案离开父也读得懂自己 |
| 5 | 分区是结论不是前提 | AI 产生的 subZones 落方案内；用户给定的落方案外 |
| 6 | 设计区递归同构 | 任何层级的设计节点对流程是同一种东西 |
| 7 | 读时叠加，不存派生 | 约束叠加发生在读取时；磁盘上没有"合并视图" |
| 8 | 决策日志 append-only | 评审/采纳/变动理由追加进父 DESIGN.md，成为系统级记忆 |
