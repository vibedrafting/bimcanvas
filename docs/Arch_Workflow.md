# Arch_Workflow — Workflow 执行架构

> **本文用途**：介绍 BIMCanvas 的 Workflow 执行技术——AI 设计任务如何从一句自然语言变成确定性编排的多 Agent 协作，以及在实测中付出代价换来的架构教训。
>
> **读者**：想了解"LLM Agent 工作流该怎么编排"的工程师，不要求 BIMCanvas 背景。
>
> **姊妹文档**：设计交付物的数据模型（方案如何存储、采纳、嵌套）见 [Arch_Design_Delivery.md](./Arch_Design_Delivery.md)——那是数据契约层，与本文的执行层解耦：换掉执行引擎，交付物模型依然成立。
>
> **状态**：2026-06 当前态（五段流）。

---

## 1. 一句话定位

把室内设计 AI 从「一份巨型提示词软编排」重构为「**确定性代码编排 + 粗粒度 LLM 子代理 + 分级知识注入**」的混合架构：流程的骨架由 JavaScript 写死，每一步的领域判断由 Agent 承担，领域知识独立成层按需加载。

## 2. 为什么需要它：纯提示词编排的三个不可靠

最初的形态是把整个设计流程写进主控的系统提示词（"先分析、再规划、然后布置、最后检查……"），靠 LLM 自己遵守。实测暴露三类结构性问题：

1. **流程不确定**：步骤会被跳过、顺序会漂移、失败不重试。提示词只能"恳求"，不能"保证"。
2. **副作用无核验**：Agent 自报"已完成采纳"但磁盘上什么都没发生；自报"验证通过"但实际 0 个模块。LLM 的自我汇报不可作为控制流依据。
3. **并行无从谈起**：提示词驱动的主控天然串行，N 个方案只能一个接一个生成。

这三个问题的共同解法：**凡是"何时做、做几次、成功与否"的判断，从 LLM 手里拿走，交给代码**。

## 3. 五层架构

```
L0 主控（自然语言提示词）   —— 模糊意图路由：听懂用户、选 workflow、喂参数、转述结果
   └─ L1 workflow 脚本（确定性 JS） —— 何时/何序/扇出/循环/分支/闸门（施工脊柱）
        └─ L2 agent（.md 薄载具）   —— 角色 + 模型档 + 工具权限 + "怎么做好一件事"
             └─ L3 知识层           —— 设计规则散文(references/*.md) + 模块库(JSON 结构化)
                  └─ MCP 工具       —— 数据读写 + 几何计算（零决策）
```

每层只做一类事，越界即架构债：

| 层 | 持有 | 严禁持有 |
|----|------|---------|
| L0 主控 | 意图分类、参数组装、收尾转述 | 流程步骤（会漂移） |
| L1 workflow | 控制流、并行、schema 校验、确定性核验 | 业务知识（检验法：删掉所有领域名词，脚本仍读得通） |
| L2 agent | 单一角色的执行方法论 | 编排（agent 不调 agent）、知识本体 |
| L3 知识 | 领域规则、评价维度、模块约束 | 流程（知识不知道自己何时被读） |
| MCP | 读写与几何 | 任何决策（"放哪里"永远不归工具） |

**核心信条**：薄编排厚知识、流程房型中立、副作用由编排核验、采纳=翻指针（见姊妹文档）。

「试金石」：把这套架构从卧室设计换成会议室设计，应当只需要换 L2/L3，L1 一行不动。

## 4. 当前主流程：五段流（无参考、多方案设计）

```
1 感知        perception-agent 单会话：用户诉求定调 + 空间骨架（动线/纵深/采光）
2 规划推演    zoning ∥ sequential 双思维并行（上游产物直传，免重复读盘）
3 多方案生成  multi-plan：组织 N 个方向层变体（每变体 ≤1 条硬锚点，其余全局自由）
4 方案落地    并行 N 个集成版 placement：
              施工简报 → 按图施工 → 落位自检 → validate → 2 次定点识图自评
              → 自优化（报警逐条处置 + 可选家具联动置换）→ 返回结构化 factsheet
5 方案对比    脚本机械拼对比表（零 LLM）；终选 = 用户在 Web 端点「采纳」
```

几个值得注意的设计决策：

- **差异化在方向层，不在配置层**：每个变体只锁一条"锚点"（如"床靠西墙"），其余决策权完整保留给落地 Agent。曾试过把整面墙的家具归属预先锁死——实测证明这剥夺了施工者的全局重判权，虚构的叙事变成铁律，质量崩溃。
- **AI 不做终选**：方案对比表只陈列事实（主家具靠墙、储物延米、可选家具有无），由用户看着可视化布局拍板。AI 裁决环节（judge）被实测证伪后移除（见 §6 教训五）。
- **识图自评内置于落地会话**：布置完成、机器验证通过后，同一个 Agent 调视觉服务问 10 个聚焦小问（"床头柜与床是否贴邻？"），报警逐条处置并强制记录——外部视角（渲染图识别）+ 内部上下文（为什么这么放）在同一会话里闭环。

## 5. 确定性控制流：代码兜底 LLM 的四种手段

这是本架构最核心的工程技术，每一种都对应一类 LLM 不可靠性：

| 手段 | 解决的问题 | 实现 |
|------|-----------|------|
| **Schema 桥** | 自由文本无法做控制流分支 | 每个 Agent 以 JSON Schema 强制返回结构化结果（不合法自动重试），脚本拿到的是可编程的数据而非散文 |
| **后置核验（verify）** | Agent 自报不可信 | 凡带副作用的步骤，派零领域的 verify-agent 查磁盘事实（模块数、文件存在性），布尔结论由脚本计算，失败走脚本写死的重试/降级路径 |
| **机械护栏** | LLM 的"独立生成"会悄悄趋同 | 方案间雷同检测用归一化字符串比对（主家具墙面归属签名两两对照），不再请 LLM "判断是否雷同" |
| **机械活下沉** | LLM 干机械活又慢又贵 | 对比表排版、章节落盘 upsert、产物拼接，全部是纯代码——曾用一个 Agent 花 4m28s 干"拼台账"这件 0 token 也能干的事 |

## 6. 实测教训（46 分钟换来的）

> 背景：第一代"七步流"把流程拆给 12 个专职 Agent（感知×2、规划×2、生成、落地×N、评审×2、裁决、优化、核验、归档），在真实户型上实测 46m05s；而旧的单会话 skill 流跑同样任务只要 15min，质量不相上下。逐段日志分解后重构为五段流（约 22-26min，Agent 数 26→10）。以下教训全部有日志实证。

### 教训一：串行拆解是纯成本，并行拆解才有收益

拆解任务的三重税：**冷启动**（每个新 Agent 会话重新加载系统提示词+知识层，26 次会话 26 次税）、**序列化转手**（上游必须把认知压成文本，有损且膨胀——中间产物曾失控到单步转录 609KB，下游花 6 分钟重读）、**机械中转**（归档 Agent 8 次调用 202s，其中 180s 阻塞关键路径）。

这些税在**串行链**上没有任何对价——Step1→2→3 接力、评审→裁决→优化流水线，拆了只亏不赚。唯一赚钱的拆分是**并行扇出**：N 个方案同时落地，墙钟≈最慢单链。

**规则：串行认知链不拆，并行扇出才拆。**

### 教训二：过程性上下文不可序列化——质量损失比时间损失更隐蔽

三个日志实证，根因相同：

1. 评审 Agent 把施工简报的辩护词当事实基底（自证循环）——它没有施工者的过程记忆，只能信文本；
2. 优化 Agent 不加验证就驳回视觉识别的正确报警——它没有评审会话的证据链；
3. 优化 Agent 用"实体 400 + 使用区 600 = 1000"的双重扣减否决了可行布置——施工者知道"使用区与通道分时复用"的语境，转手后丢了。

"为什么排除了那个选项"这类隐性状态写不进交接文档。设计是连贯认知活动，切断会话就是切断认知。

### 教训三：正确的颗粒度是"认知单元"，不是"工序"

教训二不能推到"全流程一个 Agent"——集成版落地会话已达 500-600KB，过长上下文有注意力稀释问题，统一上下文的收益曲线会掉头。五段流保留的拆分点全是**认知断点**：感知→规划是对象切换、生成→落地是一对多扇出、方案与方案之间互相独立。

**规则：一个连贯认知单元 = 一个 Agent 会话。**"设计一个方案"是单元；"评审刚才那个设计"不是——它是同一单元的延续，应留在原会话内（自检/自评/自优化）。

### 教训四：Workflow 的价值是控制流，不是拆任务

"用 workflow 编排"与"细拆 Agent"是两件独立的事，七步流错误地把它们绑死了。五段流证明 workflow + 粗粒度 Agent 是成立的组合：脚本依然提供 schema 闸门、verify 核验、查重护栏、并行扇出——这些价值与 Agent 拆多细无关。

### 教训五：质量投资排序——知识层与确定性验证优先于"更多审查者"

旧单会话流 15min 质量稳定，靠的是三样：知识层规则写得好、validate 确定性闸门、用户终选。七步流追加的 4 个评审/裁决/优化 Agent 合计 ~46min Agent 时间，换来的质量增量接近零、甚至为负（自证循环、误驳报警均发生在这些环节）。

同样的预算花在哪里更值：把一条领域规则写进知识层（如"通道扣减只扣家具实体深度"），所有方案、所有未来任务永久受益；多雇一个评审 Agent，每次执行付一遍冷启动税，还可能引入新的误判链。

### 教训六：给 LLM 的每一份输入都要问"它需要知道吗"

中间产物限长（定调≤25 行、骨架≤40 行、草稿≤30 行）带来的不只是省 token——更短的上游材料让下游 Agent 的注意力集中在真正的约束上。每个中间字段都是双向收费：上游生成一次、下游阅读一次。

### 附注：一条平台层发现

后台任务的完成通知（task_notification）只在主控空闲时投递给宿主进程；主控回合内完成的任务，通知直接注入主控的 prompt 流、宿主侧零信号。任何依赖"宿主收到完成通知"的回合内收口设计都不成立，须改用心跳静默类推断判据。（实测定案 2026-06-11。）
