BIMCanvas Agent Deck

Agent 不是直接改 JSON 的黑盒，而是一条可审查的 标准工作流

从用户发出一句自然语言开始，BIMCanvas Agent 会先判断任务类型，再加载对应 workflow， 读取空间上下文，在隔离环境中执行写操作，最后经过 Server 验证与用户审查后才交付。 这套设计的重点不是“会不会布置”，而是“怎么稳定地布置”。

02 / 08
Positioning

Agent 在系统里的位置，是 决策层，不是计算层

从架构上看，Agent 端承担的是“理解用户、选择策略、发出动作”的职责。几何计算、约束验证、 状态管理与 Git 运维都不应该由 Agent 自己完成。这样做的目的，是把 AI 的自由度限制在“决策”而不是“造数据”。

用户请求
通过 /api/chat/stream 进入 Agent，携带项目路径、窗口 ID、用户消息等上下文。
MainAgent
负责意图识别、任务分类、工作流编排，以及最终回复整合。
Workflow Skills
按任务类型自动加载 query-workflow、edit-workflow、generate-workflow。
执行体
可以是当前直接执行的 MainAgent，也可以是后续派发的 layout-agent；对外暴露的标准流程不变。
Server + MCP
负责截图、验证、Git Worktree、自动存档、前端通知等确定性工作。
Agent 只做决策

决定“放什么、放哪儿、为什么这样放”，但不自己推导 innerBoundary、禁区或碰撞结果。

Server 做计算与验证

Zone、Exclusion、碰撞、方向归一化、自动生成 ID，都应该收口在 Server 端统一执行。

Git Worktree 做隔离

只要任务涉及写操作，就优先把修改放到隔离环境中，避免干扰用户当前窗口和主分支。

03 / 08
Standard Flow

标准工作流可以压缩成 6 个环节

无论是查看信息、移动单件家具，还是完整生成一个房间方案，Agent 端都尽量复用同一条主链路。 变化的是权限、读写强度和是否需要启动 Git 隔离层，而不是流程逻辑本身。

01 / 接收
接收请求

读取 `projectPath`、`windowId`、`message`，建立本次会话的项目上下文。

/api/chat/stream
02 / 分类
判断任务类型

把用户需求归入 `query`、`edit` 或 `generate`，决定允许的工具范围和后续流程。

query / edit / generate
03 / 加载
加载 Workflow

自动注入对应 Skill，把“这类任务必须先做什么、禁止做什么”固定下来。

Workflow Skill
04 / 感知
读取空间与规则

看截图，读模块库、设计原则、room zones、exclusions、openings，建立上下文。

Screenshot + Read
05 / 执行
执行并修正

写入文件后立即 `validate_layout`，若失败则最小修正；编译通过后再做截图审查。

Write -> Validate -> Review
06 / 交付
交付与用户控制

写任务完成后通知 Web 展示 diff，最终是否合并、合并到哪里，由用户决定。

Review Gate
04 / 08
Task Types

一切都从 query / edit / generate 的分流开始

这一步不是简单的关键词匹配，而是整个安全边界的入口。特别是 query 任务，如果不先分类清楚， 很容易出现“用户只想问一句，Agent 却写了一堆数据”的越权行为。

Read Only
Query

目标是回答问题，不是修改项目。

例子：“主卧现在有多少家具？”
允许：Read、Glob、Grep
禁止：Write、Edit、自动补数据
Git：无需 AI Job，无需 Worktree
交付：只返回事实，不返回修改
Single Change
Edit

目标是完成一个明确、局部、单一的修改动作。

例子：“把主卧的床向右移动 500mm。”
允许：Read、Write、Edit、验证
边界：只改目标对象，不扩展需求
Git：通常进入 AI Job 隔离环境
交付：给出一个可审查的局部 diff
Full Layout
Generate

目标是完整生成一个区域方案，最依赖前置感知和验证闭环。

例子：“给主卧做一套动线优先方案。”
允许：完整工作流 + 多轮修正
要求：先读规则，再写结果，写后必须验证
Git：需要 AI Job，可扩展成多 Worktree 并行
交付：方案结果 + 审查状态 + 可合并分支
05 / 08
Generate Deep Dive

Generate 是 Agent 端最有代表性的 标准主链

它最能体现 BIMCanvas 的设计哲学：先感知，再理解，再形成策略，然后写文件、调用编译器、做截图审查， 最后才向用户汇报“已经完成”。如果跳过任何一环，稳定性都会明显下降。

执行前必须补齐的上下文

空间截图

先看一眼真实空间形态，理解门窗、主通道和空余面，而不是只盯 JSON。

设计原则 + 房间规则

读取跨房间设计原则，以及当前房间对应的布置规则，防止生成结果只满足几何、不满足设计逻辑。

模块库契约

读取 modules/README.md 与 modules/module_library.json，尺寸与关系禁止编造。

空间约束数据

读取 computed/room_zones.json、computed/exclusions.json、baseline/openings.json。

Generate 的 6 段展开

1
感知

把截图、房间边界、门窗和禁区拼成一张“可设计空间地图”。

2
理解

识别房间类型、用户约束、主次功能、可能的锚点家具和动线方向。

3
策略

决定先放什么、哪些家具必须成套、主通道预留多少、哪些东西宁可不放也不能硬塞。

4
执行

写入 schemes/{zoneId}/modules.json，只输出被允许的数据格式。

5
审查

先 validate_layout 做硬约束检查，再通过截图审查视觉与功能合理性。

6
汇报

只有自审通过后，才向用户报告放置清单、修正情况和整体评价。

禁止跳过验证、禁止编造尺寸、禁止自审未过就说“完成了”。这三条是 Agent 端最重要的稳定性底线。
06 / 08
Full Example

完整示例：给主卧生成一套 动线优先 方案

下面用一个最典型的写任务，把标准链路串起来。这个例子既能体现 generate-workflow 的读取与验证闭环， 也能把 Git Worktree 隔离、用户审查合并这两个设计点讲清楚。

用户输入：
“给主卧做一个动线优先方案，床头靠北墙，尽量保留 900mm 主通道，如果放不下就少放辅助家具。”
任务分类

这是一个 generate 任务，不是简单 edit，因为目标是重新规划完整布局。

执行体抽象

可以由当前 MainAgent 直接执行，也可以由 layout-agent 承接；对外工作流保持一致。

关键文件

computed/room_zones.json、computed/exclusions.json、baseline/openings.json、schemes/rz_master/modules.json

关键工具
request_background_screenshot
Read
Write
validate_layout
ai_job_create
ai_job_complete
1. MainAgent 先判定这是 generate 写任务
Routing

系统自动加载 generate-workflow，并切换到“完整布置”所需的读取与验证流程，而不是走单点编辑逻辑。

2. Server 为写任务准备隔离环境
Isolation

调用 ai_job_create(name="master-flow")。如果当前分支有未提交修改，Server 会先自动存档，再创建临时分支和 Worktree。

3. 执行体先“看懂房间”，再决定怎么放
Perceive

先取背景截图，再读取 room zones、禁区、门窗、模块库和设计原则。此时还不能写入，因为连锚点家具和主通道都还没判断清楚。

4. 形成动线优先策略
Strategy

例如：床头贴北墙，衣柜沿东墙布置，主通道至少 900mm，若梳妆台会压缩通道则直接放弃。这里体现的是“少做比做错更好”。

5. 写入目标文件
Write

把决策结果写到 schemes/rz_master/modules.json。输出只包含合法模块、bounds、facing、items，不在 Agent 侧生成几何派生数据。

6. 调用 validate_layout 做硬检查
Compile

Server 会统一检查越界、墙体/柱体/禁区重叠、模块互撞，并规范化 facing。如果失败，Agent 必须回到 Worktree 修正而不是硬报成功。

7. 编译通过后做截图审查
Review

此时看的是设计质量：床边是否逼仄、门口是否压迫、窗边是否被高柜占死。如果视觉和功能不合理，再做一次最小修正。

8. 通知 Web 可审查，用户决定是否合并
Delivery

调用 ai_job_complete(names=["master-flow"]) 后，Web 展示 diff 与预览。用户可以合并到当前分支，也可以丢弃整套方案。Agent 不自动 merge。

Parallel Design

同一套标准流，如何扩展成 并行方案

多方案并行不是另一套系统，而是在标准写任务外面再包一层 Job 调度。核心逻辑不变： 每个方案都在自己的 Worktree 中读、写、验证、提交，最后把选择权留给用户。

Primary Window
用户当前窗口

真实交互入口，通常绑定主分支或某个策略分支。它负责承接用户对话，但不直接承受 AI 的临时写入。

main 或 strategy/flow-first
AI Job Worktree
单个方案的隔离环境

一旦进入 edit / generate，Server 就基于当前分支拉出临时分支与 Worktree，让执行过程与用户操作物理隔离。

feat/ai-master-flow-20260331
Multi Scheme
多方案只是多份 Job

如果用户说“给我 3 个方案”，系统就创建 3 个 AI Job：例如 storage、flow、minimal，各自跑完整标准流。

feat/ai-storage / feat/ai-flow / feat/ai-minimal

Worktree 不是分支

分支是持久版本，Worktree 是临时执行目录。Agent 在 Worktree 里工作，但交付的是可被用户采纳或丢弃的版本差异。

同一分支不能被重复检出

这就是为什么 BIMCanvas 需要“窗口 Worktree”和“AI Job Worktree”分层设计，避免 Git 自身的并发限制撞到用户体验上。

合并权永远在用户

Agent 只负责生成候选方案，Web 负责展示 diff，最终是否合并、合并到哪个窗口分支，由用户控制。

08 / 08
Takeaways

Agent 端设计的核心，不是“更聪明”，而是 更可控

如果把这套设计压缩成一句话，就是：让 AI 负责决策，让 Server 负责确定性，让 Git 负责隔离，让用户负责最终采纳。 这样才能把一次布置任务，变成一条可复盘、可修正、可合并的工程流程。

标准流的价值

把 prompt、工具、文件、验证和交付串成固定顺序，减少“想到哪做到哪”的随机性。

稳定性的来源

来自任务分类、Skill 边界、必读上下文、验证闭环、截图审查和 Worktree 隔离，而不只来自模型能力。

扩展性的来源

单方案与多方案复用同一内核，新增的是 Job 数量和分支组织，不需要重写 Agent 的思考逻辑。
