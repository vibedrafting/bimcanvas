# BIMCanvas Agent 架构与提示词设计

> **版本**：v2.0 | **更新日期**：2026-01-13
> **目的**：定义 BIMCanvas Agent 的整体架构、SubAgent 设计规范、提示词优化指南

---

## 一、设计哲学

### 1.1 整体架构

```
┌─────────────────────────────────────────────────────────────────┐
│                    BIMCanvas Agent 架构                          │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│   ┌─────────────────────────────────────────────────────────┐   │
│   │  主控 Agent（协调者）                                    │   │
│   │  • 分析用户意图，判断任务类型                            │   │
│   │  • 派发任务给 SubAgent                                  │   │
│   │  • 整合结果，向用户汇报                                  │   │
│   └─────────────────────────────────────────────────────────┘   │
│                              ↓ 派发                             │
│   ┌─────────────────────────────────────────────────────────┐   │
│   │  SubAgent（领域专家）                                    │   │
│   │  • layout-agent：家具布置专家                            │   │
│   │  • zone-agent：空间分区专家                              │   │
│   │  • ...                                                  │   │
│   └─────────────────────────────────────────────────────────┘   │
│                              ↓ 调用                             │
│   ┌─────────────────────────────────────────────────────────┐   │
│   │  MCP 工具（能力扩展）                                    │   │
│   │  • 领域特定功能封装                                      │   │
│   │  • 数据访问接口                                          │   │
│   └─────────────────────────────────────────────────────────┘   │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

> **架构演进**：早期设计为单体 PlacementAgent，现已**废弃**。当前采用「主控 Agent + SubAgent」架构，更好地实现职责分离和并行执行。

### 1.2 角色定位

| 组件 | 比喻 | 核心职责 |
|------|------|----------|
| **主控 Agent** | 项目经理 | 任务协调、意图解析、结果整合 |
| **SubAgent** | 领域专家 | 专注单一领域任务执行 |
| **MCP 工具** | 工具箱 | 能力扩展、数据接口 |
| **Server** | 心脏 + 神经系统 | 状态管理、几何计算、验证 |

### 1.3 职责边界

```
主控 Agent：协调派发，不直接执行专业任务
SubAgent：专注执行，不越权扩展任务
Server：管理状态、执行验证，不做布置决策
```

| 维度 | 主控 Agent | SubAgent | Server |
|------|------------|----------|--------|
| **任务类型判断** | ✅ | ❌ | ❌ |
| **SubAgent 调用** | ✅ | ❌ 禁止嵌套 | ❌ |
| **领域任务执行** | ❌ | ✅ | ❌ |
| **状态管理** | ❌ | ❌ | ✅ |
| **约束验证** | ❌ | ❌ | ✅ |

### 1.4 MCP 工具 vs SubAgent

| 维度 | SubAgent | MCP 工具 |
|------|----------|----------|
| **本质** | AI Agent，有决策能力 | 函数调用，无决策能力 |
| **复杂度** | 复杂任务，需要推理 | 简单任务，确定性输出 |
| **自主性** | 有限自主性 | 无自主性，被动调用 |
| **示例** | 布置家具、规划方案 | 读取数据、验证碰撞 |

## 二、核心设计原则

### 2.1 任务类型分类（关键！）

> **教训来源**：layout-agent 在执行"统计模块数量"查询任务时，错误地写入了数据。

**必须区分两种任务类型**：

| 任务类型 | 操作类型 | 允许的工具 | 示例 |
|----------|----------|------------|------|
| **query** | 只读 | Read, Glob, Grep | 统计、查看、列出、检查 |
| **execute** | 可写 | Read, Write, Edit, Glob, Grep | 布置、添加、移动、删除 |

**主控 Agent 判断规则**：

```markdown
## 任务类型判断

**query（只读）任务关键词**：
- "有多少..."、"统计一下..."、"查看..."、"列出..."
- "当前状态是..."、"已经布置了什么..."、"检查..."
- 特征：用户只想获取信息，不期望系统做任何修改

**execute（可写）任务关键词**：
- "帮我布置..."、"添加一个..."、"移动..."、"删除..."
- "设计..."、"创建..."、"修改..."、"更新..."
- 特征：用户明确期望系统修改数据
```

**任务描述规范**（主控 Agent 调用 SubAgent 时）：

```markdown
调用 SubAgent 时，必须在任务描述开头指定：

【操作类型】: query 或 execute
【用户需求】: ...
【目标对象】: ...
【约束条件】: ...
```

### 2.2 最小权限原则

**按任务类型配置工具权限**：

```python
# query 任务：只读工具
query_tools = ["Read", "Glob", "Grep"]

# execute 任务：完整工具
execute_tools = ["Read", "Write", "Edit", "Glob", "Grep"]
```

### 2.3 行为边界约束

**SubAgent 提示词必须包含的约束**：

```markdown
## 行为边界

### 禁止行为
- ❌ 在 query 任务中使用 Write/Edit 修改任何数据
- ❌ 在发现空数据时自动创建示例数据
- ❌ 执行用户未明确要求的操作
- ❌ 自作主张扩展任务范围
- ❌ 根据其他文件推断不存在的数据（幻觉）

### 允许的主动行为
- ✅ 发现问题时提出建议（但不自动执行）
- ✅ 在 execute 任务中优化布置方案
- ✅ 报告执行过程中遇到的问题
```

### 2.4 主动性边界

> **核心原则**：宁可少做，不可多做

| 等级 | 描述 | 示例 |
|------|------|------|
| **被动执行** | 严格按任务描述执行 | query 任务 |
| **有限主动** | 在任务范围内做合理优化 | execute 任务中的布置优化 |
| **建议但不执行** | 发现问题时报告，等待指令 | 发现空数据时报告而非创建 |

**反例（禁止）**：

```
用户问"有多少模块"
→ Agent 发现是空数组
→ Agent 认为"用户可能想要布置"
→ Agent 自动创建数据  ← 错误！
```

**正例（正确）**：

```
用户问"有多少模块"
→ Agent 发现是空数组
→ Agent 报告"当前项目没有布置任何模块，数量为 0"
→ 结束  ← 正确！
```

## 三、SubAgent 清单与职责

### 3.1 layout-agent（家具布置专家）

**职责**：
- 读取房间分区数据，理解空间特点
- 分析门窗位置，规划动线
- 根据布置规则为房间布置家具
- 输出符合规范的布置结果

**操作模式**：

| 模式 | 触发条件 | 允许工具 |
|------|----------|----------|
| query | 统计、查看、检查 | Read, Glob, Grep |
| execute | 布置、添加、移动、删除 | Read, Write, Edit, Glob, Grep |

### 3.2 zone-agent（空间分区专家）

**职责**：
- 分析户型结构
- 划分功能区域
- 生成 Designable Zone

### 3.3 规划中的 SubAgent

| SubAgent | 职责 | 状态 |
|----------|------|------|
| **strategy-agent** | 策略生成、方案对比 | 规划中 |
| **validation-agent** | 布置验证、冲突检测 | 规划中 |
| **git-agent** | 版本管理、分支操作 | 规划中 |

## 四、核心工作场景

### 场景 A：策略分叉 (Strategy Fork)

**目标**：风格与策略的 A/B 测试

**用户指令**："给我的客厅出三个方案：一个是'极致收纳'，一个是'动线优先'，还有一个'极简留白'。"

**执行流程**：

1. **意图解析**（主控 Agent）：
   - 识别 action = `parallel_generate`
   - 提取 target_zone = `living_room`
   - 输出设计意图对象

2. **操作编排**（Server）：
   - 创建三个 Worktree
   - 将策略配置写入各 Worktree

3. **并发执行**（SubAgent × 3）：
   - 三个 layout-agent 实例同时启动
   - 各自根据不同的策略参数执行布置决策

4. **提交与验证**（SubAgent + Server）：
   - 各 Agent 执行 `git commit` 提交方案
   - Server 验证结果，通知前端展示

### 场景 B：布局求解器 (Layout Solver)

**目标**：硬约束下的局部最优解搜索

**用户指令**："这个卫生间太小了，帮我看看能不能塞进一个浴缸和淋浴房。"

**执行流程**：

1. **意图解析**（主控 Agent）：识别 action = `layout_solve`
2. **操作编排**（Server）：创建临时 Worktree
3. **迭代搜索**（SubAgent）：高频迭代尝试，失败则继续
4. **结果交付**：只有验证成功的方案会被 Commit

### 场景 C：主编式合并 (Editorial Merge)

**目标**：用户作为总设计师的方案融合

**触发方式**：用户 UI 操作（非自然语言指令）

**用户操作**：用户看着三个平行方案，觉得"方案 A 的沙发摆得好，但方案 B 的电视柜设计更合理"。

**执行流程**：

1. **可视化对比**（Server + Web）：
   - 前端通过"三联屏"展示不同 Worktree 的渲染结果
   - 用户可以切换、对比各方案

2. **区域级选择**（用户 + Web）：
   - 用户勾选方案 A 的 `Zone: SofaArea`
   - 用户勾选方案 B 的 `Zone: TVArea`
   - 前端生成合并请求

3. **Cherry-pick 合并**（Server）：
   - 执行精确的 JSON 合并
   - 检查依赖冲突（如有 `DependencyGroup` 被拆分则警告）
   - 合并到 `main` 分支

4. **清理**（Server）：
   - 删除未被采纳的 Worktree
   - 保留合并后的最终方案

**对 Agent 的前置要求**（在生成阶段）：
- **解耦设计**：生成的方案应高度模块化，避免强耦合
- **依赖标记**：强关联的家具需标记 `DependencyGroup`，提示用户成套采纳

> 注：此场景中 Agent 不直接参与执行，但其在场景 A/B 中的设计质量决定了合并的可行性。

> 详细的并行设计模式见 [Agent_SDK_Parallel.md](./Agent_SDK_Parallel.md)

## 五、Git Worktree 并行架构

### 5.1 架构原理

```
传统认知：1 个 Git 仓库 = 1 个文件夹 = 1 个当前分支
实际上：1 个 Git 仓库 = N 个文件夹 = N 个并行分支
```

**`git worktree`** 允许从同一个 `.git` 仓库中，"映射"出多个独立的文件夹。

### 5.2 混合架构

```
项目根目录/
├── .git/                      # 共享的 Git 历史
├── baseline/                  # main 分支的基础数据
├── schemes/                   # main 分支的方案
├── .worktrees/                # 临时工作树目录
│   ├── ai-job-1/              # Worktree 1 → feat/ai-storage
│   │   ├── baseline/
│   │   └── schemes/
│   ├── ai-job-2/              # Worktree 2 → feat/ai-flow
│   └── ai-job-3/              # Worktree 3 → feat/ai-minimal
```

### 5.3 并行工作流程

```
┌─────────────────────────────────────────────────────────────────────────┐
│                     Agent + Git 完整工作流                               │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  【触发阶段】                                                            │
│  用户请求 ──→ 主控 Agent 解析意图 ──→ 创建策略配置                       │
│                                                                         │
│  【准备阶段】                                                            │
│  Server ──→ git worktree add .worktrees/ai-job-{id} feat/ai-{name}     │
│         ──→ 将策略配置写入 Worktree                                     │
│         ──→ 启动 SubAgent 进程，传入 Worktree 路径                      │
│                                                                         │
│  【执行阶段】                                                            │
│  SubAgent ──→ 在 Worktree 中读取数据                                    │
│           ──→ 执行布置决策                                               │
│           ──→ 写入 schemes/{s}/*.json                                   │
│           ──→ git add . && git commit -m "feat(layout): ..."           │
│                                                                         │
│  【验证阶段】                                                            │
│  Server ──→ 读取 Commit 内容                                            │
│         ──→ 执行约束验证                                                 │
│         ──→ 验证通过：通知前端展示                                       │
│         ──→ 验证失败：通知 SubAgent 修正                                 │
│                                                                         │
│  【交付阶段】                                                            │
│  用户选择 ──→ Server 执行 git merge feat/ai-{name} 到 main             │
│           ──→ git worktree remove .worktrees/ai-job-{id}               │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

## 六、协作工作流

### 6.1 主控 Agent 调用流程

```
┌─────────────────────────────────────────────────────────────────┐
│                     主控 Agent 调用流程                          │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  1. 接收用户输入                                                 │
│     ↓                                                           │
│  2. 判断任务类型                                                 │
│     • 是否需要调用 SubAgent？                                    │
│     • 如果需要，是 query 还是 execute？                          │
│     ↓                                                           │
│  3. 构建任务描述                                                 │
│     • 【操作类型】: query/execute                                │
│     • 【用户需求】: ...                                          │
│     • 【目标对象】: ...                                          │
│     ↓                                                           │
│  4. 调用 SubAgent                                                │
│     Task(subagent_type="layout-agent", prompt=任务描述)          │
│     ↓                                                           │
│  5. 接收结果                                                     │
│     ↓                                                           │
│  6. 整合并汇报给用户                                             │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 6.2 任务描述规范

**标准格式**：

```markdown
【操作类型】: {query | execute}
【用户需求】: {用户原始需求的准确描述}
【目标对象】: {目标房间/区域/文件，如果有}
【约束条件】: {特殊要求或限制，如果有}
【期望输出】: {期望 SubAgent 返回什么}
```

**query 任务示例**：

```markdown
【操作类型】: query
【用户需求】: 统计当前项目已布置的模块数量
【目标对象】: schemes/modules.json
【约束条件】: 仅统计，不做任何修改
【期望输出】: 模块数量 + 按类型分布（如果有）
```

**execute 任务示例**：

```markdown
【操作类型】: execute
【用户需求】: 在主卧布置一张双人床
【目标对象】: 房间 rz_3（主卧）
【约束条件】: 床头靠北墙，不阻挡门
【期望输出】: 更新后的 modules.json + 布置说明
```

### 6.3 结果整合规范

**SubAgent 返回格式**：

```markdown
【执行结果】: {成功 | 失败 | 部分成功}
【操作摘要】: {执行了什么操作}
【数据变更】: {修改了哪些文件，如果有}
【详细信息】: {具体数据或说明}
【问题报告】: {遇到的问题，如果有}
```

## 七、提示词设计规范

### 7.1 结构模板

```markdown
---
name: {agent-name}
description: {一句话描述}
tools: {工具列表}
model: {sonnet/opus/haiku}
---

你是 BIMCanvas 的 {agent-name}，{角色定位}。

## 职责
{核心职责列表，3-5 条}

## 操作模式

### query 模式（只读）
{query 模式的行为规范}

### execute 模式（可写）
{execute 模式的行为规范}

## 核心规则
{领域规则，精简版}

## 行为边界
{禁止行为 + 允许行为}

## 输出格式
{输出数据格式说明}
```

### 7.2 长度限制（重要！）

> **已知问题**：SubAgent 提示词过长会导致加载失败。

| 指标 | 建议值 | 说明 |
|------|--------|------|
| **总字符数** | < 3000 字符 | 超过可能导致加载失败 |
| **总行数** | < 150 行 | 便于维护和阅读 |
| **单条规则** | < 50 字符 | 便于 AI 理解 |

**精简策略**：

1. **分离详细规则到知识库**
   ```markdown
   ## 知识库

   知识库路径：`knowledge/placement_guide.md`

   ### 查阅规则
   - 生成任务：必须查阅
   - 编辑任务：简单任务无需查阅
   ```

2. **使用索引而非完整内容**
   ```markdown
   ## 章节索引

   | 需求 | 关注章节 |
   |------|----------|
   | 通道宽度 | 四、尺寸标准 |
   | 家具朝向 | 六、朝向决策 |
   ```

3. **精简规则表达**
   ```markdown
   # 冗长版（避免）
   当用户请求布置家具时，需要确保大型家具如床、衣柜、沙发等尽量靠墙放置

   # 精简版（推荐）
   - 大型家具靠墙（床、衣柜、沙发）
   ```

### 7.4 常见陷阱

| 陷阱 | 问题 | 解决方案 |
|------|------|----------|
| **缺少操作模式** | Agent 不知道是否可以写入 | 明确定义 query/execute 模式 |
| **工作流以写入结尾** | 默认所有任务都要写入 | 区分 query 和 execute 工作流 |
| **缺少禁止行为** | Agent 过度主动 | 明确列出禁止行为 |
| **提示词过长** | 加载失败 | 精简 + 知识库分离 |
| **规则过于笼统** | Agent 自由发挥过度 | 具体化规则，给出示例 |

### 7.3 关键要素清单

| 要素 | 重要性 | 说明 |
|------|--------|------|
| 操作模式定义 | ⭐⭐⭐ | 必须区分 query/execute |
| 行为边界 | ⭐⭐⭐ | 明确禁止和允许的行为 |
| 工作流程 | ⭐⭐ | 步骤化的执行流程 |
| 输出格式 | ⭐⭐ | 数据格式规范 |
| 知识库引用 | ⭐ | 详细规则外置 |

## 九、工具体系

### 9.1 数据读取工具

| 工具 | 功能 | 说明 |
|------|------|------|
| `read_room_zones` | 读取 Room Zone | 读取 `computed/room_zones.json` |
| `read_openings` | 读取门窗数据 | 读取 `baseline/openings.json` |

## 十一、AI 作为 OBB 规划师

> AI 只操作「方向包围盒」(Oriented Bounding Box)，不处理复杂几何。

```
AI 视角：
┌─────────────┐
│   bounds    │  ← AI 操作的是矩形包围盒
│  [4 顶点]   │
│   facing    │  ← 语义朝向（north/south/east/west）
└─────────────┘

Core 层：
bounds + facing → 精确几何位置 + 旋转角度
```

**布置约束**：

```
对于每个要放置的模块：
1. bounds 必须完全在 zone.innerBoundary 内
2. bounds 不能与任何 exclusionAreas 重叠
3. bounds 不能与其他已放置 modules 重叠
```

## 十二、经验教训

### 12.1 问题 1：SubAgent 在查询任务中修改数据

**问题描述**：用户问"有多少模块"，layout-agent 发现 modules.json 是空数组后，自作主张写入了家具数据。

**根因分析**：
1. 主控 Agent 没有明确指定操作类型
2. SubAgent 提示词缺少 query 模式定义
3. SubAgent 工作流默认以 Write 结尾

**解决方案**：
- 主控 Agent 调用时必须指定操作类型
- SubAgent 提示词定义 query/execute 两种模式
- query 模式禁止使用 Write/Edit 工具

### 12.2 问题 2：SubAgent 在空数据中产生幻觉

**问题描述**：用户查询"有多少模块"，modules.json 实际为空数组，但 Agent 返回了虚假的"18 个模块"结果。

**根因分析**：
1. Agent 读取 room_zones.json 看到有 6 个房间
2. Agent 根据房间类型"推断"应该有什么家具
3. 编造了一个看似合理但完全虚假的结果

**解决方案**：
- 添加"数据真实性约束"：输出必须严格基于实际读取的文件内容
- 明确"空数据处理规则"：空数据时必须报告"数量为 0"，禁止推断
- 添加"输出验证"步骤：报告前验证内容与文件实际一致
- 在禁止行为中明确：禁止根据其他文件推断不存在的数据

### 12.3 问题 3：SubAgent 提示词过长导致加载失败

**问题描述**：SubAgent 提示词文本过长时，会导致 SubAgent 加载失败。

**解决方案**：
- 提示词控制在 3000 字符以内
- 详细规则外置到知识库
- 使用索引引用而非完整内容

### 12.4 问题 4：SubAgent 过度主动

**问题描述**：SubAgent 在发现"问题"时，自作主张地"帮助"用户解决，违背用户原始意图。

**解决方案**：
- 明确列出禁止行为
- 强调"宁可少做，不可多做"原则
- 发现问题时报告而非自动解决

### 12.5 最佳实践

**提示词模块化**：

```
提示词核心（< 3000 字符）
├── 角色定义
├── 操作模式
├── 行为边界
└── 知识库引用

知识库（详细规则）
├── 布置规则
├── 尺寸标准
└── 常见错误
```

**防御性设计**：

```markdown
## 执行前检查

在执行任何操作前，确认：
1. 操作类型是否为 execute？（query 禁止修改）
2. 操作是否在任务描述范围内？
3. 是否有明确的用户授权？

如果任何一项不满足，停止执行并报告。
```
