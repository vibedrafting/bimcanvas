# Agent 提示词设计哲学

> 本文档记录 BIMCanvas Agent 提示词体系的设计理念与演进方向。
> 面向读者：接手本项目提示词调优工作的 AI assistant。
> 关联文档：规则体系地图 `.claude/skills/rule-tuning/references/rule-system-map.md`

---

## §1 提示词如何影响 AI

提示词不是"命令"，而是**上下文构建**——它决定 AI 在生成回答时站在什么立场、带着什么约束、用什么思维框架工作。

### 三层影响机制

**注意力引导** — 决定 AI "看向哪里"

提示词中提到的概念和关键词会在 AI 的知识空间中激活相关区域。说"主卧布置"，AI 就聚焦在卧室设计知识上；说"L 形空间"，AI 就开始考虑异形空间处理。**你提到什么，AI 就重视什么。**

**约束空间** — 决定 AI "不做什么"

好的提示词不只告诉 AI 该做什么，更重要的是划定边界。明确的禁止项（如"禁止编造 module_library 中不存在的家具"）比十条正面指令更能防止 AI 犯错。

**角色与标准设定** — 决定 AI "以什么水准工作"

"放个床"和"作为资深室内设计师，在满足人体工学和动线流畅性的前提下布置睡眠区"——同一个任务，不同的角色设定会导致截然不同的输出质量。

### 正面作用与反面作用

| 正面 | 反面 |
|------|------|
| 减少歧义——明确约束让 AI 不用猜测意图 | 过度约束——规则太多互相矛盾，AI 被迫妥协 |
| 提升一致性——规范和模板让输出风格统一 | 注意力稀释——提示词太长，关键信息被噪音淹没 |
| 激发深度——引导性描述让 AI 探索更深层解法 | 虚假确定性——指令过于具体，AI 不敢偏离低效路径 |
| 防止遗漏——检查清单确保全面覆盖 | 角色污染——不当角色设定导致 AI 过度自信 |

**核心认知：提示词越多不代表越好。每条规则都有认知成本——AI 需要在所有规则中分配注意力，规则越多，每条规则分到的注意力越少。**

## §2 提示词设计六原则

### 原则 1：结构化分层，而非平铺直叙

```
# 错误：一大段文字混合目标、约束、步骤
# 正确：分层组织
  第一层：角色和目标（你是谁，要做什么）
  第二层：约束和规范（不能做什么，标准是什么）
  第三层：具体指令（步骤、模板、示例）
```

AI 处理结构化信息的效率远高于连续文本。章节标题、表格、层级列表都能帮助 AI 快速定位相关规则。

### 原则 2：用示例代替描述

```
# 弱：请用简洁专业的语言描述布置方案
# 强：参考示例——"床头靠北墙居中，两侧各留 500mm 放置床头柜，衣柜沿东墙填满 2400mm 有效段"
```

AI 从一个具体示例中提取到的模式，远比十句抽象描述更精确。在 BIMCanvas 项目中，`module_library.json` 的 `relation_rules` 如果能配合一个"好的布置 JSON 片段"作为示例，效果会显著提升。

### 原则 3："不要做什么"比"要做什么"更重要

AI 的默认行为是"尽可能多做"——加功能、加容错、加优化。明确的禁止项能精准修剪不需要的行为。

在 BIMCanvas 中的体现：`BIMCANVAS.md` 的禁止事项（禁止编造家具、禁止凭猜测修改）比正面指令更有效地防止了 Agent 的过度行为。

### 原则 4：提供"为什么"，而不只是"是什么"

```
# 弱："衣柜应填满有效段全长"
# 强："衣柜应填满有效段全长——连续柜面比碎片化布置视觉更整洁，且最大化收纳效率"
```

当 AI 理解规则背后的原因，它就能在**规则未覆盖的边界场景**中做出合理推断。没有理由的规则只能被机械执行；有理由的规则能被灵活应用。

### 原则 5：渐进式信任，而非一次性全托

分阶段给 AI 放权——先做方案让人审核，再逐步扩大自主权。BIMCanvas 的"阶段 A → 验证 → 阶段 B"就是这种模式的实践：不是让 AI 一次布完所有家具，而是分阶段布置、分阶段验证。

### 原则 6：保持信噪比

每条规则都应该问：**去掉这条，AI 的行为会变差吗？** 如果不会，就删掉。冗余规则不是无害的——它们占用 AI 的注意力配额，稀释真正重要的规则的权重。

## §3 BIMCanvas Agent 提示词体系

### 三文件架构

```
BIMCANVAS.md (系统身份 + 执行规范)
       │
       ↓ 自动加载
generate-workflow/SKILL.md (执行流程 + 检查清单)
       │
       ├─ 参考 → placement_guide.md (设计知识库)
       │           提供：通道标准、房间布局规范、朝向逻辑、设计原则
       │
       └─ 查询 → module_library.json (模块行为规则)
                   提供：家具尺寸、topology_rules、relation_rules
```

### 各文件职责边界

#### SKILL.md — 流程卡（管"做事的顺序"）

| 应该有 | 不应该有 |
|--------|----------|
| 步骤序列（截图 → 读数据 → 分析 → 放置 → 验证） | 具体设计规范数值（如"窗侧 200mm"） |
| 入口/出口条件（"阶段 A 前必须完成…"） | 详细的评估方法论（如"怎么计算有效段"） |
| 检查清单（H/S 项：逐项确认） | 房间类型的设计经验 |
| 常见误判提醒（已知陷阱） | |

**类比**：施工流程卡——"第 3 步：检查墙面平整度"，但不写"平整度标准是多少"。

#### placement_guide.md — 规范手册（管"做事的标准"）

| 应该有 | 不应该有 |
|--------|----------|
| 通用设计原则（靠墙、顶角、异形利用） | 具体模块的尺寸约束 |
| 房间类型布局规范（主卧/次卧/客厅各怎么布） | 工作流执行步骤 |
| 间距/通道标准值及适用场景 | |
| 整体布局方法论（衣柜选墙、床定位） | |

**类比**：室内设计规范手册——"主卧衣柜应选有效段最长的墙面"。

#### module_library.json — 产品说明书（管"每个零件的规格"）

| 应该有 | 不应该有 |
|--------|----------|
| 模块尺寸 / 参数化约束（size, morphology.limits） | 房间整体布局策略 |
| 放置规则（topology_rules: 靠墙、避门） | 工作流步骤 |
| 模块间关系（relation_rules: 衣柜选墙、组合关系） | |

**类比**：产品安装说明书——"1500 柜体：靠墙放置，选非床头墙最长有效段"。

### 数据流：规则如何流入 Agent 决策

```
用户请求 "布置次卧"
  │
  ▼
MainAgent 加载 generate-workflow SKILL.md
  │  ← 定义执行步骤、预检规则、检查清单
  ▼
步骤 2: 读取 placement_guide.md
  │  ← 通道标准、房间布置要点、朝向逻辑
  ▼
步骤 4: 读取 module_library.json
  │  ← 家具尺寸 + topology_rules + relation_rules
  ▼
步骤 6A: 综合三者做出布置决策
  │  → placement_guide 提供标准值和设计原则
  │  → relation_rules 提供模块特定约束
  │  → SKILL.md 提供预检规则和误判提示
  ▼
写入 → validate_layout → 截图审查(检查清单)
```

## §4 核心矛盾：规则合规性 vs 设计创造力

### 当前体系特征

BIMCanvas Agent 的提示词体系具有 **重规则、强流程、弱原理** 的特征：

- **规则丰富**：placement_guide 覆盖了主卧、次卧、客厅等各类房间的布置细节
- **流程严格**：SKILL.md 定义了线性阻塞的工作流，每步都有入口条件
- **原理稀薄**：规则大多是结论式的（"应该这样做"），较少解释设计逻辑（"因为这样做能达到什么效果"）

这种特征的结果是：**AI 能可靠地生成"不犯错"的布置方案，但难以生成"有设计感"的方案。**

### 为什么"更多规则"不等于"更好的设计"

人类设计师的工作方式不是查规则表——他们内化了设计原理，在具体场景中**推导**出合理方案。一个优秀设计师面对 L 形房间时，不会去翻"L 形房间规则"，而是基于"空间流动感"和"视觉均衡"这些原理，创造性地利用异形空间。

AI 也可以做到这一点——前提是提示词给它提供了原理层面的认知，而不仅仅是规则层面的指令。

**交通法规的比喻**：

当前体系像交通法规——红灯停绿灯行、限速 60、禁止掉头。能保证 AI 不出事故（布置不出错），但开出来的路线是机械的。要让 AI 像老司机一样开车，需要在法规之上加"驾驶美学"——什么时候加速、什么时候缓行。而这一层不是靠更多规则实现的，是靠让 AI 理解目的地、路况和乘客感受来实现的。

## §5 三个演进方向

### 方向一：原理层 — 让 AI 理解"为什么"

**目标**：从"规则驱动"转向"原理 + 规则"双层结构。

**主战场**：`placement_guide.md`

当前状态：规则丰富但多为结论式（"衣柜填满有效段"）。
演进目标：为关键规则补充设计原理，形成"原理 → 规则"的推导链。

```
当前：靠墙放置（原则） → 衣柜选最长有效段（规则）
目标：靠墙放置（原则） → 连续柜面视觉整洁 + 最大化收纳（原理） → 衣柜选最长有效段（规则）
```

**在三个文件中的落地**：

| 文件 | 做什么 | 不做什么 |
|------|--------|----------|
| `placement_guide.md` | 为关键规则补充设计原理（"因为……所以……"） | 不是写论文，1-2 句话点明即可 |
| `module_library.json` | relation_rules 中逻辑不自明时加一句原因说明 | 不重复 guide 中已有的原理 |
| `SKILL.md` | 不涉及，保持纯流程 | — |

**价值**：当 AI 遇到规则未覆盖的场景时，能从原理出发推导合理决策，而不是僵硬套用最接近的规则。

### 方向二：自由度分层 — 让 AI 知道"哪里可以发挥"

**目标**：明确区分约束强度，释放设计创造力。

当前问题：所有规则的语气都差不多强硬，AI 不敢偏离任何一条。

**三层约束模型**：

| 层级 | 性质 | 示例 | AI 行为 |
|------|------|------|---------|
| **不可违反** | 功能 / 安全 | 门开启不被阻挡、主通道 ≥ 900mm | 必须满足，无例外 |
| **强烈建议** | 设计规范 | 床头靠实墙、衣柜填满有效段 | 默认遵守，可在说明理由后偏离 |
| **设计自由度** | 审美 / 偏好 | 间距分配比例、辅助家具位置 | 鼓励 AI 自主决策 |

**在三个文件中的落地**：

| 文件 | 做什么 |
|------|--------|
| `placement_guide.md` | 对每条规范标注约束层级 |
| `module_library.json` | topology_rules = 不可违反；relation_rules 中区分"必须"和"建议" |
| `SKILL.md` | 检查清单中明确：H 项必须通过，S 项允许 AI 说明理由后偏离 |

**价值**：AI 知道在哪里必须严格遵守，在哪里可以展现设计直觉。人类设计师的"好品味"恰恰体现在没有硬性规则的地方。

### 方向三：目标评估 — 让 AI 判断"做得好不好"

**目标**：从"检查对不对"升级到"评估好不好"。

当前状态：检查清单只验证合规性（"有没有阻挡门开启"），缺少设计品质评估。

**新增评估维度（示意）**：

| 维度 | 评估内容 |
|------|---------|
| 空间流动感 | 动线是否自然？有没有需要侧身的路径？ |
| 视觉均衡 | 家具视觉重量是否平衡？有没有一侧拥挤另一侧空旷？ |
| 功能舒适度 | 日常动作（起床、开柜、坐下）是否都有充足空间？ |

**在两个文件中的落地**（module_library 不参与）：

| 文件 | 做什么 |
|------|--------|
| `placement_guide.md` | 新增"设计品质评估维度"章节，定义评估标准 |
| `SKILL.md` | 在截图审查步骤中引用评估维度，作为 H/S 清单的补充 |

**价值**：让 AI 能区分"合格的布置"和"优秀的设计"，从被动合规走向主动追求品质。

### 三个方向的关系

三个方向不互斥，而是互补的：

```
原理层 → AI 能理解"为什么"→ 面对新场景能推导
         ↓
自由度分层 → AI 知道"哪里可以发挥"→ 在自由区域展现创造力
         ↓
目标评估 → AI 能判断"好不好"→ 自主迭代提升品质
```

## §6 实操指南：调优提示词时的检查清单

### 新增一条规则前，问自己

1. **这条规则解决的是已发生的问题，还是假想的问题？** 只为实际出现的 Agent 错误行为增加规则。
2. **这条规则放在哪个文件？** 按职责边界放置——流程规则 → SKILL.md，设计标准 → placement_guide，模块行为 → module_library。
3. **去掉这条规则，AI 会犯错吗？** 如果不会，不要加。每条规则都有认知成本。
4. **这条规则和现有规则有冲突吗？** 检查是否与其他规则矛盾。矛盾的规则比没有规则更糟——AI 会在矛盾中随机选择。
5. **这条规则需要解释原因吗？** 如果规则的逻辑不自明，加一句"因为……"。

### 修改规则时的注意事项

- **改规则前先理解 Agent 的决策链**：读日志，追踪 Agent 实际读取了哪些规则、做了什么推理。问题可能不在规则本身，而在 Agent 对规则的理解。
- **优先修改 placement_guide**：它是 Agent 的"设计知识库"，影响面最广。module_library 的修改只影响单个模块。
- **避免在 SKILL.md 中硬编码设计知识**：如果发现自己在 SKILL.md 中写具体数值（如"窗侧 200mm"），说明这条规则应该放在 placement_guide 里。
- **一次只改一个变量**：修改一条规则后测试效果，确认有效再改下一条。同时改多条规则无法判断是哪条起了作用。

### 常见反模式

| 反模式 | 表现 | 正确做法 |
|--------|------|---------|
| **规则叠加** | 为了修复 A 问题加了规则 X，X 导致 B 问题又加规则 Y | 找到根因，用一条精准规则解决 |
| **职责越界** | SKILL.md 中写了具体设计标准 | 拆到 placement_guide 中，SKILL.md 只引用 |
| **面面俱到** | 试图用规则覆盖每一种可能场景 | 提供原理让 AI 自行推导边界场景 |
| **语气一致** | 所有规则都用"必须""禁止"语气 | 区分约束层级，建议性规则用"建议""优先" |
| **重复表述** | 同一条规则在多个文件中重复出现 | 一处定义，其他处引用 |
