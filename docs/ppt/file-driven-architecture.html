.bcp 项目格式

.bcp 是项目的标准交换格式，本质是包含标准目录结构的 ZIP 文件。上传后解压为项目目录，即刻成为 Git 仓库。

project.bcp (ZIP) ├── project.json 项目元数据 + 方案列表 │ ├── baseline/ 建筑基础数据（只读 ← Revit 导出） │ ├── metadata.json 坐标转换参数 │ ├── architecture.json 墙体 + 柱子轮廓多边形 │ ├── openings.json 门窗位置 + 开启方向 │ ├── rooms.json 房间边界 + 类型 │ └── location_lines.json 完成面定位线 │ ├── computed/ 计算派生数据（Server 自动生成） │ ├── room_zones.json 房间 → 可设计区域 + innerBoundary │ └── exclusions.json 门扇扫过区域 → 矩形禁区 │ ├── schemes/ 方案设计数据（AI / Web 可读写） │ ├── strategy.json 策略元数据（权重、约束、提示） │ ├── zones.json 设计区域划分 │ ├── finishes.json 完成面定义 │ └── {zoneId}/ │ └── modules.json ★ 家具模块布置 ← Agent 核心输出 │ ├── context/ 用户需求描述 ├── knowledge/ 设计原则 └── modules/ 模块素材库 + SVG 资源

多策略通过 Git 分支隔离，而非 schemes/ 子目录。每个分支的 schemes/ 目录结构相同。

05 / 15

三条核心数据流

1
用户编辑流 — Web → Server → File
用户在 Web 画布上拖动家具 → canvasStore 更新内存状态 → endBatchUpdate() 触发 → REST API POST /api/project/save → Server 写入 schemes/{zoneId}/modules.json → FileWatcher 检测到变化 → SignalR 广播给其他客户端。

关键机制：批量更新模式（拖动过程不逐帧保存）、脏数据追踪（isDirty）、磁盘即时同步。
2
文件同步流 — File → Server → Web
Agent 直接写入 modules.json（或用户用 VS Code 编辑）→ FileSystemWatcher 检测变化 → 500ms 防抖 → 检查 Git 操作锁 → BroadcastUpdate() → SignalR 推送 ReceiveUpdate → Web 端 syncFromServer() 重新加载并渲染。

关键机制：500ms 防抖（避免连续写入的中间状态）、Git 感知（Git 操作期间跳过广播）、历史栈保留（Agent 修改可 Ctrl+Z 撤回）。
3
项目加载流 — File → Server → Web
用户上传 .bcp 文件 → Server 解压到项目目录 → 初始化 Git 仓库 → 计算 computed 层（room_zones + exclusions）→ REST API 返回完整 ProjectData → Web 端 loadProject() 一次性加载全部数据。

关键机制：ChangeSource 标记为 UserUpload（清空历史栈）、Computed 层按需重建。

Server = 文件播放器

Server 不"拥有"数据。它读取文件、聚合、分发——任何外部进程修改了文件，系统自动感知并同步。

┌─────────────────────────────────────────────────────────────────┐ │ Server 核心组件 │ ├─────────────────────────────────────────────────────────────────┤ │ │ │ ProjectContext 项目上下文（单项目模式） │ │ ├── CurrentProjectPath 当前项目路径 │ │ └── IsGitOperationInProgress Git 操作锁 🔒 │ │ │ │ ProjectWatcherService 文件监听服务 │ │ ├── FileSystemWatcher 监听 schemes/*.json │ │ ├── 500ms 防抖 避免连续写入的中间状态广播 │ │ └── Git 感知 Git 操作期间跳过文件变化事件 │ │ │ │ CanvasHub (SignalR) 实时通信中枢 │ │ ├── ReceiveUpdate Server → Web（文件变化通知） │ │ └── ReceiveGhostPatch Server → Web（Agent 实时预览） │ │ │ │ ProjectController (REST) 项目管理接口 │ │ ├── GET /api/project 读取完整项目数据 │ │ ├── POST /api/project/upload 上传 .bcp 文件 │ │ └── POST /api/project/save 保存 modules │ │ │ └─────────────────────────────────────────────────────────────────┘
防抖机制 (500ms)
Agent 短时间内连续写入多个文件时，只在最后一次写入后 500ms 才触发同步广播，避免 Web 端收到中间状态。
Git 感知机制
Git checkout/merge 操作同时修改多个文件。设置 IsGitOperationInProgress=true 阻止 FileWatcher 触发更新，操作完成后手动调用 loadProject()。
07 / 15

五大典型数据流场景

A
Web 端拖动模块
DragManager.onMouseUp() → beginBatchUpdate() → updateModule()（多次，不触发保存）→ endBatchUpdate() → saveToServer() → Server 写入文件
价值：Web 是文件系统的可视化编辑器。拖动结束才一次性写入，不污染历史栈。
B
Agent 修改布置
Agent 直接写 modules.json → FileWatcher → 500ms 防抖 → SignalR ReceiveUpdate → Web syncFromServer()
价值：历史栈保留（标记为 AgentModify），用户可用 Ctrl+Z 撤回 Agent 的修改！
C
外部编辑器修改 JSON
用户在 VS Code 中编辑 modules.json 修改坐标并保存 → FileWatcher 检测 → Server 重新解析 → SignalR 广播 → Web 端动画过渡到新位置
价值：实现"热重载"般的开发体验。但外部修改会触发 Undo 栈清空（外部干扰规则）。
D
Git 分支切换
IsGitOperationInProgress = true → 执行 git checkout → 多文件同时变化，FileWatcher 全部跳过 → 操作完成 → loadProject(GitCheckout) → 清空历史栈，保持视图
价值：分支切换 = 方案切换。Git 操作锁防止中间状态广播。
E
上传新项目
POST .bcp → 解压 → Git init → 计算 computed → 返回 ProjectData → loadProject(UserUpload) → 清空历史栈
价值：新项目从零开始，旧历史不干扰。

变更源追踪 + Undo/Redo

不同场景需要不同的历史管理策略。ChangeSource 枚举标记每次变更的来源，驱动策略分支。

ChangeSource典型触发清空历史保留历史保持视图
SystemInit系统启动✅❌❌
UserUpload上传新项目✅❌❌
GitCheckout切换分支✅❌✅
GitDiscard放弃修改✅❌✅
AgentModifyAI 修改家具❌✅✅
ServerSync文件同步推送❌✅✅
UserEdit用户编辑❌✅—

Undo/Redo 机制
  • 用户移动 A→B → Server 记录逆向操作入栈
  • 点击 Undo → 执行逆向操作 → 写入文件
  • Undo 本质是"逆向写入文件"，不是内存回滚
    • ⚠
    外部干扰规则
  • 检测到非 Web 端发起的文件变更（VS Code 手动编辑）
  • 立即清空 Undo 栈
  • 原因：外部修改切断了 Undo 链条，强行回滚会导致状态不一致
  • Agent 修改不触发（标记为 AgentModify，保留历史）

    持久化双层策略

    "磁盘即时同步 + Git 周期存档"——既保证实时一致性，又提供完整版本历史。

    第一层：磁盘即时同步
    触发：用户交互结束时（MouseUp）
    动作：立即写入 JSON 文件
    效果：VS Code 等工具能实时看到修改
    去抖动：禁用。采用阻塞式立即写入，确保文件与内存毫秒级一致
    第二层：Git 版本存档
    触发：显式保存 / 自动存档时机
    动作：git add . && git commit
    效果：生成 Git 历史节点，支持版本回溯
    自动存档时机：创建 Worktree 前、阶段性成果完成后
    # 文件驱动 + Git 版本控制的完整闭环 用户拖动家具 │ ▼ 第一层：MouseUp → 立即写入 modules.json ← 毫秒级同步 │ │ VS Code 实时可见 ✓ │ FileWatcher 感知 ✓ │ Web 端同步 ✓ │ ▼ 第二层：git add . && git commit ← 周期性存档 │ │ 版本回溯 ✓ │ 分支对比 ✓ │ 方案合并 ✓ │ ▼ Git Worktree：多方案并行隔离 ← Agent 并行工作

    深度集成 Git：为什么？

    文件驱动解决了"数据放哪"，但没解决三个关键问题：
    AI 写坏了怎么办？多个 AI 同时写怎么办？多方案怎么管？

    🛡
    问题 1：AI 写坏了怎么办？
    AI 直接写文件 = 直接修改生产数据。
    没有隔离机制，一次失误就污染用户当前方案。

    Git 方案：Worktree 隔离 — AI 永远在"草稿纸"上工作，
    用户审查后才合并到"正式稿"。
    ⚡
    问题 2：多 AI 并发写怎么办？
    3 个 AI 同时生成方案，共用一个文件夹？
    文件会互相覆盖，状态混乱。

    Git 方案：每个 AI 一个 Worktree — 物理隔离的目录，
    共享 .git 历史，互不干扰。
    🔀
    问题 3：多方案怎么管理？
    用户想要"极致收纳"和"动线优先"两套方案并存。
    复制文件夹？命名 v1、v2、v3？

    Git 方案：分支 = 方案 — 天然的版本管理，
    diff 对比、merge 合并、log 追溯，全部开箱即用。

    核心洞察

    文件驱动 + Git 不是两个独立设计，而是同一个架构哲学的两面：
    文件是数据载体，Git 是操作协议。选择文件驱动的那一刻，就天然获得了 Git 的全部能力。

    Git Worktree：平行宇宙引擎

    传统认知：1 个 Git 仓库 = 1 个文件夹 = 1 个当前分支
    实际上：1 个 Git 仓库 = N 个文件夹 = N 个并行分支

    # Git Worktree 物理结构 项目根目录/ ← 主仓库（真窗口） ├── .git/ ← 共享的 Git 历史（只有这一份） ├── baseline/ schemes/ computed/ ← 当前分支的文件 │ └── .worktrees/ ← 平行宇宙入口 │ ├── ai-job-storage/ ← AI-1 的隔离环境 │ ├── .git → ../../.git ← 符号链接，共享历史 │ ├── baseline/ ← 继承主仓库的基础数据 │ └── schemes/ ← AI-1 独立修改，不影响其他人 │ ├── ai-job-flow/ ← AI-2 的隔离环境 │ └── schemes/ ← AI-2 独立修改 │ └── window-2/ ← 用户虚拟窗口 └── schemes/ ← 用户在另一个方案上编辑
    空间高效
    .git 历史只存一份（通常占项目 80% 体积）。
    Worktree 只包含工作文件的副本，创建和销毁都是毫秒级。
    完全隔离
    每个 Worktree 是独立的物理目录，文件系统级别隔离。
    AI-1 写文件不会影响 AI-2，也不会影响用户的主目录。
    合并便捷
    共享同一个 .git 历史，分支之间可以直接 merge/diff。
    不需要复制文件、不需要"另存为"，Git 原生支持。

    Agent Git 工作流：只需两个工具

    设计原则：Agent 只做决策，Server 处理复杂性。
    Agent 只需 2 个 MCP 工具，所有 Git 细节由 Server 内部完成。

    # Agent 视角：极简的工作流 用户："给客厅出三个方案" │ ▼ MainAgent 解析意图，规划 3 个并行任务 │ ├─── ai_job_create("storage") ──→ Server 内部自动完成： │ │ 1. 获取当前分支 │ │ 2. 检测未提交更改 → 自动存档 │ │ 3. 创建临时分支 + Worktree │ ▼ │ 返回 { worktreePath, branchName } │ │ │ ▼ │ SubAgent 在 worktreePath 中工作 │ 读取数据 → 布置决策 → 写入 JSON │ ├─── ai_job_create("flow") ──→ 同上，并行执行 │ ▼ │ SubAgent 独立工作... │ └─── ai_job_create("minimal") ──→ 同上，并行执行 ▼ SubAgent 独立工作... # 所有 SubAgent 完成后 │ ▼ ai_job_complete(["storage", "flow", "minimal"]) │ │ Server 内部：git add . && git commit（每个 Worktree） │ Server 通知 Web 端：3 个方案已就绪 │ ▼ Web 端展示三联屏 → 用户选择合并/丢弃 ← Agent 不参与
    MCP 工具调用时机Server 内部动作
    ai_job_createexecute 任务开始时自动存档 → 创建分支 → 创建 Worktree
    ai_job_completeSubAgent 完成后git commit → 通知 Web 展示 diff

    Agent 不负责的操作：获取当前分支（Server 自动获取）、自动存档（Server 自动执行）、合并/清理（用户通过 Web UI 决定）。
    用户始终拥有最终决策权。

    七大 Git 业务场景

    Git 操作不是技术细节，而是业务能力。每个场景都对应用户的真实需求。

    1
    Query 只读查询
    "主卧有多少家具？"
    无 Git 操作 — Agent 直接读取当前目录文件
    2
    简单编辑
    "把床向右移 50cm"
    ai_job_create → 编辑 → ai_job_complete → 用户审查合并
    3
    策略分叉（多方案）
    "出三个方案"
    并行创建 3 个 ai_job → 3 个 SubAgent 隔离工作 → 三联屏对比
    4
    布局求解器
    "能塞进浴缸和淋浴房吗？"
    沙盒模式迭代尝试，只有成功方案才提交，99 次失败对用户透明
    5
    主编式合并
    用户在三联屏勾选：A 方案的客厅 + B 方案的主卧
    cherry-pick-regions — JSON 级别的区域合并
    6
    多窗口独立任务
    3 个窗口操作不同策略，各自独立
    每个窗口 = 一个 Worktree，Agent 不需要知道自己在哪个窗口
    7
    虚拟窗口关闭
    检测未合并更改 → 有更改？弹窗确认 → [合并后关闭] [丢弃并关闭] [取消] → 清理 Worktree + 更新 UI

    真窗口 vs 虚拟窗口： 真窗口操作主仓库目录，可自由切换分支；虚拟窗口操作 Worktree，绑定固定分支。 Agent 不需要区分 — Server 已设置好工作目录上下文，ai_job_create 不传 baseBranch 时自动获取。
