## 1. 产品概述

### 1.1 一句话定位

**基于 AI CLI 的室内装修平面方案设计助手，通过结构化 JSON 数据实现 Revit 与 AI 的协作，在 Web 画布上进行人机交互设计。**

### 1.2 核心要素

| 要素 | 角色 | 说明 |
|------|------|------|
| **AI CLI 工具** | 整个项目的运行依赖 | 使用 Claude Code 作为 AI 交互入口 |
| **JSON 数据模型** | Revit ↔ AI 的数据桥梁 | 结构化、AI 可读写的格式 |
| **Web 画布** | 人机协作界面 | AI 呈现方案，用户实时编辑/批注 |
| **模块库（族库）** | AI 设计的素材来源 | 提供真实家具数据和对应的 Revit 模型 |
| **MCP 工具** | AI 的能力扩展 | 让 AI 能够感知和操作画布、族库 |

### 1.3 解决的核心问题

| 问题 | 现状 | BIMCanvas 解决方案 |
|------|------|---------------------|
| AI 理解门槛高 | Revit 原生格式复杂，AI 难以直接读写 | JSON 是结构清晰的文本格式，AI 可直接理解 |
| AI 设计是"空想" | AI 输出的家具名称无法对应真实产品 | 模块库提供真实家具 + 对应 Revit 模型 |
| 设计迭代效率低 | 每次修改都需要打开 Revit 操作 | Web 画布实现实时协作编辑 |
| 设计与建模耦合 | 创意构思和专业建模混在一起 | 先在画布设计，确认后再同步到 Revit |

## 2. 目标用户

### 2.1 主要用户画像

**室内设计师**
- 具备专业设计能力
- 使用 Revit 进行建模
- 需要快速出方案与客户沟通
- 希望 AI 辅助完成重复性布局工作

### 2.2 用户痛点

1. Revit 操作复杂，学习曲线陡峭
2. 设计迭代周期长，修改成本高
3. AI 工具无法直接理解和操作 BIM 模型
4. 创意构思阶段被软件操作困住

## 3. 核心工作流

### 3.1 用户工作流

> **MVP 版本**：快速验证核心价值，AI 直出方案，对话调整。

#### 第一步：准备阶段

1. 打开 Revit，激活平面视图
2. 点击"开始设计"按钮
3. 系统自动识别墙体、门窗等建筑元素
4. Web 端显示户型底图

**启动方式**：
- **快速启动**：一键提取建筑信息 → 填写设计需求 → 开始设计
- **对话模式**：通过对话逐步引导 AI，灵活配置

---

#### 第二步：确认空间

5. AI 根据 Revit 房间名称自动识别空间类型（客厅、卧室等）
6. Web 端显示房间功能标签
7. 用户确认或手动调整房间功能

---

#### 第三步：AI 自动设计

8. AI 根据需求和空间约束自动布置家具
   - 家具放置在可用空间内
   - 避开门扇活动区域
   - 不与其他家具重叠
9. Web 端实时显示完整布置方案

---

#### 第四步：交互调整

10. 用户可以：
    - 在 Web 端拖拽调整家具位置
    - 通过对话指导 AI 修改（如"把床转90度"）
11. 循环迭代直到满意

---

#### 第五步：应用到 Revit

12. 确认最终方案
13. AI 自动加载家具模型并同步到 Revit
14. Revit 中显示完整的布置结果

---

### 3.2 两种启动方式详解

#### 方式一：快速布置（一键启动）

```
用户点击 Revit Ribbon「快速布置」按钮
    │
    ▼
┌─────────────────────────────┐
│   步骤1: 自动提取           │
│   • 获取当前视图范围         │
│   • 提取墙/门/窗/柱元素      │
│   • 转换为结构化数据        │
└──────────────┬──────────────┘
               │
               ▼
┌─────────────────────────────┐
│   步骤2: 弹出配置窗口        │
│   • 设计诉求输入框           │
│   • 项目配置选择列表         │
│     - 设计风格              │
│     - 空间类型              │
│     - 预算范围              │
│     - 家庭成员              │
│   • 确认/取消按钮           │
└──────────────┬──────────────┘
               │ 用户点击确认
               ▼
┌─────────────────────────────┐
│   步骤3: 启动 AI CLI        │
│   • 启动 Claude Code        │
│   • 传入: 数据文件路径      │

└─────────────────────────────┘
```

**适用场景**：用户已有明确的原建筑，想快速开始设计

---

#### 方式二：开启对话（手动引导）

```
用户点击 Revit Ribbon「开启对话」按钮
    │
    ▼
┌─────────────────────────────┐
│   直接启动 Claude Code      │
│   • 用户通过对话引导 AI      │
│   • 逐步触发 MCP 工具        │
│   • 灵活填写项目配置         │
└─────────────────────────────┘
```

**适用场景**：用户需要更灵活的交互，或没有现成的 Revit 原建筑

## 4. 系统架构

### 4.1 架构总览

详细架构设计见 [Architecture.md](./Architecture.md)。

**核心设计决策**：

| 决策点 | 选择 | 理由 |
|--------|------|------|
| **数据核心** | JSON 文件 + .bcp 包 | Token 效率高，AI 理解好，易于版本控制 |
| **数据架构** | File-Driven Architecture | 文件为单一真理源，Server 作为"播放器" |
| **视图渲染** | SVG | 矢量图形，浏览器原生支持 |
| AI 入口 | Claude Code | 已有成熟工具，直接复用 |
| 画布载体 | Web 页面 | 跨平台、交互库丰富 |
| 同步机制 | WebSocket | AI 每次操作用户立即可见 |

### 4.2 File-Driven Architecture

> 详见 [Architecture.md §2 文件驱动架构](./Architecture.md#2-文件驱动架构-file-driven-architecture)

**核心理念**：文件是唯一真理源，Server 是"文件播放器"而非"内存数据库"。

### 4.3 OBB 规划师设计约束

> **AI = OBB 规划师**：AI 只操作矩形包围盒 (OBB)，不计算精确几何。

| 原则 | 说明 |
|------|------|
| **AI 决策位置** | AI 输出 `center + size + facing`，Core 负责转换为精确几何 |
| **Polygon2D 是真理** | JSON 存储精确几何，AABB 仅作运行时优化 |
| **多样化交互** | AI 可用 Semantic / Vec2D / Polygon2D 任意格式输出 |

**设计理由**：
- 降低 AI 的几何计算负担
- 让 AI 专注于设计决策而非数学运算
- 精确几何由 Core 层保证

### 4.4 Server-Agent 职责划分

> 详见 [Architecture.md §3.3 Server vs Agent 职责边界](./Architecture.md#33-server-vs-agent-职责边界)

**关键设计原则**：
- **Server 不做决策**：它不决定"沙发放哪里"，只执行验证和计算
- **Agent 不持有状态**：它只发指令，状态由 Server 管理
- **Server 是通信中枢**：所有组件通过它交换数据

## 5. 功能需求

### 5.1 Revit 插件功能

#### 5.1.1 Ribbon 面板按钮

| 按钮 | 图标 | 功能 | 优先级 |
|------|------|------|--------|
| 快速布置 | 🚀 | 一键启动：提取数据 → 配置窗口 → 启动AI | P0 |
| 开启对话 | 💬 | 直接启动 Claude Code | P0 |
| 项目配置 | ⚙️ | 打开配置面板（设置默认参数） | P1 |

#### 5.1.2 配置窗口

| 配置项 | 类型 | 选项 | 说明 |
|--------|------|------|------|
| 设计诉求 | 文本框 | 自由输入 | "帮我设计一个现代简约的客厅" |
| 设计风格 | 单选 | 现代简约/北欧/中式/轻奢/其他 | |
| 空间类型 | 多选 | 客厅/卧室/书房/餐厅/厨房/卫生间 | |
| 预算范围 | 单选 | 经济型/标准型/高端型 | |
| 家庭成员 | 输入 | 人数 + 是否有老人/儿童/宠物 | |
| 特殊需求 | 文本框 | 自由输入 | 附加要求 |

### 5.2 Canvas-MCP 功能

详细工具规范见 [Arch_MCP_Tools.md](./Arch_MCP_Tools.md)。

**核心工具分类**：

| 分类 | 工具 | 说明 |
|------|------|------|
| 画布管理 | `canvas_create`, `canvas_describe`, `canvas_export` | 画布生命周期 |
| 元素操作 | `element_add`, `element_move`, `element_rotate`, `element_delete` | 家具操作 |
| 版本控制 | `canvas_get_changes`, `canvas_ack_commits` | 变更追踪 |
| 查询分析 | `element_at`, `space_analyze`, `relation_get` | 空间分析 |

### 5.3 Web 画布功能

| 功能 | 说明 | 优先级 |
|------|------|--------|
| JSON → SVG 渲染 | 渲染画布内容 | P0 |
| 缩放/平移 | 视图操作 | P0 |
| 元素选择 | 点击选中 | P0 |
| 元素拖拽 | 移动家具 | P0 |
| 元素旋转 | 旋转方向 | P0 |
| 实时同步 | AI ↔ 用户双向 | P0 |
| 批注绘制 | 添加文字批注 | P1 |
| 撤销/重做 | 操作历史 | P1 |

## 6. 数据模型

> **注意**：本节为概述，详细数据模型定义见 [Schema.md](./Schema.md)。

### 6.1 三层汉堡模型

```
┌─────────────────────────────────────────────┐
│  顶层 (Computed) - 自动生成                   │
│  • room_zones.json   房间区域                 │
│  • exclusions.json   禁区（门扇扫过区域等）    │
├─────────────────────────────────────────────┤
│  中层 (Schemes) - 方案设计                    │
│  • zones.json        设计区域划分             │
│  • finishes.json     完成面定义               │
│  • modules.json      家具模块布置             │
├─────────────────────────────────────────────┤
│  底层 (Baseline) - 建筑基础（只读）            │
│  • architecture.json 墙体 + 柱子              │
│  • openings.json     门窗数据                 │
│  • rooms.json        房间边界                 │
└─────────────────────────────────────────────┘
```

### 6.2 .bcp 项目格式

`.bcp` 是项目的标准交换格式，本质是包含多文件夹结构的 ZIP 文件，便于版本控制和传输。

## 9. 不做的事情（Out of Scope）

| 不做 | 原因 |
|------|------|
| 3D 渲染效果图 | 超出核心价值，可用其他工具 |
| 施工图深化 | 需要专业 CAD 工具 |
| 材料报价系统 | 业务复杂度高 |
| 多用户同时编辑 | Phase 1 不做，后续考虑 |
