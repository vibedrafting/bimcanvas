# 首页实例设置系统现状说明

> 更新时间：2026-03-26  
> 所属分支：`feature/docker-deployment`  
> 对应计划：`plans/Docker_Deployment_Implementation_Plan.md` 阶段三（统一配置 UI）

## 1. 系统定位

当前这套“设置系统”指的是首页中的“实例设置”能力，不是全局任意页面都可见的设置中心。

当前定位如下：

- 入口只放在首页，进入工作区后不显示。
- 目标是统一管理单实例部署相关的 4 组配置：
  - `server`
  - `web`
  - `agent`
  - `ccr`
- 前端负责聚合展示、编辑、即时反馈。
- 后端负责读取配置文件、校验、写回、返回运行态信息，并在需要时触发实例重启。

这套设置系统主要服务 Docker 部署阶段三目标：把原来分散在多个 JSON 文件中的实例配置集中到一个 UI 中管理。

## 2. 入口位置与页面结构

### 2.1 首页入口

设置入口目前挂在首页右上角，由首页视图直接控制显示与切换：

- `BIMCanvas.Web/src/views/HomePage.vue`

当前实现特点：

- 首页模式使用 `homeMode = 'projects' | 'settings'` 控制。
- 当 `homeMode === 'projects'` 时显示“实例设置”按钮。
- 当 `homeMode === 'settings'` 时显示设置页头部和返回按钮。
- 离开首页后，这个入口不会出现在工作区，这一点已经按需求实现。

### 2.2 设置页主体

真正的设置表单页面位于：

- `BIMCanvas.Web/src/components/UI/HomeSettingsPanel.vue`

当前页面结构包括：

- 顶部运行态摘要区
- 运行方式配置区
- 默认模型与推理行为配置区
- 连接与鉴权配置区
- CCR 路由配置区
- Web 展示配置区
- 高级 JSON 编辑区
- 底部固定操作栏（刷新 / 重启实例 / 保存配置）

## 3. 前端代码位置

### 3.1 主要文件

| 文件 | 作用 |
|------|------|
| `BIMCanvas.Web/src/views/HomePage.vue` | 首页入口展示、首页与设置页切换 |
| `BIMCanvas.Web/src/components/UI/HomeSettingsPanel.vue` | 设置页 UI、本地草稿、保存/重启交互 |
| `BIMCanvas.Web/src/services/SettingsService.ts` | 前端设置 API 访问层 |
| `BIMCanvas.Web/src/types/settings.ts` | 设置页前端类型定义 |
| `BIMCanvas.Web/src/composables/aiCommandCenter/useAgentConfig.ts` | 监听 `web_config` 热更新事件，刷新模型列表/图层配置 |

### 3.2 当前前端职责

前端当前做的事：

- 从 `/api/settings` 拉取聚合后的四组配置。
- 在本地维护 `server/web/agent/ccr` 四组草稿。
- 根据当前模式提示真正生效的默认模型字段。
- 保存时统一提交到 `/api/settings`。
- 对 `web` 组配置做即时前端广播。
- 对需要重启的配置显示“待重启”状态，并允许调用 `/api/settings/restart`。
- 保留高级 JSON 编辑入口，便于直接核对原始配置对象。

### 3.3 当前前端交互语义

这部分是这次改造中最重要的语义修正：

- 直连模式下，真正生效的默认模型来自 `agent.model`
- CCR 模式下，真正生效的默认模型来自 `server.ccr.defaultModelFamily`

也就是说：

- 不是所有“默认模型”字段都同时生效。
- 设置页现在会根据运行模式显示“真源字段”。
- 这个逻辑由后端运行态信息和前端计算一起支撑。

### 3.4 当前前端状态

当前前端已经完成的点：

- 首页专属入口已实现。
- 设置页渲染空白问题已修复。
- 从设置页返回首页后首页空白问题已修复。
- UI 已从浅色表单改为更接近项目现有风格的暗色玻璃方案。

当前仍然需要注意的点：

- 这仍然是“实例级配置台”，不是完整的系统设置中心。
- 目前没有独立的设置页自动化 E2E 测试，主要依赖构建验证和人工回归。

## 4. 后端代码位置

### 4.1 主要文件

| 文件 | 作用 |
|------|------|
| `BIMCanvas.Server/Controllers/SettingsController.cs` | 暴露设置读取、保存、重启 API |
| `BIMCanvas.Server/Services/SettingsService.cs` | 聚合四组配置、校验、写回、生成运行态信息 |
| `BIMCanvas.Server/Services/SettingsRestartService.cs` | 协调“重启实例”动作 |
| `BIMCanvas.Server/Dtos/SettingsDto.cs` | 设置系统 DTO 契约 |
| `BIMCanvas.Server/Services/ConfigService.cs` | 解析配置目录和各配置文件路径 |

### 4.2 API 现状

当前 API 结构：

- `GET /api/settings`
  - 返回 `server/web/agent/ccr` 四组配置
  - 返回 `runtime` 运行态信息
- `PUT /api/settings`
  - 接收四组配置中的任意部分
  - 写回对应 JSON 文件
  - 返回变更组、需重启组、最新设置快照
- `POST /api/settings/restart`
  - 提交实例重启请求

### 4.3 后端运行态信息

`SettingsService.BuildRuntime(...)` 当前会返回：

- `mode`
  - `direct` 或 `ccr`
- `effectiveDefaultModelPath`
  - 当前真正生效的默认模型字段路径
- `effectiveDefaultModelValue`
  - 当前真正生效的默认模型值
- `dockerManagedRestart`
  - 是否检测到容器环境
- `restartBehavior`
  - `docker-auto` 或 `manual`
- `restartHint`
  - 面向 UI 的文字提示

这使前端可以明确告诉用户：

- 现在到底运行在哪种模式
- 默认模型究竟读哪个字段
- 当前重启是 Docker 自动拉起还是需要手动重启服务

### 4.4 重启机制现状

`SettingsRestartService` 当前的实现方式是：

- 收到重启请求后，延迟约 800ms
- 调用 `IHostApplicationLifetime.StopApplication()`
- 让当前进程优雅退出

这套实现的含义是：

- 如果运行在 Docker 中，应该由容器 `restart policy` 接管拉起
- 如果不是 Docker 环境，只会停进程，不会自动重新启动

所以“点击重启实例”并不等于“无条件自动重启成功”，是否真的自动拉起取决于当前部署方式。

## 5. 配置文件落点与模板位置

### 5.1 运行时配置文件落点

实际运行时配置路径由：

- `BIMCanvas.Server/Services/ConfigService.cs`

统一决定。

当前规则：

- 如果设置了 `BIMCANVAS_HOME`，优先使用该目录
- Windows 下默认目录是：`%USERPROFILE%\\Documents\\BIMCanvas`
- 非 Windows 下默认目录是：`~/.bimcanvas`

运行时实际读写的文件名是：

- `server_config.json`
- `web_config.json`
- `config.json`
- `ccr_config.json`

注意：

- 设置系统写的是运行时目录中的文件
- 不是直接写仓库里的模板文件

### 5.2 仓库内模板位置

仓库中的模板文件目前位于：

- `BIMCanvas.Server/Templates/global-config/server/server_config.json`
- `BIMCanvas.Server/Templates/global-config/server/web_config.json`
- `BIMCanvas.Server/Templates/global-config/agent/config.json`
- `BIMCanvas.Server/Templates/global-config/server/ccr_config.json`

模板现状：

- `server_config.json` 中 `ccr.defaultModelFamily` 默认已是 `sonnet`
- `agent/config.json` 中 `model` 默认已是 `sonnet`
- `web_config.json` 仍提供 `opus / sonnet / haiku` 作为可选展示模型列表
- `ccr_config.json` 保存 CCR Provider 与 Router 的默认结构

## 6. 当前功能现状总结

### 6.1 已实现

- 首页专属设置入口
- 四组配置统一聚合编辑
- 默认模型真实生效字段提示
- 即时生效与需重启的行为区分
- `web` 配置保存后前端热更新广播
- 实例重启接口
- 高级 JSON 编辑能力
- 暗色风格设置页重设计

### 6.2 当前“即时生效”范围

当前真正做到即时反馈的主要是 `web` 配置：

- `customModels`
- `layerPresets`

保存后设置页会派发：

- `bimcanvas:web-config-updated`

当前已知使用这个事件的代码位置：

- `BIMCanvas.Web/src/composables/aiCommandCenter/useAgentConfig.ts`

也就是说，`web` 组配置的热更新目前主要体现在前端展示层，尤其是模型列表和图层预设相关能力。

### 6.3 仍需重启的范围

以下几组当前都按“需重启”处理：

- `server`
- `agent`
- `ccr`

原因是这些配置会影响：

- 服务监听
- Agent 连接与模型选择
- CCR 路由与 Provider
- 启动行为

## 7. 当前实现边界与注意事项

### 7.1 校验深度并不完全一致

当前后端校验策略不是四组完全对称的：

- `server` 使用 `ServerConfig` 做结构校验
- `web` 使用 `WebConfig` 做结构校验
- `agent` 当前主要保证顶层是 JSON 对象
- `ccr` 当前主要保证顶层是 JSON 对象

这意味着：

- `agent` 和 `ccr` 目前更偏“原样透传 + 基础防御”
- 还没有做到强类型、细粒度字段级校验

### 7.2 设置系统目前是实例级，不是用户级

当前设置系统修改的是当前实例配置，而不是用户个人偏好。

因此它更适合：

- Docker 实例初始化
- 单实例部署调优
- 运维型配置管理

不适合直接理解成：

- 多用户个人设置页
- 工作区内上下文设置页

### 7.3 高级 JSON 编辑能力保留了风险

当前设置页保留了高级 JSON 编辑区，这是为了：

- 便于迁移
- 便于调试
- 便于核对真实配置结构

但也意味着：

- 用户可以直接编辑原始对象
- 更容易引入结构错误或语义错误
- 尤其是 `agent` / `ccr` 这两组目前校验较弱

## 8. 建议后续工作

如果后续继续完善这套设置系统，建议优先做以下几项：

1. 为 `agent` 与 `ccr` 增加强类型校验，而不只是顶层对象校验。
2. 为设置页补充最基本的端到端回归用例，覆盖“进入设置页、保存、返回首页、重启提示”链路。
3. 继续细化“即时生效”范围，明确哪些前端组件会消费 `web_config` 热更新。
4. 评估是否需要把高级 JSON 编辑区做成默认折叠，降低误操作概率。
5. 如果未来支持多实例/多租户，需要重新审视当前“实例级配置台”的边界。

## 9. 一句话结论

当前这套设置系统已经完成了阶段三的核心骨架：

- 入口在首页
- 前后端链路已通
- 四组配置可统一读写
- 默认模型生效语义已理顺
- Docker/非 Docker 的重启行为已区分

但它当前仍然更适合“部署与实例管理”，还不是一个完备、强约束、全自动校验的系统级设置中心。
