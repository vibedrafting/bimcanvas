## 1. 议题概述

- **主题**：generate-workflow 执行效率优化 -- 用结构性工具边界替代行为引导，将布置耗时从 27 分钟降至 14 分钟以内
- **发起时间**：2026-03-20
- **参与者**：用户（产品/架构决策者）、Claude（提示词分析 + 方案设计）、Antigravity、Codex
- **背景信息**：

  BIMCanvas Agent 使用 claude-opus-4-6 模型（extended thinking, maxThinkingTokens=16000）执行室内家具布置任务。当前 generate-workflow 工作流分为五个阶段：感知 -> 规划(2.1/2.2/2.3) -> 尝试与修改 -> 优化 -> 汇报。

  2026-03-20 的主卧布置测试（金凤127 项目，rz_3，L 形主卧）暴露了核心性能瓶颈：总耗时 26 分 53 秒，其中 thinking 时间占 20 分 22 秒（75%）。最终布置结果质量高（validate_layout 一次通过，0 错误，4 个设计目标全部达成），但执行速度不可接受。

  **问题根因**：

  此前已经历三轮提示词优化尝试（强制输出、出声思考、精度边界等），均未能有效控制 thinking 时间。第三轮发现 maxThinkingTokens=-1（无限制）是单次卡死 8-30 分钟的直接原因，改为 16000 后单次不再卡死，但总 thinking 时间仍达 20 分钟。

  日志分析揭示了根本性的机制错位：提示词中的行为引导（"规划=出声思考"、"精度边界"、"允许试错"等）运行在对话层，但 Agent 的实际分析发生在 thinking 层。两个层之间没有强制同步点，只要 thinking token 预算够用，Agent 就会在 thinking 中完成所有分析后才输出结论。这是模型训练的自然倾向，无法通过提示词覆盖。

  **已验证的事实（来自日志）**：

  （一）做得好、应当保留的提示词设计：
  - 工作流 5 阶段结构被完整执行，没有跳过步骤
  - 语义方案 v0.1/v0.2/v0.3 三版本全部输出到对话，锚定机制生效
  - AskUserQuestion 在正确时机触发（梳妆台位置 = 战略选择）
  - "先家具 -> 再分区"单向约束被正确执行，无循环依赖
  - validate_layout 一次通过（8 模块，0 错误）
  - 两个语义方案示例（L 形主卧 + 窄长卫生间）提供了有效的模式锚定

  （二）做得不好、需要改进的提示词设计：
  - Stage 2.1 thinking block 3:47 + Stage 2.2/2.3 thinking block 8:43 = 12:30，规划阶段的分析全在 thinking 中完成后才输出
  - "出声思考"指令无效：Agent 在 thinking 中做完分析，对话中只输出结论
  - "精度边界"规则失效：Agent 在规划阶段大量计算精确坐标（应是 Stage 3 的工作）
  - "允许试错"姿态未内化：Stage 3 写入前仍做 5:50 的心算预验证
  - 16000 token 限制把一个大 thinking block 拆成多个小块，但总量未减

  **核心诊断**：

  行为引导类规则（出声思考、精度边界、允许试错）对 thinking block 内部行为没有约束力。优化方向不应是"写更强的行为指令"，而应是"用结构替代自律"——通过工具调用创造物理性的阶段边界，让每个 thinking block 只需处理一个子阶段的工作量。

  **已确定的优化方向**：

  方向 A -- 结构性阶段边界：新增 MCP 工具 `save_semantic_plan` 作为每个规划子阶段的"提交按钮"，工具调用创造 turn 边界，强制将一个 12 分钟的 thinking block 拆成多个 2-3 分钟的小块。

  方向 B -- 减少 Agent 需要推导的信息量：`save_semantic_plan` 的返回值携带下一阶段的预处理数据（如床头墙候选、可用墙段扫描），将推导工作从 Agent thinking 移到 Server 端预计算。

  方向 C -- 删除无效规则释放注意力：遵循注意力零和原则，删除已证明无效的行为引导（出声思考、精度边界等），减少 ~30% 的规划阶段提示词长度。

  **已确认的约束**：
  - generate-zoning 保持独立 Skill，不合并到 v0.2 提交流程
  - 两个语义方案示例（核心锚定物）不可删除
  - 设计质量不可降级（validate 通过率 + 设计目标达成率保持）

  **待讨论的核心问题**：
  1. `save_semantic_plan` 返回值的详细设计：预处理什么、预处理多少、与策略文件如何协作
  2. Stage 3 "快速草稿"协议的具体提示词表达
  3. maxThinkingTokens 是否需要配合下调（16000 -> 8000）
  4. Web 端语义方案展示的 UI 设计

  **相关文件**：
  - 工作流提示词：`BIMCanvas.Agent/templates/skills/generate-workflow/SKILL.md`
  - 分区 Skill：`BIMCanvas.Agent/templates/skills/generate-zoning/SKILL.md`

## 二、现有提示词设计的优缺点

### 做得好的地方

**1. 工作流 5 阶段结构被完整执行**

感知→规划→尝试→优化→汇报没有跳过。说明阶段划分清晰、阶段描述简明，Agent 能正确理解并遵循。

**2. 语义方案三版本全部输出到对话**

v0.1 / v0.2 / v0.3 都以独立的对话块输出，不是只留在 thinking 里。锚定机制（"输出到对话 = 白纸黑字 = 不再推翻"）生效了。两个完整示例（L 形主卧 + 窄长卫生间）提供了强模式锚定，Agent 的输出格式与示例高度一致。

**3. AskUserQuestion 在正确时机触发**

梳妆台位置（东墙₂组合 vs 东墙₁靠窗）被正确识别为战略选择并询问用户。"战略 vs 战术"的判断标准（"两个方案对日常体验有质的差异"）被正确应用。

**4. "先家具→再分区"单向约束被正确执行**

Step 1 先用物理约束确定床/衣柜最优墙面，Step 2 再用家具位置过滤分区方案（竖切打断北墙→淘汰，横切紧凑→可行但无优势，不分割→最优），Step 3 确定结论。逻辑链清晰，无循环依赖。

**5. validate_layout 一次通过（0 错误）**

8 个模块无碰撞无越界。坐标计算质量高。

**6. 最终设计质量高**

4 个设计目标全部达成：隐私递进（入口→更衣→睡眠）、功能叙事（北墙连续存储）、延伸区意图（更衣化妆一站式）、采光轴畅通。

### 做得不好的地方

**1. 最大问题：两个巨大 thinking block——规划阶段全在 thinking 里完成**

| thinking block | 耗时 | 内容                                                         |
| -------------- | ---- | ------------------------------------------------------------ |
| Stage 2.1      | 3:47 | 床头墙 3 候选对比 + 衣柜 L 形可行性 + 部分分区预判           |
| Stage 2.2/2.3  | 8:43 | 分区 3 方案对比 + 梳妆台候选扫描 + 通道宽度计算 + v0.2/v0.3 组合 |

提示词说"规划=出声思考"、"在 thinking 中只做初步判断（几秒钟），然后在对话中展开分析"。但 Agent 的实际行为是：在 thinking 里做完所有分析 → 输出结论到对话。对话中出现的表格（如"床头墙快速筛选"）不是"出声分析过程"，而是 thinking 里算完后的结论整理。

**根因**：提示词的行为引导（"出声思考"）在对话层，但 Agent 的分析在 thinking 层。两个层之间没有强制同步机制。只要 thinking 预算够用（16000 tokens），Agent 就会在 thinking 里完成分析——这是模型训练的自然倾向，提示词无法覆盖。

**2. v0.1 没有"立即"输出——锚定机制的时效性打折**

从 Stage 2 开始到 v0.1 输出：11:37:20 → 11:41:07 = **3:47**。

提示词要求"每完成一个子阶段，立即将当前版本输出到对话中"。但 Stage 2.1 的 thinking block 里，Agent 已经在做 Stage 2.2 的工作（床头墙候选对比、衣柜 L 形几何推理、分区方案预判），v0.1 输出时实际上已经是 2.2 的一半工作做完了。

**3. "精度边界"规则失效——Agent 在规划阶段大量计算精确坐标**

提示词禁止规划阶段"计算 bounds 四角坐标"，但 thinking 中充斥着：

```
"X=9280-10030，500mm buffer → X=8780 to X=10530"
"wardrobe: X=10330-14100, Y=5150-5750"
"vanity: X=13700-14100, Y=4200-5150"
"passage: X=14100-600-12400 = 1100mm"
```

Agent 在 Stage 2 就做了 Stage 3 的坐标工作。一旦开始算坐标，碰撞验证→通道验算→L 形几何的连环推理就停不下来——这是 thinking 扩张的直接推手。

**4. Stage 3"允许试错"没有生效——写入前仍做 5:50 的心算预验证**

Stage 3 的 thinking block（5:50）中 Agent 做了：衣柜移门 vs 梳妆台冲突分析、床头柜深度规则验证、通道宽度三段计算、bounds 四角坐标生成、窗帘与床头柜间距验证。

提示词说"先放下去看效果，出错了调整就好"，但 Agent 在 Write 之前做了近 6 分钟的"一次完美"预演。模型训练倾向于"算好了再写"——"允许试错"作为设计姿态不足以覆盖这个训练倾向。

**5. 16000 token 限制效果有限**

对比之前 maxThinkingTokens=-1（无限制）时 8-30 分钟单次卡死，16000 限制把一个大块拆成了多个较短的块。但 Agent 在多个 thinking block 中仍然完成了同样体量的分析工作——总 thinking 时间 20:22 没有本质减少。预算控制了"单次最长时间"，但没有减少"需要思考的总量"。

### 核心诊断

> 提示词层面的行为引导（"出声思考"、"精度边界"、"允许试错"）对 thinking block 内部行为没有约束力。这不是规则写得不够好的问题，而是机制错位——规则在对话层，但 Agent 的分析在 thinking 层，两个层之间没有强制同步点。

## 三、优化方向

### 核心思路

> 不是"让 Agent 更快地做同样的工作"，而是"让工作本身变简单"。
> 不是"写更强的行为指令"，而是"用结构替代自律"。

### 三个方向

**方向 A：结构性阶段边界**

用工具调用（MCP tool call）创造物理性的 turn 边界。工具调用结束当前 turn 的 thinking，返回结果后开启新 turn——新 turn 的 thinking 只需要处理下一个子阶段的工作量。

现状：2.1 + 2.2 + 2.3 在同一个 thinking 里完成（12:30 总计）
目标：每个子阶段一个 turn，每个 turn 的 thinking 控制在 2-4 分钟

**方向 B：减少 Agent 需要推导的信息量**

Agent 在 thinking 里大量时间花在从原始墙面数据推导候选结论（筛选床头墙、评估 L 形衣柜、扫描可用墙段）。如果这些推导工作由 Server 预处理完成，Agent 只需要验证/选择，thinking 时间大幅缩短。

**方向 C：删除无效规则，释放注意力**

遵循注意力零和原则——已证明无效的行为引导（"出声思考"、"精度边界"、"在 thinking 中只做初步判断"）不仅不起作用，还占据了注意力预算。删除后为结构性规则腾出空间。

## 四、具体改动草案

### 改动一：新 MCP 工具 `save_semantic_plan`

**这是整个优化的核心机制。**

#### 目的

1. **功能价值**：持久化语义方案，Web 端展示规划状态和演进历史
2. **行为价值**：作为每个规划子阶段的"提交按钮"，创造 turn 边界

#### 工具定义

```
工具名：mcp__canvas__save_semantic_plan
输入：
  zoneId: string                    # 目标 Zone ID
  version: "v0.1" | "v0.2" | "v0.3"
  content: string                   # 语义方案文本（markdown 格式）
输出：
  saved: true
  next_stage_hints: object          # 下一阶段的预处理数据
```

#### 返回值（方向 B 的载体）

| version | next_stage_hints 初步构想                     | 目的                              |
| ------- | --------------------------------------------- | --------------------------------- |
| v0.1    | 床头墙候选列表 + 衣柜墙候选列表               | 减少 Stage 2.2 的推导工作         |
| v0.2    | 可选家具可用墙段（≥800mm，已排除门窗 buffer） | 减少 Stage 2.3 的扫描工作         |
| v0.3    | 无                                            | v0.3 后进入 Stage 3，不需要预处理 |

> **开放问题**：`next_stage_hints` 的具体内容和预处理程度是核心设计决策，需要结合 Agent 策略文件（bedroom.md 等）详细讨论。核心权衡：预处理越多 → thinking 越短，但 Server 逻辑越重且灵活性越低。

#### 行为机制

```
现状（行为引导 → 无效）：

  [THINK] Stage 2.1 分析 + Stage 2.2 分析 + Stage 2.3 分析 ... (12分钟)
  [AI] 输出 v0.1 + v0.2 + v0.3
  [TOOL] AskUserQuestion

目标（结构性边界 → 强制分段）：

  [THINK] Stage 2.1 分析 ... (2-3分钟)
  [TOOL] save_semantic_plan(v0.1)          ← turn 边界
  [THINK] Stage 2.2 分析 ... (2-3分钟)     ← 新 turn，基于返回的候选数据
  [TOOL] save_semantic_plan(v0.2)          ← turn 边界
  [THINK] Stage 2.3 分析 ... (1-2分钟)     ← 新 turn，基于返回的墙段数据
  [TOOL] AskUserQuestion / save_semantic_plan(v0.3)
```

#### 实现涉及文件

- `BIMCanvas.Agent/src/mcp/canvas.py` — Python 端新增工具定义
- `BIMCanvas.Server/Controllers/` — C# 端新增 REST endpoint
- `BIMCanvas.Server/Services/` — 语义方案存储服务 + 候选预计算逻辑
- `BIMCanvas.Web/` — 语义方案展示组件（SignalR 推送）

## 一、 测试日志体现出的“提示词设计”优缺点

通过分析长达 25 分钟的主卧布置测试日志，我们可以清晰地看到当前提示词（Prompt）在引导大语言模型（LLM）行为时的红利与陷境。

### 🌟 表现优异的地方（红利）
1. **空间语义与因果逻辑（WHY）理解极佳**
   - Agent 完美理解了提示词中赋予规则的“WHY”。例如它准确识别了“进门到深处”的隐私梯度关系，知道更衣区应在此、床应在深处；并在放置梳妆台时，准确判断了“门开启禁区”与“使用间隙”的本质区别。
2. **战略与战术判断异常精准**
   - 提示词中建立的优先权机制非常成功。Agent 能敏锐地识别到“梳妆台是紧跟衣柜还是靠窗”是一个会改变后续所有尺寸、并影响日常体验的【战略选择】，从而果断停止内耗，主动发起 `AskUserQuestion` 寻求用户介入。
3. **最终产出的设计质量（Layer 2）极高**
   - 最终输出的布置方案毫无违和感，所有通道、动线完全符合《通用设计原则》的要求。

### ⚠️ 表现不佳的地方（陷境 / Root Cause）
**核心症状：高达 80% 的时间被消耗在 `[THINK]` 内部的“高微积分二维装箱演算”中。**
1. **“低成本试错机制”由于恐惧而彻底失效**
   - 日志显示，Agent 把 `validate_layout` 当成了“最终判决考试”，而不是“过程中随时可按的计算器”。
   - 它在 `[THINK]` 块中长考了近 18 分钟。因为它在脑海中试图完全心算出 4 边墙的剩余长度、床和柜子的厚度、甚至门开启的重叠量。它力求在产出 JSON 时得到 0 Errors。
2. **被具体数字绑定，认知约束过载**
   - 我们在 `bedroom.md` 中写了太多“好心”的指导，比如“扣除 500mm 门缓冲”、“检查剩余进深减去床厚度减去衣柜是否 < 800mm”。
   - 一旦 LLM 看到这些硬性数字指标，它的“做题家”基因就会发作。这导致在思考过程中出现大量的由于数字减法引发的“推倒重来”，极大地浪费了 Token 和算力。

## 二、 优化应该改动的方向

优化必须围绕《Agent 提示词设计哲学》展开，核心思想是：**把大模型当作文科生用它的“设计直觉（拓扑关系）”，把数学计算全部扔给理科生（Server验证工具）。**

1. **定性取代定量（数字脱敏）**：
   - 坚决将引发二次运算的规则（如“检查是否满足 < 800mm”）从规划阶段中剔除掉。
   - 所有在规划阶段的推理，必须基于“最长实墙”、“对侧”、“靠门侧”等纯模糊的拓扑词汇构建。
2. **强制翻转心智：从“怕错”改为“依赖试错”**：
   - 用最高级别（强硬语气）的必须/禁止规则，声明：在规划阶段预先心算避免重叠**是严重的违规行为**。
   - 拔高 `validate_layout` 的地位，让大模型知道错了一点关系都没有，工具给的 Error 日志就是下一步行动的坐标系。
3. **模糊组装与信息组块（Chunking）**：
   - 人类不会去算“左边柜子450，中间床1800，右边柜子450”。人类脑海中会浮现一个“约等于3米的睡觉组合封套”。
   - 在提示词中教导模型利用黑盒封套思维思考，降低部件级的零碎计算。只要封套撞墙报错，那就是合规砍掉不重要配件的最好时机。

### 1. 改造 `generate-workflow/SKILL.md`（约束与示例）

**草案 A：升级【精度边界】为绝对硬约束**
用硬性列举斩断引发算力爆炸的内耗。

> ### 精度边界（【必须】极度重要）
>
> **【必须】规划阶段全程绝对禁止任何形式的算术运算（不可出现加减法等式）和空间剩余量的精确计算。**
>
> | 规划阶段允许（定性描述）             | 规划阶段绝对禁止（定量心算）              |
> | ------------------------------------ | ----------------------------------------- |
> | "北墙放衣柜，西墙最长首选放床"       | 计算 bounds 的四角坐标                    |
> | "让床头群组作为一个整体靠西墙"       | 出现 `4850-1800-450=2600` 这类数学计算式  |
> | "通道应该比较宽裕，具体交由工具验证" | 计算具体的剩余通行间隙是 950mm 还是 850mm |
> | "衣柜填满延伸区"                     | 验证家具边界是否在 innerBoundary 内       |
>
> WHY：大模型执行连续数学排布极度消耗 Token 且常常因为算错陷入死循环。Server 端的 `validate_layout` 能在 0.1 秒内精准完成所有的重合和越界计算。你的核心职责是“分配家具归属哪面墙”，任何剩余空间的加减法都必须交给 Server 工具去试错！

**草案 B：重构【尝试 ↔ 修改】逻辑，植入试错示例**
增加一小段报错应对的锚点，让它学会怎么把 Error 变成垫脚石。

> ## 3. 尝试 ↔ 修改
>
> > **核心姿态：依赖工具试错。** 像人类设计师一样工作——凭直觉把大致坐标凑出来写进文件，然后**立刻**让 `validate_layout` 撞墙报错。不允许在脑中完成无重叠验证后才敢写文件！这是极为严重的违规行为！
> >
> > **【试错工作流示例】**
> > 大致排布写入 modules.json → 调用 `validate_layout` → 工具报错："床(X:9100)与衣柜(X:9000)重叠100mm" → 你不需要自己重算整个屋子的坐标，直接接纳工具的指引，将床向南平移100mm → 再次验证直至通过。
> >
> > WHY："一次完美"的预期是引起长考膨胀的罪魁祸首。快速迭代（瞎填→报错→依报错修正）的成本远低于在脑内预防所有问题。

## 一、测试日志结论

### 1.1 这次测试发生了什么

本次测试对应一次完整主卧 generate 任务。

关键时间点：

- 用户发起任务：`11:35:42`
- 输出 `v0.1`：`11:41:16`
- 加载 zoning 后进入长时间规划：`11:41:29 - 11:50:12`
- 向用户提问：`11:51:04`
- 用户回答后再次长时间思考：`11:52:42 - 11:58:32`
- 第一次写入 `modules.json`：`11:59:38`

- 最终完成：`12:02:35`

结论上，这次任务：

- 最终布局结果是对的
- 第一次写入就通过验证，工程质量很高
- 但总耗时接近 `27 分钟`
- 第一次 `Write` 发生在接近第 `24 分钟`

这说明当前问题不是“不会做”，而是“做得太慢，且慢在写入前的脑内论证”。

### 1.2 当前提示词设计做得好的地方

这次日志已经证明，当前提示词设计在“做对”这件事上是有效的。

- **五阶段骨架有效**
  Agent 的行为确实被组织成了 `感知 -> 规划 -> 尝试/修改 -> 优化 -> 汇报`，不是一团混乱的自由发挥。

- **语义方案机制有效**
  Agent 已经不再完全闷在 thinking 里直到最后才说话，`v0.1 / v0.2 / v0.3` 的外化机制是生效的。

- **设计品质目标有效**
  最终输出不是单纯“家具摆进去”，而是能围绕空间节奏、功能叙事、空间意图、采光通风来组织解释，说明 `design_evaluation.md` 对策略层有正向作用。

- **房间策略有实际引导力**
  这次主卧的床头墙、衣柜墙、延伸区利用方式，最后都落到了合理方案，说明 `bedroom.md` 对方向判断是有用的。

- **Layer 1 / Layer 2 分层是成功的**
  工程合规与设计品质被明确区分，这能避免“还没放进去就开始审美复盘”的混乱。

- **“允许试错”至少被写进了工作流哲学**
  虽然行为层还没完全兑现，但这是正确方向。后续优化应该继续强化，而不是回到“一次完美”的工作流。

### 1.3 当前提示词设计表现不佳的地方

日志也清楚暴露出，当前提示词设计还没有稳定解决“做快”的问题。

- **Stage 2 仍然过重**
  最大耗时发生在规划阶段，而不是执行阶段。说明当前提示词仍在鼓励 Agent 把大量问题留在写入前解决。

- **规划阶段的“禁止精算”没有真正落地**
  文档明确要求 Stage 2 只做粗估，但日志里仍出现了大量精细几何推演、门扇禁区分析、柜体碰撞预判、L 型转角可行性演算。这说明规则写了，但行为没有被稳定激活。

- **“允许试错”还停留在理念层**
  这次首版写入之所以成功，不是因为 Agent 快速写入后依赖验证闭环修正，而是因为它在写前已经在脑中做了大量预验证。

- **AskUserQuestion 边界不够稳定**
  日志里 Agent 多次在“这是不是战略选择”“该不该问用户”之间摇摆。说明 `BIMCANVAS.md`、`generate-workflow`、`bedroom.md` 之间的边界还不够统一。

- **`generate-zoning` 的职责边界还没有完全落实**
  设计文档已经明确“必须执行，但复用已有分析”，但日志中 zoning 相关阶段仍然重新展开了较多空间理解和候选推演。问题不是 zoning 不该执行，而是它还没有真正以“复用已有分析”的姿态执行。

- **部分规则形态仍在诱导穷举**
  虽然卧室规则已经从旧矩阵走出来了，但当前策略仍然在某些节点上诱导 Agent 对多个候选做长时间横向比较。

- **后置验证存在一定重复论证**
  `validate_layout` 之后，Layer 1 和 Stage 4 的检查在这次任务里仍带有一定重复确认色彩。它们结构上是合理的，但节奏上还不够克制。

### 1.4 当前提示词设计的总判断

一句话总结当前现状：

**当前提示词体系已经比较成功地解决了“做对”的问题，但还没有稳定解决“做快”的问题。**

更准确地说：

- 它已经能把 Agent 引向正确、完整、可解释的布局
- 但还没能把 Agent 稳定引向“像人类设计师一样先形成首版、先落一次、再看效果、再修正”的工作姿态

## 二、优化目标

下一轮优化的目标，不是让 Agent “少思考”，而是让它“把思考用在更对的地方”。

目标应定义为：

- 更早形成 `v0.1`
- 更早形成 `v0.2`
- 更早进入第一次 `Write`
- 把更多几何问题交给 `validate_layout`
- 把更多设计质量问题交给写后截图审查和定向调整
- 保持最终布局质量不下降

最终希望建立的工作姿态是：

**像人类设计师一样，先形成一个可信首版，尽快放下去看，再根据真实结果修正，而不是在脑中证明很久才敢第一次写入。**

可观测指标建议保留：

- 首次 `v0.1` 输出时间
- 首次 `v0.2` 输出时间
- 首次 `Write` 时间
- thinking 总时长占比
- 首次写入后的 `validate_layout` 通过率
- 最终设计质量

## 三、优化方向

### 3.1 总方向

下一轮不应继续沿着“再多写几条约束，让 Agent 不要想太久”这个方向走。

正确方向是：

- 改工作流结构，让慢路径更难发生
- 改边界定义，让 Agent 少在规则冲突之间摇摆
- 改示例，让正确节奏更容易被模仿

换句话说：

**优化重点应从“增加规则密度”转向“重建执行节奏”。**

### 3.2 方向一：减轻 Stage 2 的“证明压力”

当前 Stage 2 在实际行为中承担了太多责任：

- 既要理解空间
- 又要完成家具决策
- 又要完成分区审视
- 又要判断是否问用户
- 又要在脑中排除大量潜在冲突

这会自然把 Stage 2 变成一个长时间的论证区。

后续应把 Stage 2 的成功标准改成：

- 形成一个足够可信的首版方案
- 而不是证明当前方案已经接近全局最优

### 3.3 方向二：收紧“何时问用户”的边界

从日志看，AskUserQuestion 是一个高放大器。

一旦规则让 Agent认为“这里可能是战略选择”，它就会开始长时间构造对比方案、解释体验差异、反复确认是否值得问。

因此后续应收紧：

- 什么时候才算真正的战略选择
- 什么时候虽然存在替代方案，但仍默认自主决策
- 什么时候系统已有明显推荐，不应再花长时间构造平行方案

### 3.4 方向三：保留 zoning 的必要性，但压实其复用边界

这一点必须明确：

- `generate-zoning` 必须执行
- “不分割”是合法结论，不是跳过 Skill 的理由
- zoning 的价值在于功能审视和功能定义

但也必须明确：

- zoning 不应重新做完整空间理解
- zoning 不应重新从 raw 层重构一遍墙面和几何关系
- zoning 应复用 `v0.1` 和“主家具最优墙面结论”
- zoning 的重点应是“分区兼容性判断 + 功能身份定义”

所以这里不是“削弱 zoning”，而是“让 zoning 真正按设计文档的方式工作”。

### 3.5 方向四：把第一次 `Write` 前移

只要首版方案已经满足以下条件，就应尽快进入第一次写入：

- 主家具关系已清晰
- 空间主要功能组织已清晰
- 关键战略选择已处理完

不应继续要求：

- 所有局部几何问题都在脑中推演完毕
- 所有细部位置都在写前已经被证明最优

### 3.6 方向五：进一步依赖验证闭环，而不是脑内预验证

后续要强化的不是“请更大胆一些”这种软鼓励，而是工作流中的结构性导向：

- 写前人工检查只保留 validate 无法覆盖的问题
- 可计算的几何冲突默认交给工具
- 首次写入失败是正常状态，不应被视为工作流失败

## 六、不建议采用的改法

为避免走偏，以下方向当前不建议采用：

- 不建议继续大规模叠加“不要想太多”“不要精算”“必须更快”之类的规则
- 不建议削弱 `generate-zoning` 的必要性
- 不建议把大量领域知识硬塞回 workflow
- 不建议为了追求速度而直接删掉 Layer 1 / Layer 2 分层
- 不建议在还没改流程骨架之前，就先对房间策略做大面积重写

这些做法要么违反提示词设计原则，要么容易掩盖真正的结构性问题。

## 七、当前草案的核心判断

这轮优化最关键的，不是让 Agent “更听话”，而是让它的时间分配结构发生变化：

- 少花时间在 thinking 中证明
- 多花时间在对话中承诺阶段性结论
- 更早进入文件写入
- 更依赖验证和修正闭环

一句话总结：

**当前工作流提示词的下一轮优化，核心不是加规则，而是让 Agent 更稳定地以“先形成首版 -> 先尝试 -> 再修正”的方式工作。**

**一、回应 @Codex 的直接提问：我认可"先轻后重"**

**二、回应 @用户 的 SDK 参数研究请求**

我研究了 Agent SDK 的源码和参数传递链路，以下是三个核心参数的系统性说明：

**(1) `maxThinkingTokens`（当前值：16000）**

控制单个 turn 中 extended thinking block 的 token 上限。值为 `null` 或 `-1` 时表示无限制（此前的默认配置，导致单次卡死 8-30 分钟）。

关键理解：这是 **per-turn** 预算，不是全会话预算。如果我们通过 `save_semantic_plan` 把一个大 turn 拆成 3 个小 turn，每个 turn 都有独立的 16000 token 预算。这意味着结构边界到位后，可以进一步**降低** `maxThinkingTokens`（比如 8000），因为每个 turn 的任务范围已经被工具调用缩小了。

但降低有风险：如果预算不足以让 Agent 完成子阶段的必要推理（比如 L 形空间的分区评估确实需要一定的推理深度），质量会下降。建议策略是**先不动预算，等结构边界到位后，再根据测试日志中每个 turn 的实际 thinking token 消耗量来调整**。

**(2) `defaultEffort`（当前值：`"low"`）**

控制模型的推理深度。从 `"low"` 到 `"max"` 逐级增加。这个参数影响的是模型在每个 token 上投入的计算量，而非 thinking block 的长度。

当前配置的一个潜在问题：`effort=low` + `thinking=adaptive` 的组合意味着模型被告知"低努力"但同时启用了扩展思考。这可能导致一种矛盾——模型每个 thinking token 的质量较低（因为 low effort），但为了弥补质量不足，它可能需要生成更多的 thinking tokens 来达到同样的结论。换句话说，**low effort 可能反而让 thinking block 变长**。

这是一个值得在第一轮测试中验证的假设：尝试 `effort=medium` 看看是否反而缩短了 thinking 时间（更高质量的 token = 更快收敛到结论）。

**(3) `defaultThinking`（当前值：`"adaptive"`）**

两个选项：`"off"` 完全禁用扩展思考，`"adaptive"` 由模型自行决定是否使用。没有 `"always"` 选项——`adaptive` 模式下模型根据任务复杂度自动判断。

禁用 thinking 是一个极端选项：Agent 将完全失去在对话外的推理空间，所有推理必须在对话输出中进行。这可能迫使 Agent "出声思考"（因为没有别的地方可以思考），但也可能严重降低坐标计算的准确性。当前不建议关闭，但可以作为后续的对比实验。

| ----------------- | -------- | ------------- | ----------------------------------------------- |

| defaultEffort     | low      | 尝试 medium   | 假设：更高质量的 token 可能让 thinking 更快收敛 |
| defaultThinking   | adaptive | 保持 adaptive | 禁用 thinking 风险太高                          |

   - `next_stage_hints`：不含预处理返回值
   - 封套思维/Chunking：延后

**Phase 1B：参数调优实验**

前提：Phase 1A 日志验证结构边界有效后执行。

内容：将 `defaultEffort` 从 `"low"` 改为 `"medium"` 跑对照日志，验证"更高质量 token 是否让 thinking 更快收敛"的假设。

**Phase 2：增量优化**

前提：Phase 1A/1B 结构稳定后。

内容：
- `save_semantic_plan` 返回值增加 `next_stage_hints`（预处理候选数据）
- 封套思维/Chunking 在 `bedroom.md` 中落地
- C 类计算指令从规划阶段迁移到验证阶段
- AskUserQuestion 触发条件统一收紧

**Phase 3：定向修正**

前提：Phase 2 日志仍显示特定空间类型卡顿。

内容：针对性处理房间策略中仍在诱导穷举的规则。

### 数值分类标准（共识）

后续所有提示词改写统一使用此分类语言：

| 类型 | 定义 | 处理方式 |
|------|------|---------|
| A 类：验证标准 | Layer 1 判据（"主通道>=900mm"） | 保留，不动 |
| B 类：模块尺寸 | 事实数据（"床 1800x2100"） | 保留，不动 |
| C 类：计算指令 | 要求 Agent 执行计算步骤的表述 | 不删除，标注适用阶段（从 Stage 2 移到 Stage 3/Layer 1） |

核心原则：**不是删除数值标准，而是重排它们的激活时机。把工程约束放回正确阶段，不是放松工程约束换速度。**

### Phase 1A 验证标准（共识）

测试场景：金凤127 主卧（rz_3），对比改动前后 Server 日志。

| 指标 | 当前基线 | Phase 1A 预期 | 判定标准 |
|------|---------|--------------|---------|
| Stage 2 最大单次 thinking | 8:43 | 显著缩短 | 每个 turn <= 4 min |
| 首次 Write 时间 | 第 24 分钟 | 前移 | < 第 15 分钟 |
| validate_layout 通过 | 首次通过 | 允许 1 轮修正 | 最多 2 轮通过 |
| 设计质量 | 4 目标全达成 | 保持 | 不出现明显降级 |
| save_semantic_plan 调用 | 无 | v0.1/v0.2/v0.3 各 1 次 | 3 次调用均出现 |

注：Phase 1A 允许 validate_layout 首次不通过——这不是质量下降，而是工作模式从"心算完美后一次通过"到"快速写入后工具修正通过"的正常改变。

### 不建议采用的做法（共识）

- 不继续叠加行为引导类规则（已证明对 thinking 无效）
- 不削弱 `generate-zoning` 的独立性和必要性
- 不在 Phase 1A 中同时改多个变量（结构和参数分开验证）
- 不在 Phase 1A 中偷偷扩展 `save_semantic_plan` 的工具契约
- 不为追求速度直接删除 Layer 1/Layer 2 分层
- 不在结构骨架没有稳定前大改房间策略文件
