## 1. 议题概述

- **主题**：Phase 1A 测试复盘 -- 2.2->2.3 阶段边界失效的根因分析与修复方案讨论
- **发起时间**：2026-03-20
- **参与者**：用户（产品/架构决策者）、Claude（主持人/实施者/SDK 专家）、Antigravity（提示词认知专家）、Codex（工程验证专家）
- **背景信息**：

  **一、前序讨论回顾**

  在上一轮讨论（`reviews/WorkflowSpeedup_Review.md`）中，团队针对 generate-workflow 执行效率问题达成了核心共识：用结构性工具边界替代行为引导。具体地，新增 `save_semantic_plan` MCP 工具作为每个规划子阶段的"提交按钮"，创造物理性 turn 边界，目标将总耗时从 27 分钟降至 14 分钟以内。

  Phase 1A 的共识交付物包括：
  1. 极简版 `save_semantic_plan` MCP 工具（持久化 + turn 边界，不含 next_stage_hints）
  2. `generate-workflow/SKILL.md` 重写（删除无效行为引导、新增强制工具调用、改 Stage 3 为"快速草稿"协议）
  3. `generate-zoning/SKILL.md` 边界收紧
  4. `BIMCANVAS.md` 最小同步修改

  Phase 1A 的排除项：不动房间策略文件（bedroom.md 等）、不动 config.json 参数、不含预处理返回值、不含封套思维/Chunking。

  **二、Phase 1A 实施完成与测试结果**

  Phase 1A 改动已全部实施（commit `4161def`），并在同一测试场景（金凤127 / rz_3 主卧 / L 形空间）下完成了新一轮测试。

  测试参数：effort=low，thinking=adaptive，maxThinkingTokens=16000（与基线完全一致）。

  核心结果对比：

  | 指标 | 基线（改动前） | Phase 1A（改动后） | 变化 | 预期目标 |
  |------|--------------|-------------------|------|---------|
  | 总耗时 | 26:53 | 25:11 | -1:42 | <= 14 min |
  | thinking 总时长 | ~20:22 | ~18:14 | -2:08 | -- |
  | Stage 2.1 thinking | 3:47 | **1:46** | **-2:01** | <= 4 min |
  | Stage 2.2+2.3 thinking | 8:43 | **11:12** | **+2:29** | <= 4 min (per turn) |
  | Stage 3 thinking | 5:50 | 4:02 | -1:48 | <= 2 min |
  | validate_layout 错误 | 0 | 0 | 持平 | 持平 |
  | 设计目标达成 | 4/4 | 4/4 | 持平 | 持平 |
  | save_semantic_plan 调用 | 0 | 3 (v0.1/v0.2/v0.3) | +3 | 3 |

  **整体评价**：设计质量完全保持，但速度优化效果远低于预期（仅降低 1:42，目标 >= 12 分钟）。Phase 1A 的核心机制在 **2.1->2.2 边界处生效**（thinking 从 3:47 降至 1:46），但在 **2.2->2.3 边界处完全失效**（两阶段合并为 11:12 的单一 thinking block，比基线 8:43 还长）。

  **三、失败点详细分析**

  **(1) 2.2->2.3 阶段边界失效（最严重问题）**

  Stage 2.2 和 2.3 的全部分析发生在 19:55:01 -- 20:06:13 的单一 thinking block 中，历时 11:12 分钟。thinking 内容涵盖了两个阶段的完整工作：
  - Stage 2.2 应有的工作：床头墙候选对比、衣柜墙候选及通道宽度验算、三种分区方案预布置验证
  - Stage 2.3 应有的工作：梳妆台候选墙段扫描、衣柜 L 型 vs 线性 vs 梳妆台组合的深度分析、梳妆台深度 600mm vs 400mm 的开关间距权衡

  `save_semantic_plan(v0.2)` 并非由工作流自然节奏触发。它是在 API `max_output_tokens`（32000 token 上限）错误强制截断超长输出后，Agent 在下一轮 brief thinking 中才补提交的（20:06:37）。若无此错误，Agent 原计划在同一长输出中连续输出 Stage 2.2 分析后直接提交 v0.2，turn 边界的效果更弱。

  **(2) "位置暂定原则" WHY 主动诱导跨阶段思考**

  日志中可见，Agent 在 2.2 主家具分析时主动扫描了梳妆台候选位置（2.3 工作），并明确说明原因是"衣柜是否 L 型取决于梳妆台位置"。这是 `SKILL.md` 中"可选家具的加入可能发现更优的全局布局"规则的直接结果 -- 这条 WHY 创造了一个逻辑需求：必须分析 2.3 内容才能判断 2.2 是否完整。

  同时，v0.2 示例中的注释"衣柜是否 L 型延伸到东墙2 取决于梳妆台位置（2.3 决定）"作为最强锚定物，直接锚定了"v0.2 需要前瞻 2.3"的行为模式。

  **(3) 2.1->2.2 成功的原因对比分析**

  2.1->2.2 边界成功是因为存在**双重 turn 边界**：`save_semantic_plan(v0.1)` 提交 + `generate-zoning` Skill 加载，两个连续工具调用形成了物理性阻断。而 2.2->2.3 之间只有 `save_semantic_plan(v0.2)` 一个工具调用，且该调用在 thinking 结束后才触发，无法起到"打断"效果。

  **(4) Stage 3 的"快速草稿"部分生效**

  Stage 3 thinking 从 5:50 降至 4:02（-1:48），有改善但仍偏长。4 分钟 thinking 仍包含：衣柜角几何重叠计算、梳妆台深度与开关间距精确权衡、衣柜门类型判断、多段走道宽度逐一验算。"快速草稿"姿态在结果层面体现（validate 一次通过、未发生多轮修正），但 thinking 层面的"一次完美"倾向仍占主导。

  **四、测试分析报告提出的修复建议**

  分析报告（`test/chat_20260320_195050/analysis_chat_20260320_195050.md`）提出了 5 条建议：

  1. **[P0] 在 2.2 和 2.3 之间增加强制工具调用** -- 推荐新建 `generate-optional-furniture` Skill，v0.2 提交后强制加载，创造物理 turn 边界（复制 2.1->2.2 成功模式）

  **五、本次讨论任务**

#### 发现一：2.1 的 thinking 并不纯粹——它已经泄漏到 2.2 领域

分析报告说"v0.1 内容轻量，只有空间骨架"。**输出确实是轻量的，但 thinking 不是。**

回看 19:52:58-19:54:44 这 1:46 的 thinking 内容：

```
[19:53:34] 床头墙候选筛选（排除窗墙+门段 buffer）→ 西墙 4850mm 最强候选
[19:53:52] 东墙₁ 3300mm 也可行，北墙东段 3570mm 弱候选
[19:54:43] 衣柜北墙有效段计算：14100-10330 = 3770mm
[19:54:43] 衣柜门开关预留 300mm 分析
```

Agent 在"Stage 2.1 thinking"里已经做了床头墙候选对比和衣柜有效段计算——这些是 Stage 2.2 的工作。但当 thinking 结束后，它只提交了 v0.1（空间骨架），把这些 2.2 分析留在了 thinking 里。

**这意味着**：save_semantic_plan(v0.1) + Skill 加载的双重 turn 边界确实**截断了正在膨胀的 thinking**，迫使 Agent 提交已有结果并开启新 turn。2.1 的 1:46 不是"Agent 只花了 1:46 做 2.1 工作"，而是"Agent 正在做 2.2 工作时被强制停下来了"。这是好消息——边界机制在起作用。

---

#### 发现二：11:12 的根因不仅是"缺少边界"，更是决策循环依赖

分析报告将 11:12 block 的根因归为"缺乏中间结构性工具调用"。这是对的，但不完整。

深入阅读 thinking 内容，我发现 Agent 陷入了一个**三角循环依赖**：

```
床头墙选择 ←→ 衣柜形态（L型/线性）←→ 梳妆台位置
     ↑                                    |
     └────────────────────────────────────┘
```

具体证据链：

1. **19:56:10** — Agent 分析完床在西墙后，立刻考虑衣柜放东墙₁："如果床放东墙₁，西墙就能放超大衣柜"
2. **19:58:34** — 分析床和衣柜在对面墙的通道："3300-2100-600=600mm < 900mm"，发现不行
3. **19:59:02** — 转向 L 型衣柜："north wall + east wall₂ corner configuration"
4. **20:00:18** — L 型分析导致发现梳妆台无处可放："vanity placement in the extension isn't really viable with this wardrobe configuration"
5. **20:01:21** — 被迫重新考虑："What if I keep the wardrobe linear on the north wall only and free up east wall₂ for vanity?"
6. **20:03:49** — 发现第三种可能："what if the wardrobe is L-shaped but I make the east wall section narrower to leave room for a vanity?"
7. **20:04:42-20:04:55** — 陷入 600×600mm 角部重叠几何分析
8. **20:05:07** — 又一次重新考虑东墙₁ 放床："Now I'm reconsidering whether the east wall might actually work better"
9. **20:06:12** — 最终收敛回西墙

Agent 在这 11 分钟里**至少重新考虑了 3 次床头墙选择，4 次衣柜形态**。每次重新考虑都触发了一连串的通道宽度验算和几何推理。

**这不是"Agent 没看到边界规则"的问题——是决策结构本身允许循环重评。** 即使在 2.2 和 2.3 之间加了边界，Agent 仍然可能在 2.2 的 thinking 里花 6-7 分钟做床/衣柜/分区的三角循环，因为这三个决策确实互相依赖。

---

#### 发现三："位置暂定原则"的影响比分析报告描述的更深

分析报告指出了"可选家具的加入可能发现更优的全局布局"这条 WHY 的问题。但日志显示这条 WHY 不仅仅是让 Agent "提前扫描梳妆台"——它从根本上改变了 Agent 对"2.2 什么时候算完"的判断。

关键证据在 **20:01:21**：

```
我意识到工作流的版本划分很关键：v0.2应该先确定主要家具和分区（床靠西墙，衣柜暂定），
然后在v0.3中评估可选家具（梳妆台）并做出调整。
```

Agent 知道应该分阶段，但紧接着又说：

```
但如果我把衣柜标记为暂定，就必须知道梳妆台的位置才能决定衣柜是 L 型还是线性...
```

**"暂定"这个概念本身就在邀请 Agent 做前瞻分析。** 如果 v0.2 要求标记"暂定"，Agent 自然会想"暂定什么？取决于什么？"，然后就去分析那个"什么"——也就是 2.3 的内容。

v0.2 示例中"衣柜是否 L 型延伸到东墙₂ 取决于梳妆台位置（2.3 决定）"更是直接锚定了"v0.2 阶段就要思考梳妆台"的模式。

#### 发现四：v0.2 的 API 错误不是 thinking 的原因

分析报告说"v0.2 由 API 错误触发"。这个表述有误导性。

实际序列：
```
20:06:13 — thinking 自然结束（"─ thinking complete ─"）
20:06:13 — Agent 开始输出 v0.2 分析文本
20:06:13 — 输出过程中触发 max_output_tokens 错误
```

**thinking 是自然完成的，不是被 API 错误截断的。** 11:12 是 thinking 的完整自然时长。API 错误只截断了输出文本（Agent 输出了大量 Stage 2.2 分析后超出 32000 token 上限），导致 v0.2 提交被推迟到下一个 turn。

这意味着：**即使加了边界，Agent 仍然会花 11:12 分钟 thinking。** 边界不解决 thinking 内容的问题——它解决的是 thinking 的范围问题。要减少 11:12，必须同时缩小每个 turn 的任务范围（边界）AND 减少 turn 内的循环重评（决策框架）。

#### 发现五：Stage 3 的 4:02 中有一类计算 validate_layout 无法覆盖

分析报告建议"快速草稿 + validate 修正"。但日志中 Stage 3 的 thinking 包含两类不同的计算：

**A 类（validate_layout 能检查的）**：
- 家具是否越界
- 家具之间是否重叠
- 是否侵入禁区

**B 类（validate_layout 检查不了的）**：
- 衣柜角 600×600mm 重叠处是否需要单独模块（lines 642-649）
- 梳妆台深度选 400mm 还是 600mm（lines 658-669）
- 门 d_7 旁开关预留 300mm 的满足方式（lines 655-661）
- 衣柜是用 1500+1500+770 还是其他组合（lines 647-648）

**B 类是模块选型和尺寸优化问题**，不是几何碰撞问题。"快速草稿"对 A 类有效（写了再让 validate 告诉你哪里撞了），但对 B 类无效（validate 不会告诉你"梳妆台应该用 400mm 还是 600mm"）。

如果要进一步缩短 Stage 3，需要**把 B 类决策提前到 v0.3 中解决**（比如在 v0.3 就确定"梳妆台 950×400mm"），而不只是在 Stage 3 说"快速写入"。

日志完美验证了这个假设的正反两面，并且验证效果极其两极分化：

1. **成功的物理阻断（Stage 2.1 → 2.2）**：在 Stage 2.1 尾声，Agent 调用 `save_semantic_plan(v0.1)` 并且系统立即加载 `generate-zoning` Skill，形成了一次真实的“发包-回传”打断。这强行让 thinking 时长受到遏制，从基线的近 4 分钟陡降至 **1分46秒**。

#### 核心反思与底层归因（基于《提示词学哲学》）

结合 `Agent_Prompt_Design_Philosophy.md` 中的原则，深挖本次长耗时的 3 个底层机制：

#### 1. “位置暂定（~）”法则是一剂毒药，引发了认知雪崩

在目前的提示词中，我们教导 LLM：“v0.2 只是暂定，v0.3 的可选家具可能会推翻前面的布局”。
**归因**：这严重违反了“降低复杂度”的初衷，让大模型陷入了**前瞻性死锁**。为了让 v0.2 不被推翻，它必须提前把 v0.3 全量思考验证。这种“渴求全局最优解”是 LLM Attention 层面的底层本能，试图用软性提示词（“不要在一轮里深度发散”）去封堵本能，结果只能是溃堤。
**改进策略**：废绝“暂定与推翻”逻辑。必须确立“主家具霸权”。在 v0.2 阶段，主家具的决策不可反悔。如果在 v0.3 发现可选家具塞不进去，直接剔除可选家具。从根本上切断它的“防回滚”算力开销。

#### 2. “快速草稿”缺乏“示例锚定（Anchor）”，未能学会真正的试错

尽管 Stage 3 总体写前时长略有压缩，但在调用 `Write` 工具前，Agent 仍花了 **4分02秒** 做精密心算（算门旁开关 300mm 是不是够，算梳妆台深度 400 还是 600 会不会侵占 110mm）。
**归因**：“示例是最强锚定”。虽然我们在文本里命令了“快速出草稿、利用 validate_layout 纠错”，但在它被训练的心智模型深处，调 Tool 必然要一次做对。它从未在提示词里见过它自己“随意给坐标 -> 报错 -> 轻巧纠正”的动作范例。
**改进策略**：不要进行干瘪的教条式陈述。必须在 `SKILL.md` 的 Stage 3 环节注入一个极具张力的“粗糙猜测 ➟ validate E005 报错 ➟ 平移修正 ➟ 通过”的 **Mock 文本实操范例**。让模型看到“容错与修复”是多么轻易被执行的。

#### 3. 为何 2.2 到 2.3 必须强化为“物理隔离”？

正如配套参考分析文件 `analysis_...md` 所建议的，新建一个 `generate-optional-furniture` Skill 是治本之策。
**归因**：`save_semantic_plan` 是一个纯异步流或快速确认（仅单向响应 `saved`），如果不夹杂其它动作，大模型会在它原有的这一次流式输出（Streaming）中一鼓作气把子阶段全写完。**唯有强制要求它通过 Tool 调用去拿一份新文档（比如调用子 Skill），才能在代码级别强制触发大模型将一轮思考（Yield）让渡回 Server**。这才是真正在 Turn 级别上的物理打断。

#### 2. 当前工作流架构与设计原则回顾

先看这轮工作流在架构上的基本意图。

#### 2.1 当前工作流的结构分工

从 `rule-system-map` 和当前提示词文件看，现有体系大致是这样的：

- `BIMCANVAS.md` 负责身份、角色、全局规范
- `generate-workflow/SKILL.md` 负责完整布置流程骨架
- `generate-zoning/SKILL.md` 负责 Stage 2.2 的分区与功能定义
- 各类 `references/*.md` 负责设计知识和房间策略参考
- `module_library.json` 提供模块规格和关系规则

也就是说，当前优化的主战场其实不是“再补一条规则”，而是“怎么通过工作流提示词把推理过程分层、分段、外化”。

#### 2.2 这轮修改想解决的核心问题

这轮修改的关键动作，是把 Stage 2 的语义规划显式拆成：

- Stage 2.1：空间骨架，提交 `v0.1`
- Stage 2.2：主要家具 + 分区，提交 `v0.2`
- Stage 2.3：可选家具 + 细化，提交 `v0.3`

并且要求：

- 每个子阶段完成后必须 `save_semantic_plan`
- 已提交内容是锚点，不应重新推导
- `generate-zoning` 必须执行，但应复用已有分析

从设计哲学上看，这个方向是正确的。它符合几个关键原则：

- **注意力零和**：把“当前只该想什么”收束到阶段内，降低整段混想
- **激活而非注入**：不是不断加知识，而是重构思考顺序
- **WHY 决定泛化**：把“为什么先 v0.1，再 v0.2，再 v0.3”讲清楚
- **位置效应**：把阶段提交提到流程核心位置
- **三级约束**：用“必须提交”形成硬边界

所以从提示词设计理念看，这轮不是方向错了，而是“边界设计还没有切到真正耗时的地方”。

#### 4. 这轮修改做对了什么

#### 4.1 `save_semantic_plan` 证明了“工具边界”是有效的

这是这轮最重要的正面结论。

以前 Stage 2 更像一整块连续内推。现在至少在 `v0.1` 这里，Agent 被强制要求：

- 先只做空间骨架
- 先把这部分外化
- 再往后推进

这个变化本身是成立的。它不是表面上的文档重构，而是对 Agent 认知节奏的真实干预。

换句话说，`save_semantic_plan` 不是装饰性工具，而是真正有机会成为“阶段完成标志”的结构锚点。

#### 4.2 当前优化方向符合提示词设计哲学

这轮修改并没有走向“再加很多细规则”的老路，而是在尝试：

- 用流程分层代替规则堆叠
- 用阶段锚点代替长链式内推
- 用结构性提交来减少回溯

这点非常重要。因为从 `Agent_Prompt_Design_Philosophy` 的角度看，真正高价值的优化本来就应该优先发生在信息架构和注意力分配层，而不是继续往中间塞更多约束。

#### 4.3 Stage 3 的负担相比旧流程有减轻迹象

从日志看，Stage 3 之后仍然花了几分钟，但它至少没有成为这轮最夸张的瓶颈。说明一部分设计决策确实被提前到语义方案阶段稳定下来了。

这件事有两面性：

- 正面：坐标阶段不再承担那么多策略摇摆
- 负面：如果前面的语义阶段没有真正切短，那只是“把时间从后面搬到前面”

而这次更接近后者。

#### 5. 为什么这轮没有实现真正的提速

#### 5.1 `save_semantic_plan` 只切开了 Stage 2.1，没有切开真正的主瓶颈

这是本次分析最核心的判断。

从日志看，真正长时间占用注意力和 token 的，不是 Stage 2.1，而是 Stage 2.2 到 v0.2 落盘之前的那一大段。

问题在于：

- `v0.1` 之后虽然形式上进入了下一阶段
- 但 Agent 在 Stage 2.2 内仍然进行了大量连续推理
- 而且这些推理并没有被进一步拆成短回路

所以当前的 `save_semantic_plan` 更像“阶段尾部的归档动作”，而不是“强行截断思考链的中途边界”。

如果一个边界只在思考已经完成之后才落盘，那它对耗时的帮助就很有限。

#### 5.2 Stage 2.2 与 Stage 2.3 在实际执行中并没有真正分离

提示词文件里写的是：

- 2.2：主要家具 + 分区 → `v0.2`
- 2.3：可选家具 + 战略选择 → `v0.3`

但日志里呈现出的实际行为更像是：

- 先在脑中把主要家具、分区、可选家具、用户分支、体验差异一起想了很长一段
- 想到非常后面才真正把 `v0.2` 提交出来

这意味着流程定义虽然写成了三段，但 Agent 的实际认知执行仍然偏向“两段”甚至“一大段”：

- `v0.1`
- 然后是一大块混合推理
- 最后再连续输出 `v0.2` / `AskUserQuestion` / `v0.3`

这不是“子阶段失效”，而是“子阶段在运行时没有形成足够强的行为切断”。

#### 5.3 分区 Skill 虽然被规定为“复用已有分析”，但实际仍在吞噬大量推理预算

`generate-zoning/SKILL.md` 的设计初衷很明确：

- 输入应该是 `v0.1 + 主要家具墙面结论`
- 不重新分析几何
- 不重新推导墙面语义
- 不重做主家具决策

但结合 `generate-workflow/SKILL.md` 当前写法，会出现一个结构性张力：

- workflow 要求 Stage 2.2 里先定主要家具，再用其过滤分区
- zoning Skill 又被整体加载进来，并且自身仍包含比较完整的候选列举、预布置验证、功能推演、方案展示逻辑

结果就是：虽然文档上写着“复用已有分析”，但 Agent 仍然很容易在这一段重新展开大量比较、预演和解释。

也就是说，提示词的“意图层”在说“请复用”，但“内容密度层”仍然在强烈诱导 Agent 继续深入推理。

#### 5.4 旧的长分析锚点仍然强于新的阶段边界

这次真正没有被消掉的，不是某一条坏规则，而是几类旧锚点：

- 候选方案的详细枚举
- 对多个功能方案的长篇比较
- 分区预布置验证的展开式叙述
- 大量“为什么”的解释文本
- 输出格式中的完整性期待

这些内容单独看都合理，但放在一起，会形成一个效果：Agent 会倾向于在进入 `save_semantic_plan(v0.2)` 之前，先把“应该想清楚的东西尽量一次性想清楚”。

这正好抵消了分阶段提交想要建立的节奏。

从提示词机制角度说，这是一个典型的权重冲突：

- 一边在强调“分阶段提交”
- 一边又在材料本体中强化“先充分比较和完整论证”

最终胜出的，是后者。

#### 5.5 这次并不是“总推理变少了”，而更像“推理位置重新分配了”

这轮流程修改后，Stage 3 的决策负担有所下降，但不能因此得出“整体更高效”的结论。

更准确的说法是：

- 一部分原本在坐标尝试阶段暴露的思考，被提前搬进了语义规划阶段
- 这降低了 Stage 3 的摇摆
- 但没有显著降低总认知成本

因此这轮的主要效果是“重分配”，不是“压缩”。

#### 6. 这轮新暴露出的问题

#### 6.1 出现了明显的输出膨胀风险

日志里在 `20:06:13` 左右出现 `max_output_tokens`，这是一个非常重要的新信号。

它说明当前问题已经不只是“想得久”，而是：

- 思考文本本身过长
- 阶段内解释与比较过多
- 语义方案前后的生成负担已经开始逼近模型输出限制

这类问题一旦继续扩大，会带来两个直接后果：

- 时长继续增加
- 运行稳定性下降，甚至阶段性中断

也就是说，这次工作流不只是“还不够快”，而是已经开始出现“文本机制膨胀”的副作用。

#### 6.2 `v0.2` 的语义边界仍然不够清晰

从当前文件定义看，`v0.2` 想承载的是：

- 主要家具墙面归属
- 分区结论
- 设计目标

这本来是合理的。

但运行时的问题是，Agent 很容易在“为了把 v0.2 写完整”这件事上，顺便把本来属于 `v0.3` 的比较也先想掉一大半。  
于是 `v0.2` 不再只是“主体框架”，而开始变成“半个完整方案的前置论证”。

一旦发生这种漂移，阶段边界就会失真。

#### 6.3 表述与编码层面存在轻微噪音

从日志和提示词文本里还能看到一些次级问题，比如：

- 特殊符号出现 `?` 替换现象
- 个别墙面标记和下标在日志中显示不稳定
- 有些 Layer 1 解释看起来形式化，但几何依据并不总是同样扎实

这些问题不是本轮耗时的主因，但会增加认知摩擦，也会削弱阶段文本作为“清晰锚点”的质量。

---

#### 7. 结合目标看，这轮偏离在哪里

你们最终想要的是：

- Agent 执行得又快又好
- 过程更像人类设计师
- 先尝试，再根据错误或反馈修正

而从这轮日志看，当前流程仍然更像：

- 先尽量把语义层一次性想全
- 再进入坐标层执行

这意味着它仍然偏“前置完备规划”，而不是“人类式的渐进设计”。

人类设计师当然也会先形成空间意图，但通常不会在第一次下笔前，就把所有候选方案、分区逻辑、体验差异、可选家具分歧一次性推演到很深。更常见的是：

- 先抓主骨架
- 先落一个较可信的方案
- 看到局部冲突后再回调
- 在试错中收敛

而当前工作流虽然增加了阶段提交，但 Stage 2.2/2.3 仍然保留了较强的“一次想清”倾向，所以距离这个目标还有明显差距。

#### 8. 总体判断

综合来看，我的判断是：

#### 8.1 这轮修改方向是对的

它证明了两件事：

- 工作流优化的重点确实应该放在“结构化思考边界”，而不是继续加规则
- `save_semantic_plan` 这类工具边界是真有能力改变 Agent 行为的

#### 8.2 但这轮性能结果不能算成功

因为：

- 真正的主瓶颈没有被切开
- Stage 2.2 和 2.3 仍然在运行时混合
- 分区 Skill 的复用意图没有完全转化为执行层的节流效果
- 输出膨胀已经开始冒头

所以这轮不能被定义为“工作流已经提速成功”，更准确的表述应该是：

> 它验证了正确的机制方向，但尚未完成对主耗时区间的结构性压缩。

#### 8.3 最值得保留的结论

如果只保留一句判断，我会保留这句：

> 当前最大的瓶颈，已经不再是“Agent 不知道该怎么分阶段”，而是“虽然知道要分阶段，但还没有在真正耗时的思考区间里强制停下来”。

这也是这轮日志对后续优化最有价值的启发。

**(1) 结构性缺失**：2.2->2.3 之间没有物理性 turn 边界。save_semantic_plan(v0.2) 在 thinking 完成后才被调用（且实际是被 API max_output_tokens 错误触发，非自然工作流节奏），无法起到"打断"效果。

**(3) 提示词权重冲突**（Codex 独立发现）：zoning Skill 内部的"候选方案详细枚举""多功能方案长篇比较""分区预布置验证展开叙述"等长锚点，产生的"完整论证"注意力权重大于"提交并继续"的阶段边界权重。Agent 能看到边界指令但选择继续分析。

### 三、指导原则

**核心原则**（Codex 提出，三方共识）：
> **每个新阶段都必须缩小决策空间，而不是继承上一个阶段的全部开放问题。**

凡是看到某个新 Skill 或新阶段只是"换个 turn 继续全局思考"，即可判定其未完成结构职责。

**主家具霸权**（Antigravity 提出，三方共识 + 窄门例外）：
v0.2 的主要家具位置一旦提交即为确认，不可推翻。v0.3 只能在不改变主要家具位置的前提下做"只增不改"的扩展（唯一例外：线性衣柜延伸为 L 型，限定条件为主衣柜所在墙面不变、新增段仅为转角处附加短边）。可选家具无法安置时，优先调整可选家具自身（缩小/换位/剔除），而非回溯主要家具。

**边界 + 减载双管齐下**（Codex 提出，三方共识）：
边界负责切断长思考（P0，第一批），内容精简负责防止每个新 turn 再次膨胀（P1，第二批紧跟）。少了任何一边都只是半修复。

### 七、补充共识：2.2->2.3 阶段边界的实现形式（2026-03-20 23:25 追加）

> 本节基于共识总结封板后的追加讨论。用户对"是否必须新建 Skill"提出了替代方案，经分析后达成以下补充共识。

**背景**：共识总结第四节第(1)条原定"新建 `generate-optional-furniture/SKILL.md`"作为 2.2->2.3 的物理隔离。用户提出：能否用 Reference File（类似 `references/bathroom.md`，通过 `Read` 调用加载）替代新 Skill？

**技术事实澄清**：

经 SDK 源码研究确认：所有 Skills 在 Agent 初始化时就已通过 Plugin 机制注入系统提示词，而非运行时按需加载。`Skill("generate-zoning")` 调用返回的只是 `"Launching skill: generate-zoning"` 一行文本——Skill 内容早已在系统提示词中。因此 Skill 调用和 Read 调用在 SDK 层面**都是普通工具调用，都创建 turn 边界**。

2.1->2.2 成功的真正原因是**双重工具调用**（save_semantic_plan + 紧接一个工具调用），不是 Skill 特有的"重量级注入"。

**两种方案对比**：

| 维度 | 新建 Skill | Reference File |
|------|-----------|---------------|
| turn 边界效果 | 有 | 有（等效） |
| 规则内容到达方式 | 从系统提示词中回忆（可能不完整） | 作为 Read 返回值直接出现（最新鲜） |
| 系统提示词开销 | +30 行（所有对话始终存在） | 0 |
| 近因效应 | 弱（内容在系统提示词深处） | 强（Read 返回值是当前 turn 最新内容） |
| 实现复杂度 | 中（新 Skill + Plugin 注册） | 低（新文件 + SKILL.md 一行指令） |

**用户决策**：先用 Reference File 方案尝试，因为实现更简单且 turn 边界效果等效。如果测试证明 Read 调用的边界强度不足，再升级为 Skill 方案。

**补充共识**：

1. **第一批落地清单第(1)条修正**：从"新建 `generate-optional-furniture/SKILL.md`"改为"新建 `references/optional-furniture-rules.md`"，通过 `Read` 调用加载
2. **SKILL.md 中的指令修正**：Stage 2.2 结尾从"加载 generate-optional-furniture Skill"改为"【必须】提交 save_semantic_plan(v0.2) 后，读取 references/optional-furniture-rules.md"
3. **文件内容不变**：Reference File 的正文内容与原定 Skill 完全一致（职责表述、三条禁止回流规则、窄门升级定义），仅载体形式从 Skill 改为 Reference File
4. **BIMCANVAS.md 的同步修改缩小**：不再需要注册新 Skill，仅保留 save_semantic_plan 工具的同步更新
5. **回退预案**：如果测试日志显示 Read 边界不够强（Agent 在 Read 后继续在同一 turn 中完成 2.3 分析），则升级为 Skill 方案
