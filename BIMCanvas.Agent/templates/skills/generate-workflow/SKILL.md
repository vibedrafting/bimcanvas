# Generate 工作流（完整布置）

## 流程概览

```
前置准备：截图（单独一轮）→ 读取数据（步骤 2-4 可并行）
  → 步骤 5：空间类型判断
  → 步骤 6：布局规划（动线 + 分区 + 骨架 + 骨架自检 + 骨架反思）
    ├─ 有参考图 → 结构化分析 → 空间映射 → 布局骨架
    └─ 无参考图 → 空间阅读 → 规则驱动 → 布局骨架
  → 封闭空间：阶段 A（按骨架落子）→ 验证（含全局动线）→ 阶段 B（辅助）→ 报告
    ├─ 局部修正（≤1次，只改违规家具）
    └─ 全局调整（≤1次/任务）：先联合调整 → 调不通再骨架重做
  → 卫生间：卫生间布置流程（测量→匹配→定位→验证）→ 报告
```

**核心原则**：不要一次性放置全部家具。分阶段放置，每阶段"编译检查 + 截图审查"，自主修正后再继续。
**编译检查**：`validate_layout` 自动检测几何错误（越界、重叠、禁区冲突），比人工心算更准确。
**截图工具说明**：截图工具会直接返回图片；如果你看不到图片内容，请用 Read 工具查看返回的文件路径。后续步骤中不再重复此提示。

## 执行前强制检查清单

在执行任何 Write 操作前，必须确认以下步骤已完成：

□ 已调用 mcp__canvas__request_background_screenshot 查看截图（前置）
  → 截图工具会直接返回图片；如果你看不到图片内容，请用 Read 工具查看返回的文件路径

□ 已读取 knowledge/placement_guide.md（项目目录下，非 Skill 目录）
  → 如果未读取，立即停止并先读取
  → 通用规则：§1-§6（设计原则、优先级、约束、尺寸、依赖关系、策略）
  → 空间专项：根据步骤 5 判断结果读取对应章节（§7-§11）

□ 已读取 modules/module_library.json
  → 如果未读取，立即停止并先读取
  → 家具尺寸必须从此文件选择，禁止编造

□ 已读取 schemes/zones.json
  → 获取分区 ID、边界和功能标签；分区 ID 用于后续写入 schemes/{zoneId}/modules.json

□ 已读取 computed/exclusions.json

□ 已读取 baseline/openings.json

**警告**：如果以上任何步骤缺失，禁止执行 Write 操作。

## 前置准备

### 步骤 1：前置截图（单独调用，不与步骤 2-4 并行）

```
mcp__canvas__request_background_screenshot(
  projectPath="{当前工作目录}",
  viewport={"mode": "full"}          // 全部房间
  // 或 {"mode": "zone", "zoneId": "rz_1"}  // 仅指定分区
)
```
→ 若用户指定了具体房间，使用 zone 模式聚焦目标分区
→ 若为全屋布置或未指定，使用 full 模式
→ 仔细查看截图，理解空间形态、门窗位置、房间朝向
→ **等收到并查看截图后，再继续步骤 2-4**

---

### 步骤 2-4：读取设计数据（可并行）

### 2. 读取设计规范（必须）
Read knowledge/placement_guide.md

### 3. 读取模块库（必须）
Read modules/module_library.json
→ 根据目标 Zone 的 tags + optionalTags 筛选兼容模块（模块的 tags 与 zone 的 tags 或 optionalTags 有交集）
→ 注意区分：匹配 zone.tags 的模块为**必备家具**，仅匹配 zone.optionalTags 的模块为**可选家具**（阶段 B 需通过两步验证，见 6B.3d）
→ 布置时参考每个模块的 agent_config 进行决策

模块数据采用「契约层 + 意图层」双层架构：
- **契约层**：id, tags, size, svgPath — 用于选择模块和渲染
- **意图层**（agent_config）— 用于布置决策，包含三个关键字段：
  - morphology.strategy: 形态策略
    - fixed: 固定尺寸（如马桶、成品床头柜）
    - horizontal_fill: 横向填充，宽度可变（如定制衣柜、窗帘）
    - parametric: 参数化，长宽均可调（如转角淋浴房、定制梳妆台）
    - pad_to_fit: 适配填充，物体不变但加填充物（如嵌入式电器）
  - morphology.limits 格式：
    - 范围格式 `[min, max]`：在最小值和最大值之间连续取值（如 `"width": [600, 1200]`）
    - 枚举格式 `{"enum": [v1, v2, ...]}`：只能取列表中的离散值（如 `"depth": {"enum": [400, 600]}` 表示深度只有 400mm 和 600mm 两种选择）
  - topology_rules: 拓扑规则 — 物体与环境的空间关系（如"靠墙放置"）
  - relation_rules: 关系规则 — 物体与其他家具的配合（如"面向电视墙"）

### 4. 读取空间数据
- Read schemes/zones.json
  → 包含所有可设计分区的 ID、边界（rawBoundary）、功能标签（tags）
  → 分区 ID（如 rz_1）用于后续写入 schemes/{zoneId}/modules.json
- Read computed/exclusions.json
- Read baseline/openings.json

### 步骤 5：空间类型判断

#### 空间类型说明

封闭空间（卧室等）走"创造性规划"流程（阶段 A/B），卫生间走"模板匹配"流程（查表+参数微调），两者步骤不可混用。

> **当前实现范围**：封闭空间和卫生间。开放空间（客餐厅一体等）暂不支持，遇到时应提示用户。

#### 判断规则

根据目标分区的 **tags** 确定布置流程：

| 判断条件 | 空间类型 | 执行的工作流 | 参照 placement_guide 章节 |
|---------|---------|-------------|--------------------------|
| tags 含 `shower` / `toilet` / `washing` | **卫生间** | → 跳转「卫生间布置流程」 | 通用规则 §1-§6 + **§11 卫生间** |
| tags 含 `circulation` 或 zone 跨多功能区 | **开放空间** | → 暂不支持，提示用户 | — |
| 其他 | **封闭空间** | → 继续「阶段 A + 阶段 B」 | 通用规则 §1-§6 + **§7 卧室** / **§8 客厅** / **§9 餐厅** / **§10 书房**（按房间类型） |

**多分区场景**：逐个分区独立执行步骤 5-6 和阶段 A/B。在每个分区的**最终验证**时，还应检查相邻分区之间的动线是否连贯（如从客厅到卧室的通道不被各自的家具阻断）。

---

### 步骤 6：布局规划

> **设计意图**：人类设计师在动手前会先形成"空间印象"——入口在哪、光线从哪来、生活动线怎么流动。这个步骤就是让你建立全局认知，用结构化的"布局骨架"固定下来，指导后续精确放置。
>
> **核心原则**：先想清楚整体方案，再动手放家具。骨架是语义描述（锚定墙面+朝向意图），不是精确坐标。
>
> **两层决策模型**：骨架确定全局框架（动线、分区、锚定墙面），agent_config 规则在骨架框架内精确定位坐标。agent_config 硬约束（【必须】标签）不可违反，但冲突应在骨架阶段解决——若执行阶段发现无法满足硬约束，应回到此步骤修改骨架，而非静默偏离。参考方案转化为骨架后，具有与规则推导骨架同等的执行约束力。

#### 6.1 空间阅读

结合截图和数据，回答三个问题（参见 placement_guide §1.1）：
1. **动线方向**：人从入口进来，自然会往哪里走？主通道走向是什么？
2. **纵深层次**：房间的"前场"（入口侧）和"深处"（远离入口）分别在哪？
3. **采光轴**：窗户在哪个方向？光线通路上有无遮挡风险？

#### 6.2 布局骨架生成

**路径 A：有参考图/方案时**

当用户提供了参考截图、参考方案描述或同类房型布局时：

1. **结构化分析**（逐项输出，不可笼统概括）：
   - **建筑结构**：参考房间的门、窗、卫生间门分别在哪面墙？
   - **床头朝向**：床头靠哪面墙？与门的位置关系（远离门/同侧/对面）？
   - **衣柜形态**：L 形还是线性？若 L 形，**布局方式**是传统布局（有垂直段伸入房间形成隔断）还是 L型靠墙（全贴墙）？在哪个墙角？两段分别沿哪面墙？
   - **入口侧留空**：入口方向是否保持开阔？家具主要集中在哪一侧？
   - **其他特征**：梳妆台/书桌位置、家具密度分布、功能分区模式

2. **空间映射**：比较参考房间与当前房间的建筑结构（门窗位置），判断映射关系：
   - **同构**：门窗位置基本一致 → 直接采用参考的布局模式
   - **镜像**：门窗位置左右/上下对称 → 将布局模式做相应镜像变换
   - **旋转**：门窗位置呈 90°/180° 旋转关系 → 将布局模式做相应旋转变换
   - **异构**：门窗位置差异较大 → 提取设计理念（如"L 形衣柜 + 入口侧留空 + 深处睡眠区"），在当前房间约束下重新规划

3. **转化为骨架**：将映射/变换后的参考方案直接转化为当前房间的布局骨架（见下方输出格式）。参考方案不是"加分项"，而是骨架的起点。

> **参考方案 ≠ 照搬坐标**：参考提供的是经过验证的空间组织策略。关键是识别映射关系，然后将策略变换到当前房间。

**路径 B：无参考图时**

基于 6.1 的空间阅读 + placement_guide 对应章节：
1. **动线骨架**：从入口门出发，确定到各功能区的主通道走向和支线
2. **功能分区**：将房间划分为 2-3 个功能区，确定各区的位置和职能
3. **家具群组锚定**：为每个功能区的家具群组确定锚定墙面和朝向意图
   - **卧室**：床的朝向 → placement_guide §7.3；衣柜墙面 → §7.4
   - **客厅**：沙发朝向 → placement_guide §8.2
   - **书房**：书桌朝向 → placement_guide §10.2
   - **餐厅**：餐桌位置 → placement_guide §9

**骨架输出格式**（结构化文字，控制在 200 字以内）：

```
### 布局骨架
- 动线：主通道从[入口位置]沿[方向]到[目标]；支线到[功能区]
- 分区：[入口侧]储物区 / [深处]睡眠区 / [窗前]采光区
- 锚定：床组→[X墙]，衣柜→[Y墙+Z墙(传统布局|L型靠墙)]，窗帘→[窗墙]
- 预判：[有/无]分区间冲突。[冲突描述（如有）]
- 来源：[规则推导] 或 [参考驱动]（标注哪些锚定来自参考方案）
```

> **来源标注的作用**：S0 骨架合规检查时，「参考驱动」项偏离需要更强的理由（用户明确要求的布局意图），「规则推导」项偏离只需说明硬约束冲突即可。此约束针对执行阶段（阶段 A/B）的偏离；骨架阶段（6.3/6.4）的修改不受此约束——骨架一旦通过反思和自检，即为后续执行的唯一依据。

#### 6.3 骨架自检

对照 placement_guide 和 exclusions.json 快速验证：
- [ ] 主通道能否保持 ≥ 900mm？
- [ ] 锚定墙面有无硬约束冲突（如锚定了窗墙作床头墙）？
- [ ] 功能分区间有无空间争夺（如衣柜和床争夺同一面墙的空间）？
- [ ] 锚定墙面的有效段是否足够放下对应家具？

如有冲突，**在此阶段调整骨架**——此时调整代价极低（只是改文字描述），远小于放置家具后再改。

#### 6.4 骨架反思

> **WHY**：骨架是方案的战略决策——锚定哪面墙、动线怎么走、功能区怎么分。战略方向平庸，战术再精细也无法挽救。此时调整代价极低（只是改文字），是质疑自己方案的最佳时机。

在踏出步骤 6 之前，回答以下问题（每个 1-2 句话）：

1. **空间资源审视**：当前骨架是否把最大家具分配给了最有价值的墙面（最长实墙）？还是只因为"这里刚好能放"就锚定了？

2. **方案品质审视**（对照 placement_guide §1.2 的评估维度）：

   - **空间效率**：房间的"战略资源"（最长实墙）和"特色资源"（独立子空间——延伸区、凹位、飘窗区等）是否被分配了与其价值匹配的功能？有没有被降格使用——如独立子空间仅作储物延伸、最长实墙分配给小家具？
   - **功能区联动**：当前的功能区组织是否形成正向联动——A 的定位为 B 创造了最佳条件？有没有一种替代组织方式，能让某个区域从"存放物品"升级为"独立功能体验"？

   > WHY：通过规则验证的方案不一定是好设计。好设计 = 合规 + 空间潜力被充分释放。这两个维度帮助在合规方案中发现"更好"的可能——它们不是检查清单，而是评估视角。具体的改进方案（重新分配家具、调整功能区、局部重组等）会从评估中自然浮现，不需要预设（详见 placement_guide §1.2）。

3. **决策**：
   - 当前骨架明显更优 → 继续执行
   - 替代方案明显更优 → 修改骨架后继续
   - 各有千秋（涉及用户生活方式偏好）→ 调用 AskUserQuestion（见下方规范）

> **注意力预算**：矩形房间的空间效率审视通常简单（大家具→长墙即可），一两句话通过；有独立子空间的房间须认真审视"特色资源"是否被善用。功能区联动对所有房间适用，但简单房间通常一句"无更优联动"即可。参考驱动的骨架已含设计意图——反思聚焦于"参考方案的空间策略是否适合当前房间的比例与墙面条件"，而非质疑参考本身。

## 阶段 A：封闭空间 -- 按骨架落子（锚点 + 主要家具）

> **适用**：封闭空间（卧室、客厅、餐厅、书房）。卫生间不走此阶段。
>
> **执行原则**：按步骤 6 的布局骨架，将锚点和主要家具精确定位。骨架提供全局方向，本阶段负责精确坐标计算。

### 家具分层定义

| 层级 | 定义 | 示例 |
|------|------|------|
| 锚点家具 | 决定房间布局核心定位 | 床、电视柜、餐桌、书桌 |
| 主要家具 | 围绕锚点的功能家具 | 衣柜、沙发、床头柜、餐椅 |
| 辅助家具 | 填充和装饰性家具 | 茶几、边几、梳妆台、落地灯 |

**成套依赖必须同阶段放置**：床+床头柜、书桌+椅子、餐桌+餐椅、床+衣柜（卧室）。

### 6A. 放置前预检

对每件要放置的家具，在确定坐标前检查：
0. **骨架一致性**：本件家具的锚定墙面和朝向是否与步骤 6 骨架一致？若不一致，必须先说明理由（硬约束冲突 / 空间不足），再决定是调整本件位置还是回到步骤 6 修改骨架
1. 是否阻挡门开启（门前净空）？→ 参见 placement_guide §4.2
2. 通行间隙是否满足通道标准？→ 参见 placement_guide §4.1
   注意：先区分「通行间隙」与「使用间隙」（参见 placement_guide §4.1），使用间隙不适用通道标准。
3. 间距分配是否合理？→ 参见 placement_guide §7.6（卧室）或对应房间章节
3b. **墙段穷举输出**（仅卧室衣柜评估前）：从 rawBoundary 提取所有边，**合并方向相同的相邻边为单一墙段**（中间顶点可能是相邻房间边界交点，不构成实际墙角），输出结构化清单后再进入衣柜评估：
   ```
   | # | 墙段 | 坐标范围 | 总长 | 有效段(扣除禁区/窗/床组) | 候选? |
   ```
4. **衣柜布局模式**（仅卧室）：是否已评估衣柜布局模式（传统衣柜布局 / L型靠墙衣柜 / 线性）？特别注意：卫生间门位置对 L 形布局方式选择的影响 → 参见 placement_guide §7.4
5. **前瞻协调**：主要家具的位置是否会阻断辅助家具的必要空间（如衣柜占据窗墙角部）？→ 参见 placement_guide §1 前瞻协调规则
6. **入口动线预判**：从入口门到床区的自然行走路线上，当前规划的家具布局是否会形成瓶颈？特别注意：入口附近两面相邻墙上同时放置家具时，是否会形成"夹道"效应

> bounds 范围、重叠、禁区冲突等几何检查将在写入后由 `validate_layout` 自动完成，无需心算。

如果检查不通过，**在放置前**调整位置或朝向，不要先写入再修正。

### 7A. 写入阶段 A 结果

Write schemes/{zoneId}/modules.json（仅包含锚点 + 主要家具）

**路径规范**：
- 正确：schemes/rz_1/modules.json（分区 1）
- 正确：schemes/rz_2/modules.json（分区 2）
- 错误：schemes/modules.json（此路径不存在，已废弃）

**查找分区**：
1. 读取 schemes/zones.json 获取所有分区 ID
2. 根据分区 ID 写入对应的 schemes/{zoneId}/modules.json

**数据格式**（id 由 Server 在 validate_layout 时自动生成并持久化，禁止手动填写）：
```json
[
  {
    "moduleId": "mod_bed_001",
    "bounds": [[x1,y1], [x2,y2], [x3,y3], [x4,y4]],
    "facing": "north",
    "items": []
  }
]
```

### 8A. 阶段 A 验证

#### 8A.1 布局编译检查（必须）

```
mcp__canvas__validate_layout()
```

自动检测几何错误：越界(E001)、墙体重叠(E002)、柱子重叠(E003)、禁区重叠(E004)、模块间重叠(E005)。

**判断**：
- 验证通过（0 个错误）→ 进入 8A.2 截图设计审查
- 验证失败 → 进入修正循环 A 的局部修正（根据错误报告修正）

#### 8A.2 截图设计审查（单独调用，不与其他工具并行）

```
mcp__canvas__request_background_screenshot(
  projectPath="{当前工作目录}",
  viewport={"mode": "full"}
)
```
→ 仔细查看截图后，对照下方检查清单逐项检查

**对照截图执行设计检查清单**：

**硬性约束（validate_layout 不覆盖，需人工判断）**：
- [ ] H4: 没有家具阻挡门开启（参照 placement_guide §4.2）
- [ ] H5: 通行间隙满足通道标准（参照 placement_guide §4.1）；使用间隙（如床头柜旁）不计入

**骨架合规（全局一致性）**：
- [ ] S0: 最终布局是否实现了骨架的核心意图？逐项对照：(1) 动线走向与骨架一致 (2) 功能分区与骨架一致 (3) 各家具锚定墙面与骨架一致。若有偏离，判定是「合理偏离」（硬约束导致，已在执行阶段说明理由）还是「意外偏离」（需触发全局调整）

**设计规则（优先修正）**：
- [ ] S1: [卧室] 床头墙定位和间距分配合理（参照 placement_guide §7.6）
- [ ] S2: 家具朝向符合 topology_rules / relation_rules
- [ ] S3: [卧室] 衣柜布局模式正确且充足——模式选择、尺寸、位置符合 §7.4；衣柜总宽已利用最长可用墙段（参照 §5.2 必须家具优先）
- [ ] S4: [卧室] 床朝向合规（参照 placement_guide §7.3）
- [ ] S5: [封闭空间] 成套家具完整（参照 placement_guide §5.1）；省略须说明原因
- [ ] S7: 沿墙柜体贴靠墙角，避免卫生死角（参照顶角规则）
- [ ] S8: [卧室] 衣柜存在性——有可用墙面时应布置衣柜（参照 §7.2）
- [ ] S9: [封闭空间] 全局动线连贯——主通道和支线畅通无阻断（对照骨架）。若动线断裂且非单件家具问题，触发全局调整

> 注意：带 `[卧室]` 标注的检查项仅在卧室场景下执行。布置客厅/餐厅/书房时跳过这些项。

**设计品质自检（参考性，不阻塞流程）**：
- [ ] Q1: 站在门口视角，家具视觉重量是否大致均衡（不出现一侧拥挤、另一侧空旷）？
- [ ] Q2: 房间整体填充程度是否令人舒适（留白充足但不过于空旷）？

**判断**：
- 检查全部通过 → 跳到阶段 B
- 单件家具 H/S 项有违反（S0 通过）→ 进入局部修正（Q 项不触发修正循环）
- S0 骨架合规失败（核心锚定偏离 ≥ 2 项）或 S9 动线断裂 → 进入全局调整

### 修正循环 A：两级修正机制

#### 局部修正（最多 1 次）

**触发**：validate_layout 报错或单件家具违反 H/S 检查项。

1. 明确列出所有违规项（编号 + 具体描述）
2. 按以下优先级制定修正方案：
   - 优先**平移**（保持朝向，仅调位置）
   - 其次**旋转**（改朝向 + 调位置）
   - 其次**缩小**（parametric/horizontal_fill 类型在 limits 内缩小）
   - 其次**替换**为更小尺寸的同功能模块
   - 最后**移除**无法修正的家具（报告中说明原因）
3. Read 当前 modules.json（确认最新状态）
4. 修改违规模块的 bounds/facing
5. Write 保存修正结果
6. 再次调用 `mcp__canvas__validate_layout()` 确认几何错误已消除

**修正原则**：最小化变动，只改违规家具，不动已通过验证的家具。

#### 全局调整（最多 1 次/整个任务）

**触发**：S0 骨架合规失败（核心锚定偏离 ≥ 2 项）、S9 动线断裂、或功能分区失败（非单件家具问题，而是多件家具的组合效果偏离了骨架意图）。

**两步走策略**：

1. **先尝试联合调整**：保留已放置家具，但允许移动/缩小/替换**任意已放置模块**（不限于违规的那件），以解决全局问题。必须说明"为什么需要动已放置的家具、调整了哪些模块、预期效果"。调整后重新 Write → validate_layout → 截图审查。

2. **调不通再骨架重做**：如果联合调整无法解决（如动线根本走不通、需要换锚定墙面），则回到步骤 6 修改布局骨架 → 清空阶段 A 结果 → 从阶段 A 重新开始。必须说明"骨架哪里有问题、修改了什么"。若骨架曾经 AskUserQuestion 与用户确认，骨架重做前须再次告知用户。

**兜底**：骨架重做后仍失败 → 保留当前最佳结果，在报告中说明空间限制。

## 阶段 B：封闭空间 -- 辅助家具

> **适用**：封闭空间（卧室、客厅、餐厅、书房）。卫生间不走此阶段。

**前提**：阶段 A 家具已验证通过（或已修正）。

### 6B. 规划辅助家具

1. Read 当前 schemes/{zoneId}/modules.json（获取阶段 A 已放置的家具）
2. **建立可用墙面清单**：
   a. 从房间边界提取每一条边作为墙段（与 §7.4 衣柜评估相同的穷举方式，含 L 形延伸区、凹位等异形区的每一面墙）
   b. 按 placement_guide §1.3 的判断方法，将每条墙段标注为「异形区」或「主体区域」
   c. 对每段墙，扣除阶段 A 已放置家具占据的区段，计算剩余连续空段
   d. 将可用墙段分为两组：①异形区残余墙段 ②主体区域空闲墙段
3. **按搜索顺序选择墙面**（placement_guide §1.3【必须】）：先在①异形区残余墙段中为辅助家具匹配位置，仅当①中无满足条件的墙段时，再搜索②主体区域（参照各模块 relation_rules）
3b. **【必须】必须家具空间保护**：在为可选家具分配墙段前，检查阶段 A 的衣柜是否充足——若衣柜总宽 < 可用墙段中最长一段的长度，该墙段**保留给衣柜延伸**（回阶段 A 补充衣柜后重新进入阶段 B），不分配给可选家具（参照 placement_guide §5.2 必须家具优先规则）
3c. **【必须】骨架意图守护**：对每件拟放置的辅助/可选家具，检查拟放置位置是否违反骨架核心意图（如"入口侧留空"、"主通道走向"）。特别注意：**入口缓冲区**——从入口门到最近功能区（床区/沙发区）的自然行走路径上，辅助家具不得将路径上任何截面的净宽压缩到低于主通道标准（900mm）。违反则跳过该位置；所有候选均违反则放弃该家具
3d. **【必须】可选家具两步验证**：对仅匹配 `optionalTags` 的家具（如梳妆台、斗柜），放置前必须通过两步验证：
   - **第一步：位置可行性** — 是否存在至少一个候选位置，满足该家具所有【必须】级 topology_rules 和 relation_rules？
   - **第二步：品质无损** — 该候选位置是否**无需偏离**任何【建议】级规则（入口门缓冲区、床脚避让等）？
   → 两步均通过 → 允许放置
   → 任一步不通过 → **放弃该家具**，在报告中说明原因
   > WHY：可选家具是"锦上添花"，不应为了放置它而牺牲通道品质或违反设计规范。偏离建议级规则是"不放"的信号，而非"硬放"的依据。
4. 对每件辅助家具执行同样的放置前预检（同 6A）

### 7B. 写入完整结果

Write schemes/{zoneId}/modules.json（包含全部家具：阶段 A 已有 + 阶段 B 新增）

**注意**：Write 时必须包含阶段 A 已有的家具，不能只写新增的辅助家具。

### 8B. 最终验证

#### 8B.1 布局编译检查（必须）

```
mcp__canvas__validate_layout()
```

自动检测全部家具（阶段 A + B）的几何错误。

**判断**：
- 验证通过（0 个错误）→ 进入 8B.2 截图设计审查
- 验证失败 → 进入修正循环 B（根据错误报告修正）

#### 8B.2 截图设计审查（单独调用，不与其他工具并行）

```
mcp__canvas__request_background_screenshot(
  projectPath="{当前工作目录}",
  viewport={"mode": "full"}
)
```
→ 仔细查看截图后，对照下方检查清单逐项检查

**对照截图执行设计检查清单**（覆盖全部家具，执行 8A.2 全部检查项 + 以下增量项）：

**设计规则（增量）**：
- [ ] S5b: 有窗户的卧室/客厅应有窗帘（窗帘属于辅助家具，在阶段 B 补充）
- [ ] S5c: [封闭空间] 可选家具（梳妆台、边柜等）未紧邻入口门放置（门边缘 800mm 内）
- [ ] S6: 家具间距合理（参照 placement_guide §8.1、§4.2）

**判断**：
- 检查全部通过 → 跳到报告结果
- 有违反 → 进入修正循环 B

### 修正循环 B（最多 1 次）

步骤同修正循环 A 的局部修正（包含修正后重新调用 `validate_layout` 确认）。

**如果修正后仍有违规**：
→ 移除违规的辅助家具，保留核心布局（锚点+主要家具）
→ 再次调用 `validate_layout` 确认核心布局无几何错误
→ 在报告中说明被移除的家具及原因

## 卫生间布置流程

> **适用**：步骤 5 判断为卫生间的分区（tags 含 shower/toilet/washing）。
> **核心原则**：卫生间布置是"模板匹配 + 参数化微调"，不是"创造性规划"。
> **参照规则**：placement_guide §1-§6（通用）+ **§11（卫生间专项）**

### BT1. 测量分区尺寸

从 zone.rawBoundary 计算：
1. **最小外接矩形**：取 rawBoundary 的 AABB（轴对齐包围盒）
2. **短边** = min(宽, 高)，**长边** = max(宽, 高)
3. **长宽比** = 长边 / 短边
4. **面积** = rawBoundary 多边形面积

### BT2. 识别门窗位置

从 openings.json 中筛选当前分区相关的门窗：
- 门的位置（在长边还是短边）→ 影响洁具排列起点方向
- 窗的位置 → 影响花洒墙面选择和淋浴区朝向

### BT3. 选择布局模式

参照 **placement_guide §11.3** 的决策树，用 BT1 的测量数据逐步判断，确定模式字母（A/B/C/D/E）和洁具排列起点方向。

### BT4. 定位洁具

参照 **placement_guide §11.4** 对应模式的详细规则：
1. 从 module_library.json 选择匹配的模块（按 tags 筛选 shower/toilet/washing）
2. 对每个洁具确定：位置（贴靠哪面墙、哪个角）、朝向（facing）、尺寸

**模块选型参照**：placement_guide §11.4 底部「模块选型速查表」

### BT5. 参数化微调

对 horizontal_fill / parametric 类型的模块，根据可用空间在 module_library 中该模块 `morphology.limits` 范围内计算实际尺寸。

### BT6. 写入并验证

1. Write schemes/{zoneId}/modules.json（包含全部洁具）
2. 调用 `mcp__canvas__validate_layout()` 编译检查
3. 若通过 → 截图设计审查（对照下方卫生间专用检查清单）
4. 若未通过 → 根据错误调整，最多修正 1 次

**卫生间截图审查清单**：

**硬性约束（validate_layout 不覆盖，需人工判断）**：
- [ ] BT-H1: 通道宽度满足 §4.1 次通道标准
- [ ] BT-H2: 无洁具阻挡门开启（参照 §1 避门规则）

**设计规则（优先修正）**：
- [ ] BT-S1: 洁具排布顺序正确——台盆→坐便器→淋浴区，从门端到深处（参照 §11.1）
- [ ] BT-S2: 台盆贴靠墙角，无卫生死角缝隙（参照 §11.1）
- [ ] BT-S3: 坐便器在可用墙段内居中（参照 §11.1）
- [ ] BT-S4: 淋浴屏两端贴靠实墙，无悬空间隙；L 形房间中干区侧边沿与台阶墙齐平（参照 module_library topology_rules）
- [ ] BT-S5: 定制台盆已最大化台面（horizontal_fill 到位）
- [ ] BT-S6: 花洒安装在实墙（非窗墙）（参照 §11.5）

> 卫生间无阶段 B（无辅助家具空间）。审查通过后直接跳转「报告结果」。

## AskUserQuestion 使用规范

> **WHY**：将决策权在战略分歧处交还用户——AI 负责发现选项和分析取舍，用户负责最终审美判断。这是系统的"终极留白"。

**触发原则**：存在战略级替代方案，且无法仅凭设计规范判断优劣时触发。

**典型场景**（非穷举，帮助校准"战略级"的量级）：
- 功能区组织方式的替代方案——如将子空间从储物延伸升级为独立功能区（功能区联动效应）
- 改变锚点家具的锚定墙导致整体功能分区重组（动线策略重写）
- 功能区内部核心家具的墙面选择——不同墙面决定用户在该区域的使用姿态和视线方向，属于生活方式偏好

**提问格式**：
```
当前方案：[一句话核心特征]
替代方案：[一句话核心特征]
核心取舍：[选A得到什么/失去什么；选B得到什么/失去什么]
```

**禁止**："您觉得这样好吗？"等笼统提问；超过 2 个选项；战术级问题（间距微调、同一墙面上的位置偏移）。注意：功能区核心家具的**墙面选择**（如西墙 vs 南墙）不是"朝向微调"——它决定用户的使用姿态，属于战略级。

**SubAgent 上下文**：layout-agent 不可直接调用 AskUserQuestion——应将分歧详情报告回主控 Agent，由主控决定是否向用户提问。

## 常见错误

| 错误 | 正确做法 |
|------|----------|
| 写入 schemes/modules.json | 写入 schemes/{zoneId}/modules.json |
| 一次性放置全部家具再验证 | 分阶段放置，每阶段编译检查+截图审查 |
| 跳过 validate_layout | 每次 Write 后必须调用 validate_layout 编译检查 |
| 自审结果只在思考中分析 | 必须输出检查清单的 PASS/FAIL 结果 |
| L 形衣柜：未区分"传统布局"和"L型靠墙"两种方式，一律按 L型靠墙处理 | 先根据卫生间门位置选择布局方式（传统 vs L型靠墙），再按对应方式布置（见 placement_guide §7.4） |
| L型靠墙：忽略内角门开启遮挡，导致内角侧柜门无法打开 | L型靠墙必须检查内角遮挡：超出另一段端面的部分 ≥ 600mm，否则用移门或放弃该墙角（见 placement_guide §7.4） |
| 跳过截图设计审查 | 编译通过后仍须截图检查 |
| 发现违规但不修正就继续 | 编译错误或设计违规必须修正后才能继续 |
| 阶段 B 只写新增家具 | 必须合并已有+新增全部写入 |
| 修正循环超过 1 次仍失败 | 移除违规家具，保留核心布局 |
| 跳过 placement_guide | 必须读取并遵守规范 |
| 卫生间走封闭空间流程 | 根据 tags 判断空间类型，卫生间走独立的卫生间布置流程 |
| 卫生间执行衣柜评估/床朝向决策 | 卫生间无这些步骤，只有测量→匹配→定位→验证 |
| 骨架反思变成冗长自我对话 | 矩形房间每个问题一句话即可；有独立子空间的房间重点回答 Q2 但控制在 3-4 句话 |
| 对每个微小决策都调用 AskUserQuestion | 仅在战略级替代方案且无法自行判断优劣时触发（见使用规范） |
