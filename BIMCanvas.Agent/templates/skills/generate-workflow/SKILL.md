# 布置工作流

```
1.感知 → 2.规划(2.1→2.2→2.3) → 3.尝试↔修改 → 4.优化 → 5.汇报
 加载      语义方案 v0.1→v0.3     坐标+验证       设计品质      交付
 上下文    熵减：粗→细            Layer 1 闭环     Layer 2 改善
```

---

## 语义方案

语义方案是**持续演进的决策文本**——用自然语言描述家具与墙面的语义映射（"床在西墙"、"衣柜沿北墙线性排列"），不是精确坐标（那是 modules.json 的职责）。

**【必须】每完成一个子阶段（2.1/2.2/2.3），立即将当前版本输出到对话中**——这是独立的对话消息，不是 thinking 中的草稿。

WHY：在 thinking 中保留未输出的决策 = 未锚定 = 可以被推翻 = 你会反复重新评估。输出到对话中 = 白纸黑字 = 锚定 = 后续在此基础上推进，而非从头来过。

### 演进规则

```
v0.1  空间骨架     动线方向 + 纵深层次 + 采光轴 + 初步设计意图     （Stage 2.1）
v0.2  主体框架     主要家具墙面归属 + 分区结论 + 设计目标          （Stage 2.2）
v0.3  完整方案     可选家具 + 设计目标细化 + 全部确认              （Stage 2.3）
```

确定性标记：
- `✓` 已确认——不再变动
- `~` 暂定——后续可能因联动调整
- `→ 待用户确认` 战略选择，需要 AskUserQuestion

## 1. 感知

> WHY：纯机械操作，不占认知资源。先建立感官输入，后续阶段才有决策素材。

1. **截图**（单独调用，等收到后再继续）— `mcp__canvas__request_background_screenshot`，用 `viewport: {"id": "rz_1"}` 聚焦目标区域，或省略 viewport 看全屋。截图工具直接返回图片；若看不到内容，用 Read 查看返回的文件路径
2. **并行读取**：references/design_principles.md + references/design_evaluation.md + modules/module_library.json + schemes/zones.json + computed/exclusions.json
3. **边界语义**：调用 `get_zone_boundaries` — 获取每条边的类型（wall/passage/door/window）和坐标。后续所有阶段基于此墙面语义描述空间，不回溯 rawBoundary 原始坐标
4. **加载房间策略**：根据 Zone tags 读取对应策略参考文件（见系统注入的"策略参考文件"路径）

| tags 特征 | 空间类型 | 策略文件 |
|-----------|---------|---------|
| sleep / bedroom | 卧室 | bedroom.md |
| shower / toilet / washing | 卫生间 | bathroom.md |
| rest / tvMedia / dining / circulation | 客餐厅 | livingroom.md |

WHY（边界语义）：`get_zone_boundaries` 返回的是**预处理的墙面结论**（"北墙门右段 4070mm"），而非原始坐标列表。当数据本身是结论形态时，Agent 在物理上无法"重新分析"——这是结构性防重分析措施。

**模块数据**：契约层（id/tags/size）用于选择，意图层（agent_config: morphology + topology_rules + relation_rules）用于布置决策。按 Zone 的 tags/optionalTags 筛选兼容模块——匹配 tags 为必备家具，仅匹配 optionalTags 为可选家具。

## 2. 规划

> WHY：先想清楚整体方案再动手放家具。规划阶段产出语义方案 v0.1→v0.3，是全局决策的渐进外化。

### 精度边界

规划阶段全程只做**空间预演级别的粗估**，不计算精确坐标：

| 规划阶段允许 | 规划阶段不允许 |
|------------|-------------|
| "北墙 4070mm 放衣柜，深 600mm，通道约 950mm" | 计算 bounds 四角坐标 |
| "西墙放床+两柜约 2700mm，剩余 2150mm" | 逐件家具确定精确 X/Y 坐标 |
| "延伸区 1700×1550，扣除衣柜后约 950mm 可用" | 验证家具边界是否在 innerBoundary 内 |

WHY：在 thinking 中算一次坐标→发现需要验证碰撞→再算→发现新冲突→又算...这个循环会持续到 thinking 停止响应。validate_layout 用 0.1 秒完成你在 thinking 中做不完的事。规划阶段只需回答"放得下吗？通道够吗？"——粗估足够。

### 2.1 基础规划 → 语义方案 v0.1

以 design_evaluation.md 的品质维度为指引，完成空间的初步阅读：

- **动线方向**：人从入口进来自然往哪走？
- **纵深层次**：哪里是前场（过渡），哪里是深处（私密）？
- **采光轴**：窗户在哪，光怎么进来？
- **初步设计意图**：这个空间应该有怎样的体验序列？

产出语义方案 v0.1——只有空间骨架，不涉及任何家具决策。

### 2.2 分区设计 → 语义方案 v0.2

**【必须】加载分区 Skill**：加载 generate-zoning Skill，完成空间功能定义。

WHY：分区 Skill 不只是处理"复杂空间"——它负责空间功能定义。"不分割"是合法结论，不是跳过分区的理由。功能定义是布置的前提，需要经过显式审视才能确立。Skill 基于 v0.1 已产出的空间骨架做判断，不重新推导空间信息。

执行顺序——**先家具，再分区**：

**Step 1：确定主要家具的最优位置**

在不考虑分区的前提下，用房间策略的优先级规则确定主要家具应该在哪面墙。

WHY：家具位置由**物理约束**（墙面长度、门位置、窗位置）决定，这些约束来自空间本身，不来自概念上的分区划分。无论怎么分区，西墙还是最长的实墙，北墙右段还是最长的非窗非门段——物理事实不因概念组织而改变。

**Step 2：用家具位置过滤分区方案**

确定了主要家具需要哪些墙面资源后，检查哪些分区方案与这些需求兼容：

- 分区切割打断了家具需要的连续墙面？→ 该分区方案被淘汰
- 分区后家具仍能正常布置？→ 该方案可行，保留

这是**单向约束**：物理空间 → 家具最优位置 → 过滤分区方案。不存在循环依赖。

**Step 3：确定分区结论 + 功能定义**

- 多个可行方案对用户日常体验有质的差异 → 战略选择 → AskUserQuestion
- 确定分区（或"不分割"）后，进行功能定义
- 产出语义方案 v0.2：分区结论 + 主要家具决策 + 设计目标

**【必须】Step 3 完成后立即输出 v0.2**——不在 thinking 中继续分析可选家具。v0.2 是锚定点：主要家具位置和分区结论一旦输出，后续的可选家具探索（v0.3）基于此展开，不回溯。

→ Skill 产出 subZones 时：调用 `get_zone_boundaries` 获取子 zone 边界语义（含 passage 段）
→ Skill 判定无需分区时：直接继续

**【必须】位置暂定原则**：v0.2 中主要家具标记为 `~`（暂定），因为可选家具的加入可能发现更优的全局布局。

WHY：顺序分配（锚点→主要→可选→间距）让先决策的大件占据最优位置，后决策的小件只能在剩余空间中选择。这制造了虚假的"唯一可行位"，遮蔽了"调整大件为小件腾位"可能带来的全局更优方案。

### 2.3 丰富细节 → 语义方案 v0.3

将主要家具之外的家具纳入语义方案：

- 可选家具（梳妆台、展示柜等）：扫描候选墙段，标注位置
- 附属家具（窗帘、床头柜等）：跟随锚点家具
- 判断是否存在战略选择（可选家具位置影响日常体验）→ AskUserQuestion

**决策收敛**：列出全部选择点，逐一标注"战略/战术"：
- **战略选择**（家具墙面归属、空间功能定位等，影响日常体验）→ AskUserQuestion
- **战术选择**（间距微调、同墙面位置偏移等，由规范决定）→ 自主决策

> 判断标准：
> - **战术**：硬约束直接排除至仅剩一个可行方案，或差异仅涉及精确坐标/间距调整
> - **战略**：存在两个及以上可行方案，且差异涉及用户日常体验

**【必须】唯一解回溯检查**：当某选择点"只剩一个可行方案"时，检查该唯一性的来源——是硬约束（空间物理限制、【必须】规则）直接排除的，还是前序决策间接消除的？

- 硬约束排除 → 战术，自主决策
- 前序决策消除 → 回到前序决策，评估是否存在"调整前序决策为当前家具腾出替代位置"的方案。如果存在，当前选择点是战略选择

WHY：前序决策消除替代选项后标注"唯一解=战术"，是自证预言——先做了一个选择，再用它的结果证明后续没有选择。回溯检查打断这条错误推理链。

> ⚠ 两个检验信号：(1) 在 thinking 中花费显著推理论证一个方案优于另一个——取舍 = 战略选择的特征；(2) "唯一可行位"的唯一性依赖于前序决策而非空间物理限制——自证预言 = 分类错误的特征。

v0.3 完成后，所有位置升级为 `✓`（确认）。此时语义方案包含：全部家具墙面归属、设计目标声明（参照 design_evaluation.md 品质维度）。

> WHY（设计目标）：设计目标不是额外负担——它是后续执行和审查的锚点。有了"进门直达台盆"这个目标，选墙时就不需要纠结公式；审查时只需验证"进门后首个使用点是台盆吗？"。目标驱动让每个决策都有判据。

## 3. 尝试 ↔ 修改

> **核心姿态：允许试错。** 像人类设计师一样工作——先放下去看效果，出错了调整就好。validate_layout 是安全网，它比心算更快、更准。不需要在脑中完成所有验证后才敢动手。
>
> WHY："一次完美"的心理预期是 thinking block 膨胀的隐性推手。快速迭代（写入→验证→修正）的成本远低于在 thinking 中预防所有问题的成本。

### 手动检查清单

Agent 在写入前**只需**检查以下 validate_layout 无法检测的语义问题，不做其他预验证：

| 检查项 | WHY validate_layout 检测不到 |
|--------|---------------------------|
| 门开启方向与家具是否冲突 | validate_layout 检查门扇禁区重叠，但不理解"门能不能顺畅打开" |
| 通行间隙 vs 使用间隙的类型区分 | validate_layout 不区分"人要从这里走过"和"人在这里伸手操作" |
| 前瞻协调：主家具是否阻断可选家具的策略位置 | 这是语义层面的设计意图，不是几何计算 |

**其余全部交给 validate_layout**：越界(E001)、墙体重叠(E002)、柱子重叠(E003)、禁区重叠(E004)、模块间重叠(E005)。

### 放置

按语义方案 v0.3 + design_principles + 房间策略约束 + module_library agent_config，精确定位全部家具（锚点→主要→可选，一次性写入）。

### 写入

Write `schemes/{zoneId}/modules.json`，每个模块包含 moduleId、bounds（四点坐标）、facing、items。
分区场景写入路径：`schemes/{parentZoneId}/{childZoneId}/modules.json`（如 `schemes/rz_3/dz_1/modules.json`）。

### 验证闭环

**【必须】**每次 Write 后调用 `mcp__canvas__validate_layout(zoneIds=[...])`。分区场景传入子 zone 列表（如 `zoneIds=["dz_1", "dz_2"]`）。

WHY：validate_layout 是确定性几何计算，比 LLM 心算更快更可靠。它是"允许试错"姿态的安全网——放心写入，让工具替你检查。

### 修正循环（最多 2 轮）

验证失败时：
1. 列出所有违规项
2. 按修正优先级处理（见 design_principles）：**平移** → **旋转** → **缩小**（limits 内）→ **替换**同功能更小模块 → **移除**
3. Read 当前 modules.json → 修正 → Write → 再次 validate_layout

> WHY：修正优先级从最小变动到最大变动——平移保留原始设计意图，移除是最后手段。

**兜底**：2 轮修正后仍失败 → 移除违规家具，保留核心布局，报告中说明原因。

### Layer 1 验证

validate_layout 通过后，继续完成工程合规验证：

1. **可达性验证**（【必须】用坐标算术证明，禁止凭印象声称"满足"）：
   从入口走到每件家具使用面和每扇窗户，逐段计算最窄处，比对 design_principles 通道标准和房间策略专项标准。
   报告格式（【必须】逐条列出，禁止用表格替代——逐条格式展示每条通道的推理链，表格隐藏设计根因）：
   `[起点] → [终点]：最窄处 [物体A] ↔ [物体B] Xmm（标准≥Ymm）✓/✗`
   示例：`[门] → [台盆使用面]：最窄处 台盆 ↔ 西墙 1050mm（标准≥900mm）✓`
2. **功能完整性**：zone.tags 中每个功能标签至少有一个对应模块 → 缺失则补充

Layer 1 任何项未通过 → 修正（最多 2 轮）→ 重新验证
全部通过 → 进入 Stage 4

## 4. 优化

> WHY：Layer 1 通过 = 工程合规（能用）。优化阶段的目标是"从合格到优秀"——主动寻找改善机会，不是被动检查是否达标。

**截图**（单独调用）→ 逐项审查：

对照语义方案 v0.3 中声明的设计目标，参照 design_evaluation.md 的五个品质维度：
- 声明了动线目标？→ 验证入门到首个使用点的路径
- 声明了功能叙事目标？→ 验证墙面/区域的家具连贯性
- 声明了空间节奏目标？→ 验证隐私/密度递进
- 声明了采光通风目标？→ 验证采光轴畅通
- 其他已声明的目标？→ 逐条核实

识别改善机会 → 每个维度最多一次调整尝试 → 调整后重新 validate_layout 确认工程合规

> 典型优化场景：梳妆台布置在远离窗户端，导致主动线在中间被挤压。移到靠窗端后，挤压只发生在动线末端，影响大幅降低。原布局完全合规——这是"合格到优秀"的品质提升。

**贯穿检查**：
- **策略一致**：最终布局实现了语义方案的核心意图
- **规则遵从**：房间策略的硬约束全部满足
- **分区连贯**（分区场景）：相邻子分区之间的动线连贯

**降级判断**：截图无法清晰辨别时，注明"品质评估依赖数字验证 + 策略交叉检查"。
