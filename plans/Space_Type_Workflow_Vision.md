# 空间类型工作流架构设想

> **状态**：讨论稿，待深入讨论后逐步实施
> **日期**：2026-03-03
> **背景**：当前 generate-workflow 用一套流程处理所有房间类型，但不同空间类型的布置逻辑差异极大，导致流程中混入大量条件分支（如"仅卧室"的衣柜墙面评估），降低了 Agent 的执行效率和规则清晰度。

---

## 一、核心观点

不同空间类型的布置流程/规则天差地别，应当拆分为独立的 Skill，而非用一个 `placement_guide.md` 管理所有设计逻辑。

## 二、空间分类

### 1. 开放空间（大面积，如客餐厅一体）

**核心特征**：需要先「分区」再「布置」。

**设计流程**：
1. 根据走廊/过道/房型特点，先规划过道动线
2. 通过过道/建筑轮廓（如内凹角）将大空间切分为规则的小空间
3. 根据小空间特征（大小、是否靠近主窗）区分功能区（客厅区、餐厅区）
4. 修改 `schemes/zones.json`，将大分区拆分为多个设计区
5. 在每个设计区内按「封闭空间」逻辑布置家具

**关键差异**：当前工作流完全没有「分区」环节——它假设 zones.json 已经是 1 房间 = 1 分区。

### 2. 封闭空间（中等面积，如卧室、书房）

**核心特征**：空间边界明确，按「锚点 → 主要 → 辅助」三阶段布置。

**设计流程**（即当前 generate-workflow 的核心逻辑）：
1. 确定锚点家具的位置/朝向/选型（如床头墙选择）
2. 确定主要家具的位置/朝向/选型（如衣柜墙面选择）
3. 补充辅助家具（如梳妆台、落地灯）
4. 全程注意成套依赖（床+床头柜、书桌+椅子）

**房间类型专项**：
- 卧室：衣柜应铺满整面墙、床头靠实墙、侧对窗户布局
- 书房：书桌朝向需考虑采光和门的位置
- 其他封闭空间各有专项规则

### 3. 特殊空间（小面积/狭窄，如卫生间、厨房）

**核心特征**：空间狭窄，布局方案有限，本质是「模式匹配」——根据尺寸比例和门窗位置选择最优模板，而非自由规划。

**设计流程**：
1. 识别房型特征（尺寸、长宽比、门窗位置）
2. 匹配最优布局模板
3. 在模板基础上微调（参数化洁具尺寸、精确定位）

**与封闭空间的关键差异**：
- 没有「锚点朝向决策」——洁具位置由房型决定
- 没有「衣柜墙面评估」——不存在这个概念
- 没有「辅助家具」阶段——空间不允许额外填充
- 避窗规则相反——卧室避窗，卫生间淋浴区可临窗

## 三、卫生间布局模式（来自用户截图）

根据 5 张典型卫生间布局截图，总结以下模式：

### 模式 A：窄长型单侧线性

**房型特征**：宽度 ≤ 1800mm，门在短边，窗对门
**布局**：所有洁具沿同一侧墙线性排列
**顺序**（从门到窗）：台盆 → 马桶 → 淋浴间
**适用**：最窄的卫生间，对侧保留完整通道

### 模式 B：窄长型 L 形布局

**房型特征**：宽度略大于模式 A，门在短边
**布局**：淋浴间占满远端（横向），马桶/台盆沿侧墙
**特点**：淋浴屏两端贴靠实墙，形成 L 形动线

### 模式 C：近方形分墙布局

**房型特征**：长宽比接近 1:1，面积中等
**布局**：洁具分布在不同墙面
**特点**：台盆占一面墙，马桶另一面，淋浴间占角落

### 模式 D：大型卫生间三面分布

**房型特征**：面积较大
**布局**：三面墙各分配一类洁具
**特点**：空间充裕，可考虑浴缸替代淋浴房

### 模式 E：半卫（无淋浴）

**房型特征**：小面积，无淋浴需求
**布局**：仅马桶 + 台盆并列
**特点**：最简配置

### 模式选择逻辑（待细化）

```
if 无淋浴需求 → 模式 E
elif 宽度 ≤ 1800mm → 模式 A（单侧线性）
elif 长宽比 > 1.5 → 模式 B（L 形）
elif 长宽比 ≈ 1.0 && 面积中等 → 模式 C（分墙）
elif 面积 > 阈值 → 模式 D（三面分布）
```

> **待讨论**：具体的尺寸阈值和门窗位置对模式选择的影响需要更多案例验证。

## 四、Skill 拆分架构设想

### 当前架构

```
generate-workflow/SKILL.md          一个 SKILL 处理所有房间
placement_guide.md                  一个文件包含所有设计规则
```

### 目标架构

```
skills/
├── generate-workflow/SKILL.md              → 路由器：识别空间类型 → 分发
├── generate-open-space/SKILL.md            → 开放空间：分区 + 逐区布置
├── generate-enclosed-space/SKILL.md        → 封闭空间：锚点 → 主要 → 辅助
└── generate-bathroom/SKILL.md              → 卫生间：模式匹配 → 选模板 → 微调

knowledge/
├── placement_guide_common.md               → 通用规则（通道宽度、门前净空等）
├── placement_guide_enclosed.md             → 封闭空间规则（卧室、书房专项）
├── placement_guide_open.md                 → 开放空间规则（分区策略、客餐厅）
└── placement_guide_bathroom.md             → 卫生间规则（布局模式、洁具定位）
```

### 路由逻辑

generate-workflow 变为路由器，根据分区的 tags/type 分发：

```
读取 schemes/zones.json
for each zone:
    if zone.tags 包含 shower/toilet/washing → 调用 generate-bathroom
    elif zone 是大空间且未细分 → 调用 generate-open-space
    else → 调用 generate-enclosed-space
```

### 公共层

以下规则跨空间类型通用，应提取到公共层：
- 通道宽度标准（§4.1）
- 门前净空（§4.2）
- validate_layout 编译检查流程
- 截图设计审查流程框架
- 修正循环机制（平移 → 旋转 → 缩小 → 替换 → 移除）

## 五、待讨论的开放问题

1. **开放空间的分区算法**：如何自动识别过道和功能区？是否需要 Server 端提供分区建议工具？
2. **卫生间模式的匹配细化**：5 种模式的精确触发条件（尺寸阈值、门窗位置组合）
3. **厨房是否也归为「特殊空间」**？厨房的布局逻辑（操作台动线：洗→切→炒）也是模板匹配
4. **Skill 间的调用关系**：路由器是否需要跨 Skill 调用，还是由 Agent 主循环根据 zones 依次调用？
5. **placement_guide 的拆分粒度**：公共层应该多薄？是否每个 Skill 内联自己的规则更高效？
6. **渐进实施路径**：先实现哪个空间类型的独立 Skill？（建议：卫生间，因为差异最大、模式最清晰）
