# 空间类型工作流架构设想

> **状态**：Phase 1-2 已实施完成（placement_guide v2.0 + SKILL.md v2.0）
> **日期**：2026-03-03
> **版本**：v2（融入技术分析和决策记录）

---

## 一、背景与动机

### 问题

当前 `generate-workflow/SKILL.md` 用一套流程处理所有房间类型。这导致两个问题：

1. **流程污染**：卧室特有的"衣柜墙面评估"、"锚点朝向决策"出现在通用阶段 A 中，布置卫生间时产生无效步骤
2. **规则冲突**：卧室的避窗规则（床头不靠窗）与卫生间相反（淋浴区可临窗）；同一个 placement_guide 中的规则互斥，Agent 需要自行判断哪条适用

### 根本原因

不同空间类型的布置逻辑在本质上不同：

| 空间类型 | 布置本质 | Agent 的角色 | 自由度 |
|---------|---------|-------------|--------|
| 封闭空间（卧室、书房） | **空间规划** — 在二维平面自由定位 | 设计师（创造性决策） | 高 |
| 特殊空间（卫生间） | **模板匹配** — 根据尺寸选最优解 | 执行者（查表+微调） | 极低 |
| 开放空间（客餐厅一体） | **先分区后规划** — 需要额外的空间划分阶段 | 规划师+设计师 | 最高 |

封闭空间的三阶段流程（锚点→主要→辅助）强行套用在卫生间上不合理：卫生间没有"锚点朝向决策"（洁具位置由房型决定），没有"辅助家具"阶段（空间不允许额外填充），没有"衣柜墙面评估"。

## 二、空间分类与布置规则

### 2.1 封闭空间（卧室、书房等）

**适用房间**：主卧、次卧、书房、儿童房等有明确墙体围合的中等面积房间。

**布置流程**：三阶段递进

```
阶段 A：锚点家具 → 确定房间布局的核心定位
         ↓
       主要家具 → 围绕锚点展开的功能家具
阶段 B：辅助家具 → 填充和装饰
```

**阶段 A 详细逻辑**：
1. **选择锚点**：每个房间有一个核心锚点家具，它决定了整个房间的布局方向
2. **确定锚点朝向**：结合 agent_config 中的 topology_rules（如"靠实墙"）和 placement_guide 的朝向规则
3. **围绕锚点规划主要家具**：主要家具的位置受锚点约束，如衣柜选墙需避开床头墙
4. **处理成套依赖**：床+床头柜、书桌+椅子、餐桌+餐椅必须同阶段放置

**房间类型专项规则**：

| 房间类型 | 锚点 | 主要家具 | 辅助家具 | 专项设计要点 |
|---------|------|---------|---------|------------|
| 主卧 | 床 | 衣柜、床头柜×2 | 梳妆台、落地灯 | 侧对窗户布局；衣柜铺满有效段全长；床头靠实墙（非窗墙、非门墙） |
| 次卧 | 床 | 衣柜、床头柜≥1 | 书桌（可选） | 同主卧布局逻辑；紧凑时省略窗侧床头柜；衣柜按可用墙面决定是否布置 |
| 书房 | 书桌 | 书柜 | 椅子 | 书桌朝向考虑采光（侧光优于背光）和门的位置（不背对门） |

**核心设计原则**：
- **间距分配**：先为两侧功能区各预留最小间距，剩余空间偏向使用侧
- **衣柜设计**：应选最长连续有效墙段，标准柜体阵列+定制柜体补充剩余宽度，形成连续柜面
- **成套依赖**：省略任何成套家具必须给出原因（如"使用侧<500mm，省略窗侧床头柜"）

### 2.2 特殊空间（卫生间）

**适用房间**：主卫、公卫、客卫等卫生间。

**与封闭空间的本质差异**：

卫生间面积狭窄（通常 3-6㎡），不同尺寸/比例的卫生间对应**固定的最优布局**，自由度极低。布置的本质不是"创造性规划"，而是"模式匹配+参数微调"。

| 维度 | 封闭空间（卧室） | 特殊空间（卫生间） |
|------|----------------|-------------------|
| 布置思维 | 空间型 — 在二维平面**自由定位** | 流程型 — 洁具沿墙**线性排列**，有严格顺序 |
| Agent 角色 | 设计师（创造性决策） | 执行者（查表+微调） |
| 决策流程 | 锚点朝向→主要家具→辅助家具 | 测量尺寸→匹配模板→参数化定位 |
| 约束方式 | 间距精细化（200/500/600mm 档位） | 宽度阈值判定（≤1800mm 触发集中布置） |
| 家具关系 | 树型依赖（衣柜依赖墙选、床头柜成对） | 链型排列（台盆→马桶→淋浴，依次相邻） |
| 避窗规则 | 床头**避窗** | 淋浴区**可临窗**（完全相反） |
| 自由度 | 多种合理方案 | 通常只有一种最优解 |
| 辅助家具 | 有（梳妆台、灯等） | 无（空间不允许额外填充） |

**布置流程**：模板匹配

```
测量分区尺寸（宽度、深度） → 识别门窗位置
  → 查 placement_guide 决策树，选择布局模式（A/B/C/D/E）
    → 按模式放置洁具（台盆、马桶、淋浴屏/淋浴房）
      → 参数化微调（台盆宽度 horizontal_fill、淋浴屏尺寸 parametric）
```

**卫生间核心设计规则**：
- **洁具排布顺序**（从入口到深处）：台盆（进出洗手方便）→ 马桶（隐私）→ 淋浴区（最深处，干湿分离）
- **台盆贴角**：台盆贴靠相邻墙角，不留无功能间隙（窄缝积灰难清洁）
- **马桶居中**：马桶在其可用墙段（台盆边沿↔淋浴屏边沿）内居中，两侧预留对称操作空间
- **台盆选型**：可用墙面>标准台盆宽度时，选定制台盆（horizontal_fill），最大化台面
- **窄卫生间集中布置**：宽度≤1800mm 时，马桶与台盆集中于同一侧墙面，对侧保留完整通道
- **花洒靠实墙**：花洒安装在淋浴区内的实墙（非窗墙），走管需要实墙支撑
- **淋浴可临窗**：淋浴区域本身可临窗布置（采光通风好），不受卧室的避窗规则限制

### 2.3 开放空间（客餐厅一体）— MVP 暂不考虑

**适用房间**：客餐厅一体、大客厅、开放式厨房等无墙体分隔的大面积空间。

**与封闭空间的本质差异**：

开放空间需要一个封闭空间不需要的前置阶段——**空间分区**。当前工作流假设 zones.json 已经是"1 房间 = 1 分区"，但客餐厅一体的场景下，一个物理房间需要被切分为多个设计区。

**设计流程**（未来实现）：

```
1. 识别过道动线 → 根据走廊/入口/房型特点规划主通道
2. 切分功能区   → 通过过道和建筑轮廓（如内凹角）把大空间切为小空间
3. 分配功能     → 根据空间特征（面积、是否靠主窗）分配客厅区/餐厅区
4. 写入分区     → 修改 schemes/zones.json，将大分区拆为多个设计区
5. 逐区布置     → 每个设计区按封闭空间逻辑独立布置
```

**技术阻塞**：
- Server 端缺少自动分区算法（无过道识别、无动线分析）
- `InnerBoundary` 计算未实现（代码中 `ComputedBoundary = null`）
- 数据模型已就绪（zones.json 支持 circulation 标签、多 zone 共享 roomId），但算法空白

**决策**：MVP 阶段先跳过，专注封闭空间和卫生间。开放空间的分区能力作为长期目标。

## 三、卫生间布局模式分析

### 从截图提取的 5 种模式

基于 5 张典型卫生间布局截图，按**房型特征→布局方案**建立映射：

| 模式 | 房型特征 | 布局策略 | 洁具分布 |
|------|---------|---------|---------|
| A: 单侧线性 | 窄长型，宽≤1800mm | 全部沿一侧墙排列 | 台盆→马桶→淋浴间（门→窗） |
| B: L 形 | 窄长型，宽>1800mm | 淋浴间横占远端，其余沿侧墙 | 淋浴间顶部，马桶/台盆侧面 |
| C: 分墙 | 近方形，面积中等 | 洁具分布在不同墙面 | 台盆左墙，马桶右墙，淋浴间角落 |
| D: 三面分布 | 面积较大 | 三面墙各一类洁具 | 充裕空间，可考虑浴缸 |
| E: 半卫 | 小面积，无淋浴 | 马桶+台盆并列 | 最简配置 |

### 模式选择决策树（初版，待案例验证）

```
1. 是否有淋浴需求？
   └─ 否 → 模式 E（半卫）

2. 短边宽度 ≤ 1800mm？
   └─ 是 → 模式 A（单侧线性）
        └─ 对侧保留完整通道

3. 长宽比 > 1.5？
   └─ 是 → 模式 B（L 形）
        └─ 淋浴间横占短边端部

4. 面积 > 阈值（待定）？
   ├─ 否 → 模式 C（分墙布局）
   └─ 是 → 模式 D（三面分布）
```

**待细化**：
- 门的位置（长边 vs 短边）对模式选择的影响
- 窗的位置如何影响淋浴间朝向
- 各模式的精确尺寸阈值需要更多案例验证

### 与封闭空间流程的本质差异

卫生间布置的核心是**查表**而非**规划**：

```
封闭空间：截图→理解空间→创造性决策→逐件放置→验证
卫生间：  截图→测量尺寸→查决策树→选模板→参数化微调→验证
```

Agent 在卫生间场景下不需要"像设计师一样思考"，只需要"像工程师一样执行"。

## 四、技术约束分析

### Skill 机制的限制

| 约束 | 说明 | 影响 |
|------|------|------|
| Skill 路由靠 description 关键词 | SDK 没有 `room_type`、`conditions` 等路由字段 | "布置卧室"和"布置卫生间"会命中同一个 Skill |
| 无 Skill 间上下文传递 | 每个 Skill 独立工作 | 多 Skill 串联需要通过文件系统共享状态 |
| 无 Skill 并行机制 | Skill 只能串联执行 | "布置全屋"无法并行处理多个房间 |

**结论**：按空间类型拆分为多个 Skill 文件在技术上可行但**收益不大**——路由精度不会因为拆分而提高，反而增加了文件管理成本。**在单个 SKILL.md 内部做分支**是更务实的选择。

### 数据模型的就绪度

| 能力 | 状态 | 说明 |
|------|------|------|
| Zone 支持多类型 | ✅ | ZoneType 枚举包含 Exclusion/Room/Designable |
| 标签系统 | ✅ | ZoneTag 已定义 shower/toilet/washing 等卫浴标签 |
| 标签→模块匹配 | ✅ | module_library.json 的 tags 与 zone.tags 交集筛选 |
| 自动分区算法 | ❌ | Server 无过道识别、无空间拆分工具 |
| InnerBoundary 计算 | ❌ | 代码中 `ComputedBoundary = null` |

### 替代方案对比

| 方案 | 优点 | 缺点 | 决策 |
|------|------|------|------|
| 多个 Skill 文件 + 路由器 Skill | 职责清晰 | SDK 路由不精准，文件管理成本高 | ❌ 排除 |
| SubAgent 模式 | 支持并行、显式调用 | 需要开发 Agent 代码 | ❌ 排除（MVP 过重） |
| **SKILL.md 内部分支** | 零架构改动，立即可行 | 单文件会变长 | ✅ 采用 |
| **placement_guide 按空间类型拆分** | 规则隔离清晰 | 通用规则（通道宽度等）需要重复或抽公共层 | ❌ 排除 |
| **placement_guide 单文件重组章节** | 改动最小，Agent 一次读取 | 文件较长 | ✅ 采用 |

## 五、决策记录

| # | 问题 | 决策 | 理由 |
|---|------|------|------|
| D1 | 路由机制 | SKILL.md 内部分支 | Skill 元数据不支持条件路由；内部分支零架构改动，立即可行 |
| D2 | 开放空间 | MVP 暂不考虑 | Server 端缺少分区算法，数据模型虽就绪但算法空白，优先解决已有能力覆盖的场景 |
| D3 | 卫生间模板位置 | 写在 placement_guide.md | 模板决策树属于设计知识（"什么情况下用什么布局"），不是工作流步骤 |
| D4 | 规范文件组织 | 保持单文件，按空间类型重组章节 | Agent 一次 Read 获取全部规则；拆多文件会增加工具调用次数且需要管理公共层 |

## 六、实施方案

### Phase 1：placement_guide.md 扩写卫生间章节

**目标**：把卫生间的模板决策树写入 placement_guide.md §5.6

**具体内容**：
- 5 种布局模式的详细描述（尺寸条件、洁具排列、示意）
- 模式选择决策树（基于宽度、长宽比、门窗位置）
- 各模式下洁具的参数化定位规则

**文件**：`BIMCanvas.Server/Templates/knowledge/placement_guide.md`

### Phase 2：SKILL.md 加空间类型分支

**目标**：在阶段 A 前增加空间类型判断，卫生间走独立子流程

**具体变更**：在 SKILL.md 的"阶段 A"章节前，增加：

```markdown
### 空间类型判断

根据目标分区的 tags 确定布置流程：
- 若 tags 包含 shower/toilet/washing → 跳转「卫生间布置流程」（§X）
- 其他 → 继续「封闭空间标准流程」（阶段 A/B）
```

在 SKILL.md 末尾（或阶段 B 之后）增加「卫生间布置流程」章节：

```markdown
## 卫生间布置流程

1. 测量分区尺寸（从 zone.rawBoundary 计算宽度、深度）
2. 识别门窗位置（从 openings.json 匹配）
3. 参照 placement_guide §5.6 的决策树，选择布局模式
4. 按模式放置洁具（从 module_library.json 选择）
5. 参数化微调（台盆宽度、淋浴屏尺寸等 horizontal_fill/parametric）
6. 写入 → validate_layout → 截图审查
```

**文件**：`BIMCanvas.Agent/templates/skills/generate-workflow/SKILL.md`

### Phase 3：placement_guide 章节重组

**目标**：按空间类型重组章节结构，减少跨空间规则混淆

**当前结构**（按功能组织）：
```
§4 尺寸标准（通道、门前净空）
§5 房间布置要点（§5.1客厅、§5.2主卧、§5.3次卧...§5.6卫生间）
§6 朝向决策逻辑（§6.1床、§6.2沙发...§6.4衣柜选墙）
§7 家具依赖关系
```

**目标结构**（按空间类型组织）：
```
§4 通用规则（通道宽度、门前净空、禁区约束）
§5 封闭空间规则
  §5.1 卧室（锚点、朝向、衣柜选墙、间距分配、成套依赖...）
  §5.2 书房
  §5.3 ...
§6 卫生间规则（模式决策树、洁具定位、参数化规则）
§7 家具依赖关系（跨空间通用）
```

**文件**：`BIMCanvas.Server/Templates/knowledge/placement_guide.md`
