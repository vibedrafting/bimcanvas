  1. Playwright Browser 复用策略

  您建议：服务内复用一个 Browser，每次新建 Context/Page

  我的补充理解：
  // 单例Browser + 池化Context的混合方案
  public class PlaywrightService
  {
      private IBrowser _sharedBrowser;
      private readonly SemaphoreSlim _semaphore = new(3, 3); // 限制并发

      public async Task<byte[]> CaptureAsync(RenderConfig config)
      {
          await _semaphore.WaitAsync(); // 并发控制
          
          try
          {
              // 复用Browser实例（启动一次）
              if (_sharedBrowser == null || !_sharedBrowser.IsConnected)
              {
                  _sharedBrowser = await _playwright.Chromium.LaunchAsync(new()
                  {
                      Headless = true,
                      Args = new[] { "--use-angle=swiftshader" }
                  });
              }
              
              // 每次请求新建Context（完全隔离）
              await using var context = await 
  _sharedBrowser.NewContextAsync(new()
              {
                  ViewportSize = new() { Width = 1920, Height = 1080 },
                  DeviceScaleFactor = config.Scale
              });

              var page = await context.NewPageAsync();

              // ... 渲染逻辑
       
              // Context自动销毁，不污染下次请求
          }
          finally
          {
              _semaphore.Release();
          }
      }
  }

  优势：
  - Browser启动慢（1-2秒），复用后首次后<200ms
  - Context隔离干净，不会状态污染
  - SemaphoreSlim控制并发（防止资源耗尽）

  2. 数据注入方式：window.__renderConfig vs URL Query

  您建议：用 window.__renderConfig 注入，不走长URL

  我的理解和补充：

  完全同意！长URL有大小限制（2KB），且不适合传递大型snapshot JSON。

  实现方式对比：

  // 方案A：page.AddInitScriptAsync（推荐，执行时机早）
  await page.AddInitScriptAsync($@"
      window.__renderConfig = {JsonConvert.SerializeObject(renderConfig)};
  ");
  await page.GotoAsync($"{webUrl}/screenshot-render");

  // 方案B：page.EvaluateAsync（执行时机晚，需等页面加载）
  await page.GotoAsync($"{webUrl}/screenshot-render");
  await page.EvaluateAsync($@"
      window.__renderConfig = {JsonConvert.SerializeObject(renderConfig)};
  ");

  我推荐方案A（AddInitScript），因为：
  - 在页面脚本执行前注入，渲染页可以在 onMounted 直接读取
  - 不需要等待页面加载完成再注入
  - 避免时序问题

  3. 区域截图：fitToBounds vs 精确裁剪

  您建议：先做 "fit to bounds 充满画布"

  我完全同意！但需要明确实现细节：

  fitToBounds 实现（新增 ThreeSceneService 方法）：
  // ThreeSceneService.ts
  export function fitToBounds(bounds: { minX, minY, maxX, maxY }) {
    const camera = getCamera() as OrthographicCamera

    const centerX = (bounds.minX + bounds.maxX) / 2
    const centerZ = (bounds.minY + bounds.maxY) / 2
    const width = bounds.maxX - bounds.minX
    const height = bounds.maxY - bounds.minY

    // 更新相机位置
    camera.position.set(centerX, 10000, centerZ)

    // 更新视锥体（关键：保持宽高比）
    const aspect = window.innerWidth / window.innerHeight
    if (width / height > aspect) {
      // 宽度主导
      camera.left = -width / 2
      camera.right = width / 2
      camera.top = width / 2 / aspect
      camera.bottom = -width / 2 / aspect
    } else {
      // 高度主导
      camera.top = height / 2
      camera.bottom = -height / 2
      camera.left = -height / 2 * aspect
      camera.right = height / 2 * aspect
    }

    camera.updateProjectionMatrix()
    render()
  }

  边距问题：
  - 当前实现是"精确适配"（bounds边缘贴画布边缘）
  - 如果需要边距，可以在调用前放大bounds：
  const padding = 500 // 500mm边距
  fitToBounds({
    minX: bounds.minX - padding,
    minY: bounds.minY - padding,
    maxX: bounds.maxX + padding,
    maxY: bounds.maxY + padding
  })

  ⚡ 我坚持的几个技术观点

  虽然完全接受KISS原则，但以下几点我认为值得保留：

  1. 并发控制（SemaphoreSlim）

  即使是串行处理，也需要限制最大并发数，避免：
  - 内存溢出（每个Browser实例约200MB）
  - CPU饱和（WebGL软件渲染消耗大）

  建议保留，配置为 MaxConcurrency = 3

  2. 渲染稳定性检测（等待3帧）

  Three.js渲染不是同步的，需要确保：
  - 所有几何体加载完成
  - 材质编译完成
  - 标签位置计算完成

  建议保留 渲染页中的 waitFrames(3) 逻辑

  3. 超时控制

  无头浏览器可能因为网络、资源加载等原因卡死

  建议保留 Playwright的超时参数：
  - page.GotoAsync(timeout: 30000)
  - page.WaitForFunctionAsync(timeout: 15000)
