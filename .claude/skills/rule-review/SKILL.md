> **审查的本质是诊断认知环境，不是逐条对标打勾。**

审查时始终用五个底层机制来判断问题（详见 `docs/Agent_Prompt_Design_Philosophy.md` §1）：

- **机制 1（注意力零和）**：每加一条规则，所有已有规则的权重都在被稀释。审查时问：去掉这条规则，Agent 行为会变差吗？
- **机制 2（激活而非注入）**：概念引入激活整个知识区域，规则修复只改一个参数——量级完全不同。审查时问：这里缺的是一条规则，还是一个 Agent 从未接触过的设计概念？
- **机制 3（WHY = 泛化）**：有 WHY 的规则能在边界场景中被灵活应用，无 WHY 的规则只能被机械执行。审查时问：这条规则教了"为什么"吗？
- **机制 4（示例 = 锚定）**：AI 从示例中提取模式比从文字中解析规则更自然。审查时问：这条规则能用示例替代吗？推论：**示例锚定基准，WHY 覆盖边界**。
- **机制 5（位置效应）**：头尾内容获得更多注意力，中间容易被遗忘。审查时问：最关键的规则是否放在了文件/章节的头部或尾部？

这五个机制能推导出所有具体检查——当你不确定某个问题是否值得报告时，回到机制层面判断。

## §3 模式 A：全面审查工作流

### A1. 理解审查背景

审查前先了解上下文：
- 用户为什么要做这次审查？（日常检查 / Agent 出了问题 / 刚做了大改动 / 其他）
- 用户有没有特定关注点？（"我觉得 SKILL.md 太长了" / "Agent 最近老在 L 形房间出错"）
- 近期有没有重大变更？（检查 git log）

如果用户没有主动说明，用发现式问题提取：
- "最近 Agent 有没有反复出现的布置问题？"
- "你对当前提示词体系最不满意的是哪个方面？"

### A2. 三层诊断式通读

按顺序读取 4 个文件。用三层视角阅读，每层带一个核心问题：

1. **信息架构**：Agent 读完这个文件后，能快速找到需要的信息吗？（结构、信噪比、职责归属）
2. **认知校准**：Agent 知道"为什么"要这样做吗，还是只知道"做什么"？（WHY、示例、约束层级）
3. **留白**：Agent 有发挥设计判断力的空间吗，还是每个决策点都被规则锁死了？（自由区域、软指导弹性）

每读完一个文件，记一句话直觉判断——哪层最强、哪层最弱。

### A3. 识别系统性问题 + 判断层级

基于 A2 的三层诊断，回答一个关键问题：

**如果只能改一件事来让这个提示词体系变得更好，应该改什么？**

然后追问：**这个问题出在哪个层级？**

判断方法（三个递进问题，借鉴 rule-tuning §1.4）：
1. Agent 有没有相关信息？
   - 有但用错了 → **参数层**（数值/措辞偏差）或**规则层**（逻辑错误）
2. 没有相关信息 → 缺的是什么？
   - 缺一个数值 → 参数层
   - 缺一条操作指导 → 规则层
   - 缺一整个设计概念 → **方法论层**（机制 2：引入概念的影响远大于添加规则）
3. 单个文件都没问题，但合在一起有矛盾？ → **架构层**

最多识别 2-3 个系统性问题，每个标注层级。

> **层级越高不代表越难修复。** 引入一个新设计概念（方法论层）可能比叠加 3 条修补规则（规则层）更简洁有效。

### A4. 针对性深入分析

对 A3 识别的系统性问题，从五个机制出发深入分析：

| 如果问题特征是 | 最相关的机制 | 诊断方法 |
|--------------|------------|---------|
| Agent 行为僵硬/机械 | 机制 3（WHY = 泛化） | 抽查关键规则：有 WHY 的占比？约束层级是否区分了硬/软/自由？ |
| 规则之间矛盾 | 机制 1（注意力零和） | 矛盾规则 = 最严重的注意力浪费。追踪来源文件，检查跨文件一致性 |
| 某个文件过长/臃肿 | 机制 1（注意力零和） | 逐节问"去掉这段 Agent 会犯错吗？"——不会就是噪音 |
| Agent 在特定场景犯错 | 机制 2 + 机制 3 | 是缺规则还是缺概念？有无具体示例？规则只有 WHAT 还是有 WHY？ |
| Agent 缺乏自主设计能力 | 留白（控制的悖论） | 决策点是否全被规则覆盖？有无显式自由区域？ |
| Agent 输出格式/风格偏离预期 | 机制 4（示例 = 锚定） | 关键输出是否有示例锚定？抽象描述能否用 1-2 个具体示例替代？ |
| 关键规则被忽略/跳过 | 机制 5（位置效应） | 被忽略的规则在文件中的物理位置？是否在中间被"淹没"？能否移到头尾？ |

在分析每个问题时，始终追问：
- **堵 vs 疏**：是否用"禁止做 X"替代了"教会做 Y"？
- **层级匹配**：建议的修复是否与问题层级匹配？（参数修复解决不了方法论问题）

如需深入分析具体检查项，参考 [references/review-checklist.md](references/review-checklist.md)。

### A5. 结构性验证（兜底检查）

A3-A4 是假设驱动的，可能遗漏不在假设范围内的问题。以下两项结构性检查作为兜底：

**职责边界验证**（对照 `references/prompt-file-map.md`）：
- [ ] SKILL.md 中是否包含了应属于 placement_guide 的设计标准数值？
- [ ] placement_guide 中是否包含了应属于 SKILL.md 的工作流步骤？
- [ ] module_library 中是否包含了应属于 placement_guide 的通用设计原则？
- [ ] 同一规则是否在多个文件中重复表述？（列出具体条目）
- [ ] BIMCANVAS.md 是否保持了纯"身份 + 规范"定位？
- [ ] module_library 中是否引用了外部文件？（必须自包含）

**跨文件一致性检查**（对照 `references/prompt-file-map.md` 跨文件追踪表）：
1. 选取表中 6 条高频同步项（衣柜选墙、间距分配、侧对窗户、通道分类、床头柜成套、顶角规则）
2. 追踪每条规则在各文件中的表述
3. 标记不一致之处（用词差异、数值差异、适用范围差异）

### A6. 与用户讨论发现

在生成正式报告前，先与用户讨论关键发现：
- "我认为当前体系最大的问题是 [X]，这是一个 [层级] 层面的问题，理由是 [证据]"
- "这个问题的影响范围是 [具体场景]"
- "我建议的改进方向是 [方向]——你同意吗？有没有我没考虑到的背景？"

聚焦最重要的 2-3 个，确认方向后再出完整报告。

### A7. 生成审查报告

```
## 审查报告

### 核心发现
[1-2 段话描述体系最大的系统性问题及其影响——这是报告的灵魂，不是问题清单]

### 问题清单（按层级 × 严重度排序）

| # | 层级 | 严重度 | 文件 | 位置 | 问题描述 | 建议修复 |
|---|------|--------|------|------|---------|---------|
| 1 | 方法论 | 高 | ... | §X.X | ... | ... |

层级：参数 / 规则 / 方法论 / 架构
严重度：高（错误决策）/ 中（效率降低）/ 低（风格/一致性）

### 改进建议（按优先级排序）
1. [建议]：涉及文件 + 问题层级 + 预期效果
```

## §4 模式 B：局部变更检查工作流

### B1. 理解变更意图

两种方式获取 diff：
- 用户直接提供 diff 文本
- 用户告知修改了哪个文件 → 执行 `git diff HEAD~1 -- <file_path>` 获取

**先理解意图再检查合规**：
- "这次修改是为了解决什么问题？"
- "这个问题出现在什么场景？Agent 当时是怎么做的？"（如有日志）

理解意图后，判断：
- 这次变更修的是什么层级的问题？（参数/规则/方法论/架构）
- 变更手段与问题层级是否匹配？

### B2. 变更归类

| 变更类型 | 判断依据 | 检查重点 |
|---------|---------|---------|
| 新增规则 | diff 中有纯新增内容 | 新增规则 5 问 + 机制检查 |
| 修改规则 | diff 中有替换内容 | 语义变化 + 跨文件同步 |
| 删除规则 | diff 中有纯删除内容 | 删除后是否留下引用悬空 |
| 结构调整 | 章节移动/合并/拆分 | 职责边界是否仍正确 |

### B3. 机制驱动检查

1. **机制 1**：新增规则是否会稀释现有关键规则的权重？（去掉这条 Agent 会犯错吗？）
2. **机制 3**：新增/修改的规则是否包含 WHY？
3. **堵 vs 疏**：如果是新增禁止项，能否改为正面引导？
4. **职责归属**：变更内容是否放在了正确的文件中？
5. **新增规则 5 问**（仅新增时）：解决的是已发生还是假想的问题？放在了正确文件？去掉后 Agent 会犯错？与现有规则有冲突？需要解释原因？
6. **机制 4**：新增/修改的规则是否可以用示例替代或辅助？复杂规则有无配套示例？
7. **机制 5**：变更是否影响了文件中关键规则的位置？关键规则是否仍在头尾？

### B4. 跨文件影响分析

对照 `references/prompt-file-map.md` 跨文件追踪表，判断哪些文件需要同步：

| 变更了 | 检查同步 |
|--------|---------|
| placement_guide | SKILL.md 检查清单 + module_library relation_rules |
| module_library | 是否仍自包含；placement_guide 对应规则是否需同步 |
| generate SKILL.md | placement_guide 的自检清单（§9.2） |
| BIMCANVAS.md | 禁止事项是否与其他文件矛盾 |

如果发现需要同步其他文件，先告知用户再执行。

### B5. 生成变更评审

```
## 变更评审

### 变更概要
- 文件：[路径]  类型：[新增/修改/删除/结构调整]  层级：[参数/规则/方法论/架构]
- 摘要：[一句话]

### 检查结果

| 检查项 | 结果 | 说明 |
|--------|------|------|
| 层级匹配 | PASS/FAIL | 变更手段是否与问题层级匹配 |
| 职责归属 | PASS/FAIL | ... |
| 包含 WHY | PASS/FAIL | ... |
| 跨文件一致 | PASS/FAIL/需同步 | 需同步时列出文件和位置 |

### 改进建议（如有）
1. ...
```

## §5 审查质量准则

1. **问题必须具体**：指出文件名、章节号、具体内容，不要笼统说"结构不够清晰"
2. **建议必须可执行**：说明"把 X 从 A 文件移到 B 文件的 §Y 章节"，而非"建议优化结构"
3. **区分"不好"与"不同"**：审查者的偏好不等于设计缺陷，以五个底层机制为判断标准
4. **关注实际影响**：优先报告可能导致 Agent 错误决策的问题，风格问题其次
5. **不替代 rule-tuning**：发现具体布置规则有误时，建议用户启动 `/rule-tuning` 工作流处理
6. **系统性问题优先于逐条问题**：审查的价值在于发现"一处改动能提升整体"，而非列出"20 条规则各自哪里不合格"
7. **判断层级优先于列举问题**：一个层级判断正确的改进建议，比十个逐条检查结果更有价值。审查的最高目标不是发现最多问题，而是找到最高杠杆的改进点
