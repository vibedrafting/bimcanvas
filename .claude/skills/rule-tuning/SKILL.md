# Agent 规则调优工作流

> **调优的本质是理解，不是修补。** 当 Agent 出错时，第一反应往往是"找到要改的规则"——但如果只看到规则层面的问题，修出来的也只是规则层面的补丁。退后一步想：Agent 的行为说明它缺少什么认知？问题出在哪个层级——是参数偏了、规则错了、还是整个方法论需要重新思考？不确定时，向用户提问——用户对设计意图的理解往往比你对规则体系的分析更接近问题本质。

## §1 收集与理解

### 1.1 收集证据

以下证据缺失任何一项，先向用户索取：
- Agent [THINK] 日志（完整推理链）
- 用户评价（哪里不对、期望是什么）
- 截图（实际结果 vs 期望结果，如有）
- 房间基本信息（房型、面积、门窗位置）

### 1.2 还原 Agent 决策链

读 [THINK] 日志，重建 Agent 的完整推理过程：
- Agent **看到了什么**（房间数据、引用了哪些规则条目、引用顺序）
- Agent **怎么推理的**（如何从规则推导出具体数值和选择）
- Agent **最终做了什么选择**
- 对比同类房间的推理链——差异点即问题信号

### 1.3 找到偏离点

在决策链中找到**第一个偏离合理方向的节点**——不是"哪里出错了"，而是"从哪里开始走偏的"。

这两个问题的区别：
- "哪里出错了" → 看到的是症状（衣柜放错墙）
- "从哪里开始走偏的" → 看到的是原因（Agent 在候选墙面评估时就漏掉了北墙）

### 1.4 追问：为什么在这个节点走偏了？

不要急于分类。先问三个递进问题：
1. Agent 在这个节点**有没有**相关信息？（是信息缺失，还是有信息但没用对？）
2. 如果有信息——**为什么没用对**？（是规则矛盾、语气过弱、还是解读歧义？）
3. 如果没有信息——**缺的是什么层面的信息**？（缺一个数值？缺一条规则？还是缺一整个设计概念？）

这三个问题的答案会自然指向问题层级（§3），不需要提前选分类。

> **Agent 自诊断偏差**：Agent 的自我分析（如"我认为缺少 XX 规则"）是有价值的线索，但 Agent 天然偏向规则级解释——它只能在已有的规则框架内分析问题。当 Agent 说"需要一条规则来..."时，追问：**是真的缺规则，还是缺一个 Agent 从未接触过的设计概念？**

## §2 与用户对齐

完成 §1 后，在确定修复方向之前与用户交互。

### 该问什么

**发现式问题**（提取 AI 不具备的信息）：
- "这个布置错误，在你看来最不能接受的是哪一点？"
- "你在实际项目中见过这种户型的合理布置方式吗？"
- "这个问题是第一次出现，还是在其他房间/项目中也见过类似模式？"

**校准式问题**（对齐双方理解）：
- "我看到两种可能：A 是 [解读 A]，B 是 [解读 B]。你的直觉倾向哪个？"
- "我倾向在 [文件] 中做 [方向性描述]，而不是 [替代方案]。你怎么看？"

### 不该问什么

- ❌ "我的分析对吗？" → 用户只能说对或不对，无法贡献新信息
- ❌ 罗列所有可能性让用户选 → 应该有自己的判断，提出具体假设让用户校准

### 何时可以跳过

如果用户在 §1 提供反馈时已经明确说明了问题原因和期望方向（如"这里应该用 L 形布局"），且你的 §1 分析与用户描述一致，可以直接进入 §3，不需要额外交互。

## §3 判断问题层级

基于 §1 的理解和 §2 与用户的对齐，判断问题出在哪个层级：

| 层级 | 信号 | "最小有效改动"在该层级意味着 | 案例 |
|------|------|---------------------------|------|
| **参数层** | Agent 方向对了，但具体数值/语气/措辞有偏差 | 改一个数值或调整一处措辞 | 案例 2：间距"可缩减至"→"应取最小值" |
| **规则层** | Agent 引用了规则但逻辑有错，或缺少一条具体操作指导 | 修正/新增一条规则（可用附录 A 的 5 分类辅助定位） | 案例 1：通道标准缺少场景映射 |
| **方法论层** | Agent 对该房间类型/场景的整体设计思路有问题——不是某条规则错了，是整个思考框架偏了 | 重构 placement_guide 对应章节或引入新的设计概念 | 案例 7：从线性衣柜 → 引入 L 形转角概念 |
| **架构层** | 三个注入文件的职责划分或交互方式导致了系统性问题——单个文件没错，但合在一起有"责任真空" | 调整文件间的信息分布或引用关系 | 案例 4：§5.2 唯独缺少"紧凑房型"限定词 |

> **层级越高，改动范围越大，但不代表越难。** 案例 7 最终的修复（引入 L 形转角概念）比初始的错误方案（叠加 3 条禁止规则）更简洁、更有效。高层级的改动往往是"换一种思考方式"，而非"改更多文件"。

> **判断不确定时**，回到 §2 向用户提问。用户说"这种户型在实际设计中通常用 XX 方式处理"这类信息，能直接帮你区分是规则层还是方法论层的问题。

## §4 设计改动

### 4.1 读取相关文件

根据 §3 判定的层级，读取对应文件：

| 层级 | 必读 |
|------|------|
| 参数层 | 包含目标规则的那一个文件 |
| 规则层 | 目标规则所在文件 + 检查其他文件中的相关引用 |
| 方法论层 | placement_guide 对应章节 + generate-workflow SKILL.md 对应步骤 |
| 架构层 | 三个注入文件的相关章节（见附录 A 注入点表） |

### 4.2 设计方案

四条原则：
1. **在正确层级上做最小有效改动** — §3 已确定层级，在该层级内追求精简
2. **一处定义** — 规则只在职责匹配的文件中定义（见附录 A 文件职责表）；module_library 必须自包含，禁止引用外部文件
3. **WHY 测试** — 每条改动问：这教 Agent "为什么"还是仅告诉"做什么"？纯 WHAT 的改动容易退化为机械规则；包含 WHY 的改动能在规则未覆盖的场景中引导 Agent 自主推导
4. **反矛盾检查** — 新增/修改后，在三个注入文件中搜索相关关键词，确认无冲突

为每处改动填写：

| # | 文件 | 位置 | 当前内容 | 改为 | 理由（WHY） |
|---|------|------|---------|------|------------|

### 4.3 与用户确认方案

向用户展示改动方案表。重点确认：
- 改动层级是否合理（"我认为这是方法论层面的问题，需要重构 §7.4，而非加一条规则"）
- 改动范围是否足够 / 是否过度

用户确认后再执行。

## §5 执行与验证

执行 §4 确认的改动后，验证：
- [ ] 用户在目标房间重新运行布置，关键指标改善
- [ ] Agent [THINK] 日志中引用了更新后的规则/概念
- [ ] 抽检至少一个同类型房间，确认无副作用
- [ ] 将本次调优记录到 references/case-studies.md（偏离点 → 层级 → 修复 → 效果）

## 附录 A：参考工具（按需查阅）

### 规则的 3 个注入点

| 注入点 | 源码路径 | Agent 读取时机 | 职责（只放这类内容） |
|--------|---------|---------------|---------------------|
| **设计指南** | `BIMCanvas.Server/Templates/knowledge/placement_guide.md` | 前置准备（步骤2） | 设计原则、标准值、评估方法论 |
| **执行工作流** | `BIMCanvas.Agent/templates/skills/generate-workflow/SKILL.md` | 每个执行步骤 | 步骤序列、入口/出口条件、检查清单、常见误判提醒 |
| **家具规则** | `BIMCanvas.Server/Templates/modules/module_library.json` | 放置每件家具时 | 模块尺寸约束、放置拓扑、模块间关系（跨项目通用，自包含，禁止引用外部文件） |

**规则一处定义、其他处引用，不跨文件复制内容。修改后检查 3 个注入点无矛盾。**

### 规则问题 5 分类

> 仅在 §3 判定为"规则层"问题时，用此表辅助定位具体规则问题类型。

| # | 类型 | 特征 | 修复策略 |
|---|------|------|---------|
| 0 | **概念缺失** | Agent 缺乏设计模式/空间策略的认知——日志中完全没有讨论该概念 | 在 placement_guide 中引入设计概念（含 WHY 设计理念），教 Agent 理解"为什么"，而非添加"做什么"的机械规则 |
| 1 | **规则冲突** | 多条规则互相矛盾（最隐蔽） | 明确优先级或删除矛盾项 |
| 2 | **语气过弱** | "可/建议"致 Agent 不执行（最常见） | "可"→"应"/"取最小值" |
| 3 | **规则歧义** | 规则存在但 Agent 解读错误 | 补充映射/注释 |
| 4 | **规则缺失** | Agent 没有找到相关指导 | 新增规则（注意与 type 0 区分——type 0 缺的是概念认知，type 4 缺的是具体操作指导） |

### 文件职责速查

> 详见 `docs/Agent_Prompt_Design_Philosophy.md` §3

| 判断条件 | 放入 |
|----------|------|
| 这是一个执行步骤、阶段入口条件、或已知误判陷阱？ | **SKILL.md** |
| 这是设计原则、间距标准值、评估方法论、房间类型规范？ | **placement_guide.md** |
| 这是某个具体模块的尺寸/拓扑/关系约束？ | **module_library.json** |

**反模式自检**：
- SKILL.md 中出现了具体数值（如"窗侧 200mm"）→ 应放 placement_guide
- 同一条规则在多个文件中重复 → 一处定义，其他处引用
- placement_guide 中写了工作流步骤 → 应放 SKILL.md
- module_library 中出现了对外部文件的引用（如"参照 placement_guide §X.X"）→ 应改为自包含描述

## 附录 B：常见调优反模式

**反模式 1："加规则禁止 X"**
错误：案例 7 初版"§7.4 新增：禁止选择床对面墙放衣柜"
正确：引入 L 形转角衣柜概念，让 Agent 理解为什么不选对面墙
教训：堵不如疏——"禁止做 X"不如"教会做 Y"

**反模式 2："Agent 说缺规则就加规则"**
错误：直接采纳 Agent 自诊断"我认为缺少 XX 规则"
正确：追问——是缺规则，还是缺一个 Agent 从未接触过的设计概念？
教训：Agent 天然偏向规则级解释——它只能在已有框架内分析问题，看不到自己的概念盲区

**反模式 3："只看出错的那个文件"**
错误：案例 4 只修了 §5.2，没检查 §4.1/§5.3/module_library 的同步性
正确：跨文件搜索同一规则的所有出现处，确认限定词一致
教训：规则在跨文件传播中会丢失限定词——一处漏了，Agent 恰好优先读到那一处

**反模式 4："问题修了就够了"**
错误：案例 1 只修了出错的 rz_2，没检查同类型的 rz_1
正确：同类房间全部抽检，确认一致性
教训：单点修复可能引入新的不一致——修好一个房间，破坏另一个房间的平衡
