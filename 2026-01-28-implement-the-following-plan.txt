
● 方案B：全局事件驱动的分支同步机制 - 详细讲解

  一、核心设计理念

  1.1 从"拉"到"推"的范式转变

  当前问题（拉模式）：
  用户操作 → 组件主动请求 → Server查询 → 返回数据 → 更新UI
           ↑ 每次都要等待 ↑

  方案B（推模式）：
  Server数据变化 → 主动推送事件 → 前端监听 → 自动更新
                    ↑ 用户无感知 ↑

  1.2 KISS原则的体现

  虽然改动文件多，但架构更简单：
  - 组件层：只读数据，不关心刷新逻辑
  - Store层：统一监听事件，集中管理数据
  - Server层：数据变化时主动通知，而非等待询问

  1.3 关键设计决策
  ┌──────────┬──────────────┬──────────────────────────────────────────────────┐
  │  设计点  │     方案     │                       理由                       │
  ├──────────┼──────────────┼──────────────────────────────────────────────────┤
  │ 事件载荷 │ 空对象 {}    │ KISS：避免在Server端推断分支名，前端统一刷新即可 │
  ├──────────┼──────────────┼──────────────────────────────────────────────────┤
  │ 触发时机 │ 4个端点      │ 只在真正改变分支列表的操作后触发                 │
  ├──────────┼──────────────┼──────────────────────────────────────────────────┤
  │ 防抖机制 │ 模块级flag   │ 避免并发重复请求，保护API                        │
  ├──────────┼──────────────┼──────────────────────────────────────────────────┤
  │ 初始化   │ 首次主动拉取 │ 页面加载时立即获取最新数据                       │
  └──────────┴──────────────┴──────────────────────────────────────────────────┘

  二、完整数据流链路

  2.1 正常流程（Agent创建分支）

  sequenceDiagram
      participant Agent as Agent (Python)
      participant Server as GitController
      participant Hub as SignalR Hub
      participant SignalR as SignalRService (Web)
      participant GitStore as gitStore
      participant Component as 所有组件

      Agent->>Server: POST /api/git/ai-job
      Server->>Server: 创建worktree和临时分支
      Server->>Hub: BroadcastBranchesChangedAsync()
      Hub->>SignalR: SendAsync("BranchesChanged", {})
      SignalR->>Window: dispatchEvent('bimcanvas:branches-changed')
      Window->>GitStore: 监听器触发
      GitStore->>GitStore: 检查防抖flag
      GitStore->>Server: GET /api/git/branches
      Server-->>GitStore: 返回最新分支列表
      GitStore->>GitStore: branches.value = 新数据

      Note over Component: Vue响应式系统自动触发
      GitStore-->>Component: computed自动重新计算
      Component->>Component: UI自动更新（无延迟）

      User->>Component: 打开下拉框
      Component->>Component: 直接读取gitStore.branches
      Note over Component: ✅ 数据已是最新，无需等待

  2.2 关键环节解析

  环节1：Server端广播

  // GitController.cs
  private async Task BroadcastBranchesChangedAsync()
  {
      // 向所有连接的Web客户端推送事件
      await _hubContext.Clients.All.SendAsync("BranchesChanged", new { });
      _logger.LogInformation("[GitController] 广播分支变更事件");
  }

  为什么是空对象？
  - 不需要告诉前端"哪个分支变了"
  - 前端统一调用 fetchBranches() 获取完整列表
  - 避免Server端复杂的分支名推断逻辑（特别是worktree场景）

  环节2：SignalR客户端接收

  // SignalRService.ts
  this.connection.on("BranchesChanged", () => {
      console.log('[SignalR] 收到分支变更事件');
      // 转发为浏览器原生事件
      window.dispatchEvent(new CustomEvent('bimcanvas:branches-changed'));
  });

  为什么要转发为window事件？
  - SignalR只负责通信，不关心业务逻辑
  - gitStore可能在SignalR连接前就初始化了
  - 解耦：任何模块都可以监听这个事件

  环节3：gitStore监听并刷新

  // gitStore.ts
  let branchSyncStarted = false;  // 防止重复初始化

  const startBranchSync = () => {
    if (branchSyncStarted) return;

    // 1. 首次主动拉取
    fetchBranches();

    // 2. 监听后续变更
    window.addEventListener('bimcanvas:branches-changed', () => {
      console.log('[GitStore] 收到分支变更事件');
      fetchBranches();
    });

    branchSyncStarted = true;
  };

  关键特性：
  - 全局单例：模块级变量确保只初始化一次
  - 首次拉取：页面加载时立即获取数据
  - 持续监听：之后依赖事件驱动

  环节4：防抖保护

  const isFetchingBranches = ref(false);

  const fetchBranches = async (): Promise<void> => {
    // 如果已有请求进行中，跳过
    if (isFetchingBranches.value) {
      console.log('[GitStore] 跳过重复请求');
      return;
    }

    try {
      isFetchingBranches.value = true;
      // ... 发送API请求 ...
    } finally {
      isFetchingBranches.value = false;
    }
  };

  为什么需要防抖？
  - 如果Server在短时间内创建多个分支（虽然少见）
  - 如果多个组件同时触发刷新（虽然我们已经清理了）
  - 保护API，避免重复请求

  环节5：Vue响应式传播

  // gitStore.ts
  const branches = ref<BranchInfo[]>([]);  // 响应式引用

  // AICommandCenter.vue
  const availableBranches = computed(() => gitStore.branches);

  // 当 branches.value 变化时：
  // 1. Vue响应式系统自动检测
  // 2. 所有依赖的computed自动重新计算
  // 3. 模板自动重新渲染

  这就是为什么组件"无需做任何事"：
  - 组件只读 gitStore.branches
  - Store负责更新数据
  - Vue负责传播变化

  ├───────────────────────┼────────────────────────────────────────┤
  │ POST /discard         │ 只丢弃更改，不影响分支列表             │

  五、关键优势分析

  5.1 性能优势
  ┌─────────────────┬───────────────────────────┬───────────────────────┐
  │      场景       │       方案A（当前）       │    方案B（升级后）    │
  ├─────────────────┼───────────────────────────┼───────────────────────┤
  │ 打开下拉框      │ 等待API响应（500-1000ms） │ 立即显示（0ms）       │
  ├─────────────────┼───────────────────────────┼───────────────────────┤
  │ Agent创建分支后 │ 需要手动打开才能看到      │ 自动更新，随时可见    │
  ├─────────────────┼───────────────────────────┼───────────────────────┤
  │ 高频操作        │ 每次都请求API             │ 防抖保护，最多1次请求 │
  └─────────────────┴───────────────────────────┴───────────────────────┘
  5.2 架构优势

  解耦：
  - 组件不关心"何时刷新"，只读数据
  - Store统一管理数据同步逻辑
  - Server主动推送，而非被动响应

  可维护性：
  - 新增组件：无需添加刷新逻辑，直接读 gitStore.branches
  - 新增端点：只需在Server端添加一行 BroadcastBranchesChangedAsync()
  - 调试简单：控制台日志清晰展示事件流

  可扩展性：
  - 未来支持多用户协作：分支锁状态实时同步
  - 未来支持更多实时功能：文件变更、构建状态等
  - 统一的事件驱动模式，易于添加新事件类型

  5.3 用户体验优势

  即时反馈：
  - Agent创建分支后，下拉框自动显示（无需刷新页面）
  - 其他用户删除分支，当前用户立即看到更新

  无感知同步：
  - 用户不需要"刷新"或"重新打开"
  - 数据总是最新的，符合直觉

  六、潜在风险与缓解

  6.1 并发请求风险

  问题：如果Server在短时间内触发多个事件
  缓解：isFetchingBranches 防抖flag

  6.2 SignalR断线风险

  问题：网络断开时无法接收事件
  缓解：
  - SignalR自动重连机制
  - 重连后手动调用一次 fetchBranches()（可选优化）

  6.3 初始化顺序风险

  问题：如果在SignalR连接前就监听事件
  缓解：
  - 在 signalRService.start() 之后调用 startBranchSync()
  - 模块级flag防止重复初始化
